# `/register-sources`

Add or modify external data sources for this project. The intake protocol that runs at new-workspace setup lives here as a returning-workspace surface — same questions, same outputs, callable any time the source landscape changes.

This skill implements the intake protocol defined in `references/external-sources/source-registration-framework.md §3`. Read that document for the full schema, the field semantics, and the rationale. This skill is the orchestration; the framework is the contract.

**Script path resolution.** No scripts are invoked here directly — the skill writes registration YAML and unit files via the standard write tools. To find the framework reference, derive the path mechanically on every harness: take the absolute path you loaded this `SKILL.md` from and replace `/skills/register-sources/SKILL.md` with `/skills/core/references/external-sources/source-registration-framework.md`. The loaded path is always available; `${CLAUDE_PLUGIN_ROOT}` is NOT reliably injected (see `protocols/startup.md`) and is a fallback only. Don't construct paths against a guessed plugin base.

---

## Step 1 — Read current state

Read `<project>/_sources/` if it exists. List every registered source by name with its `authority` field. If the directory doesn't exist, say so plainly: *"No sources registered yet. Let's add the first one."*

If sources are already registered, narrate what's there in plain voice — count, names, and a one-line summary of each authority statement. Don't bullet-table-bomb the user; one or two sentences is fine.

---

## Step 2 — Ask what's changing

Three branches, one question: *"Adding a new source, modifying an existing one, or just auditing what's registered?"*

- **Audit only.** The narration from Step 1 is the audit. Stop here unless the user has follow-ups.
- **Add new.** Go to Step 3 with the new-source flow.
- **Modify existing.** Go to Step 3 with the re-intake flow per `source-registration-framework.md §"Re-intake"`.

---

## Step 3a — New-source intake

Walk the framework's six-step intake protocol for each new source. Plain voice, one question at a time — don't front-load a wall of questions.

1. **Name and discover.** Ask for the source's human-readable name (e.g., *"team task tracker"*, *"design review docs"*). If the user has an installation orchestration layer that can enumerate sources, surface what's available; otherwise the user provides the name directly.
2. **Authority decision.** Authority means: what can CORE reliably learn from this source, and what should it not trust? Give the user that framing first if the term is new to them, then ask: *"What's this source's authority for this project's intelligence?"* One or two sentences. The prose answer becomes the `authority` field on the registration AND the body of a `source-of-authority-<source-name>` unit in `<project>/_memories/` per the annotation framework.
3. **Confidence + relevance + cadence + kind.** Surface the installation's suggested defaults if the installation provides any; otherwise ask the user directly. The field semantics in framework §1 define each value in terms of data-shape signal, not source category — `kind` describes the shape of the data (field-typed records, mixed-shape content with consistent metadata, prose without enforced structure), `cadence` describes when the source should be pulled, `confidence-default` describes the default confidence absent specific signal. Read the field's framework-spec semantics to the user when they ask what a value means; don't pre-supply category-to-value mappings.
4. **Optional fields.** Ask about `confidence-overrides`, `stability-defaults`, `body-construction-policy`, `archive-policy-overrides` only if the user mentions a relevant pattern (e.g., *"some of these are auto-generated by automation — those shouldn't carry full confidence"* → `confidence-overrides` rule). Don't ask for these by default; they're rare.

   **Platform credentials.** If the source is a SaaS platform whose direct-tool API needs a tenant-specific constant — an Atlassian cloudId, a Salesforce org domain, a ServiceNow instance URL — that's not the session auth the harness manages, and CORE doesn't collect it (it's platform-specific). It lives in your installation's overlay config (e.g. an opaque `connector_overrides` block), and your overlay's docs say what to put there. If you're registering one of these and don't have the constant, the registration will look fine but every refresh will quietly fall back or fail auth — so check your overlay's platform profile before you finish. See `references/external-sources/source-registration-framework.md §1` (optional fields) for the boundary.
5. **Write the unit first, then the registration.** Create `<project>/_memories/source-of-authority-<source-name>.md` with the authority prose as the body. Then create `<project>/_sources/<source-name>.yaml` with all the fields the user supplied, including `authority-unit-id` pointing at the unit just written. Both writes happen in the same step — the registration's `authority-unit-id` is required, and the unit must exist before the field can be populated.
6. **Confirm and move on.** Read the registration back in one sentence. *"Registered the team task tracker as `session-pull`, structured, sourced-confidence default, authoritative for ticket status and ownership."* Ask if there's another source to add. Loop until done.

Create `<project>/_sources/` if it doesn't exist when writing the first registration. The leading underscore follows the standing convention for CORE-managed project subdirectories.

---

## Step 3b — Re-intake (modifying an existing source)

When the user wants to change an existing source's authority, relevance, confidence default, or other prose fields, the framework's `§"Re-intake"` rules apply. The registration updates and a new `source-of-authority` unit supersedes the prior per the supersedes-not-deletes pattern.

1. Read the existing registration YAML and find the linked `authority-unit-id`. If the field is missing, find the authority unit by convention (`<project>/_memories/source-of-authority-<source-name>.md`) and surface the missing-id as a finding.
2. Ask what's changing — authority restatement, cadence shift, confidence default revision, relevance criteria change, or kind reclassification.
3. For changes to authority or relevance: write a new `source-of-authority-<source-name>-<YYYY-MM-DD>.md` unit (date-stamped to disambiguate from prior). Set the new unit's frontmatter to mark the prior as `supersedes:` target. Update the prior unit's frontmatter to `status: retired`. Update the registration's `authority-unit-id` to the new unit's id and rewrite `authority` field to the new prose.
4. For changes to cadence, confidence default, or kind: update the registration YAML in place. Don't create a new authority unit — the source-of-authority statement hasn't changed.
5. Confirm the change in plain voice. *"Updated the team task tracker — authority now scoped to engineering tickets only; design tickets explicitly excluded. Prior authority unit retired and superseded."*

---

## Step 4 — Narrate results

Tell the user what happened in one or two sentences. Names of sources registered or modified, what changed, where the files landed. If the registration round-trips into anything else the user should know about — e.g., the installation's orchestration skill needs to be re-pointed at the new registration — say so.

If the user added the project's first source, mention that the installation now needs to write to `~/.core/workspaces/<id>/source-pull-log.jsonl` per the monitoring contract (framework §7) — `/finalize` will surface signals from this log on session close.

---

## What this skill does NOT do

- Does not run extraction. Source pulls and observation writes are the installation's job per the orchestration-skill contract (framework §6).
- Does not validate the installation's extractor pointer. The `extractor-pointer` field is opaque to CORE — the installation knows what its extractors look like.
- Does not auto-discover sources. CORE has no registry of "known external systems" per the framework's generalization guarantee.
- Does not run on a new workspace — the new-workspace intake in `protocols/startup.md` handles initial registration. This skill is for returning-workspace adds and modifications.
