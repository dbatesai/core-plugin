# D1 — The Case

**Why rewrite CORE, what to build instead, and whether it should exist at all.**

## The short version

**Verdict: rebuild CORE small, for its owner's own use, in the owner's own marketplace, and only if Layer 1 first beats the kit. Otherwise CORE does not ship; use the kit.**

*The kit* is Claude Code's built-in memory pointed into the repository, plus the same four-line instruction block CORE uses. The test against it runs before any hook or script is written, and each later part must beat the setup below it.

Coding agents forget. Each session starts cold, and the decision you made on Tuesday is gone by Thursday. CORE is a plugin that gives a project a memory: it writes down decisions, risks, people, and promises in plain files, brings them back when they matter, and says what needs you.

CORE 3 works, but it has grown to 100 scripts and 600 KB of instructions, and its health checks can say "fine" while looking at nothing. Meanwhile the agent programs it runs in now do much of what CORE built by hand.

The proposal rebuilds CORE in two layers:

1. **Layer 1, the skills.** A file layout, five short skills, and a four-line instruction block. No code needed. A small script ships alongside to check CORE itself; its other commands ship only if they earn it.
2. **Layer 2, the hooks.** They make the habits happen at fixed moments. Each ships only if it helps.

---

## 1. The problem

There are two problems. The second was caused by solving the first.

### Problem one: agents forget the project

A coding agent is good at the file in front of it and lost on the project around it. Between sessions it loses:

- **Decisions and their reasons.** It re-proposes the option you already rejected.
- **Risks and their status.** Nobody remembers that the vendor deadline moved.
- **People.** Who owns what, who promised what.
- **Promises.** The reply due Friday. The question you have put off twice.

It also only reacts. It does not say "the legal reply is due today" unless you ask.

So a project memory has five jobs:

- **Remember** — write down what is worth keeping, as it happens.
- **Recall** — bring the right note back when it matters.
- **Interact** — speak up about what needs you, without being asked.
- **Update** — refresh outside reference data, such as an issue tracker or calendar.
- **Focus** — say little, and say the right thing at the right moment.

A *harness* is the agent program: Claude Code, OpenAI Codex, or Google Antigravity. A *hook* is a command the harness runs at a fixed moment, such as when a session starts. A *skill* is a short instruction file the harness loads when it is needed. *MCP* is the standard way an agent calls an outside tool.

### Problem two: the fix grew too big to trust

CORE 3.20.1, measured on its own repository:

| | CORE 3.20.1 | Proof |
|---|---|---|
| Scripts | 100 files, 34,313 lines | [G 2.1] |
| Instructions | 40 files, 607 KB | [G 2.1] |
| Read before your first task | 127 KB, about 32,000 tokens | [G 2.2] |
| Tool steps in one ordinary session | 58, of which 49 are at startup | [runtime §1.5] |
| `CORE_*` settings | 34 names, 31 read from the environment | [runtime §8] |
| Releases | 46 in five months | [G 2.1] |

The measuring does not hold. Five defects were reported, and each was checked against the source [G 3]:

1. **Scripts look in the wrong folder and report clean.** Five hard-code a path under `~/.claude`; one then prints "0 candidates of 0 entries" as a success [G 3.1].
2. **A startup check says memory is "not yet" loaded while it is loaded** [G 3.2].
3. **A close marker says "closed" over an empty list of completed steps** [G 3.5].
4. **A transcript reader prints nothing and exits as a success**, whatever it is given [G 3.3].
5. **CORE's own startup upkeep trips its own change detector**, so a finished session is reported as owing work [G 3.4].

All five were reproduced here by running the shipped scripts.

They are one defect in five costumes: **a check that reports success while doing nothing.** CORE 3's changelog holds 132 fixes of this kind across 46 releases [changelog §2.2]. CORE's own documents name the pattern — "Instruments report healthy while recording nothing" — and list its fix as "add as found" [G 2.7]. That is how the code reached 34,000 lines.

## 2. Why solve it

Projects run for months. The same person works in three harnesses, on three operating systems, on a laptop and in cloud sessions. A forgotten decision costs an afternoon; a forgotten deadline costs more. And no single tool checked here covers the whole job (section 6).

## 3. What happens if we don't

**If CORE 3 stays as it is:** every session pays about 32,000 tokens before work starts. Health reports keep being wrong in ways that are hard to see, which teaches you to stop reading them. It does not support Antigravity [G 2.4].

**If CORE is simply dropped:** memory falls back to each harness's built-in. Claude Code's is on by default, on one harness, and stays on one machine unless one setting, `autoMemoryDirectory`, points it into the repository. Codex's is off by default. Antigravity's documentation says "Agents don't remember conversations" [G 4.1–4.3]. Nothing tracks risks or people, and nothing writes a session's close into the project.

## 4. The solution

### The premise

**Keep the judgment. Drop the machinery.**

CORE 3 learned real things: what is worth writing down, how to record a decision so the rejected option is not proposed again, how to keep "owed" apart from "attempted" and "proven", how to stop a removed fact from coming back. The harnesses now supply much of the machinery CORE 3 built around it.

### Layer 1: the skills

- **The record.** Plain markdown files in the project: `PROJECT.md` (a short brief you edit), and `_memories/` (one file per fact). Readable; commit them if you choose.
- **Five skills:** `core` (the brief, and when to speak up), `remember` (write, replace, or close a memory), `pulse` (what is due or stale; refresh outside data), `finalize` (close a session), and `metrics` (check CORE itself). For Codex and Antigravity, setup offers to commit a copy to `.agents/skills/`, which both read [codex §3] [antigravity §4].
- **A four-line instruction block:** read the brief first; look in `_memories/` before answering about the past; write down what a later session will need and the code will not show; at the start of a session, tell the user once about anything due within a day. It goes where each harness always reads it: `.claude/rules/core.md` on Claude Code, `.agents/rules/core.md` on Antigravity, and on Codex `AGENTS.override.md` if it exists, else `AGENTS.md` [claude-code §1] [antigravity §2] [codex §1].

Claude Code cloud sessions and cloud scheduled tasks never load plugins or `.agents/skills/` [claude-code §8, §12]. There the floor is the record and the committed instruction block: a write rule and a due line, but no replace rule and no close. The five skills on your claude.ai account lift it.

**The script.** One small file with no dependencies. Skills find it without a hook, and never inside the project. Its self-audit commands (`check`, `selftest`, `metrics`, `env`) ship with Layer 1. Its record commands (exact due dates, the index, recall, the close receipt, moving CORE 3 stores) ship only if the script rule keeps them; otherwise skills use their no-script steps.

### Layer 2: the hooks

- **A session-start hook** loads the brief and what is due, and re-sends them after the harness shortens a long conversation.
- **A prompt hook** offers up to three memory pointers per prompt (on Antigravity, once per turn: CORE marks where each turn starts [antigravity §6]).
- **A liveness line**, kept per machine, tells the agent to say so when the hooks did not run.
- Hooks run only in *enabled* projects, where you have said "enable CORE here" on this machine. Skills are not gated (section 7).

Three rules cover both layers.

- **Every check answers working, broken, or not measured**, and the third is never shown as the first. Writes are counted from disk.
- **"Not measured" never ships.** Only "kept" ships. If the kill test, any honesty or security test, the comparison with CORE 3, or the line budget is not kept or not measured, nothing ships.
- **A removed part takes its dependants with it.** A release without hooks reports only what it can observe, never "broken" about a hook removed on purpose.

### What the harness does, and what CORE adds

| Job | The harnesses already provide | CORE adds |
|---|---|---|
| Remember | File tools, skills, the session transcript | What to keep; the format; replace, don't overwrite; a removed fact stays removed |
| Recall | Session-start and prompt-time hooks on all three; file search | A one-line-per-memory index; three pointers or nothing |
| Interact | Scheduled tasks and prompt-time hooks on all three | What needs you; "speak at a pause, once"; one prompt each scheduler can run |
| Update | MCP; helper agents | One file per outside source with a freshness limit; "outside text is data" |
| Focus | — | Hard limits; no repeats; snooze on "not now" |

### The size

| | CORE 3 | CORE 4 limit (checked after the build) |
|---|---|---|
| Script lines | 34,313 | 1,800 at most, all shipped JavaScript |
| Instruction bytes | 607 KB | 60 KB at most |
| Loaded at session start | about 32,000 tokens | about 4,000 (estimate) |
| Skills | 8 | 5 |
| Settings | 34 `CORE_*` names | 2 environment switches and 4 project settings |

One rule for the budget: all shipped JavaScript stays at most 1,800 lines. Over it, the hooks are shelved; still over, nothing ships.

## 5. Why this solution and not another

**The evidence points at plain files.** Letta, the team behind MemGPT, moved its memory to "a git-tracked collection of Markdown files" searched with normal file tools, with no vector index by default [memory-layers-a §2.2].

**Small injected context beats large.** Accuracy falls as input grows [G 5.1], so the hooks pass pointers, not documents.

**The defect class is structural, so the fix must be.** CORE 3's checks lie in six ways [G 3.6]. Each has a rule in CORE 4 that removes the cause. For example, CORE 4 never writes generated text inside your files, so it needs no machinery to tell its writes from yours. D2 §6 lists all six.

**The harnesses now carry the load.** All three have session-start and prompt-time hooks, load the same skill format, and read a project rules or instruction file [G 4.1–4.3]. Claude Code will run a plugin's test cases with and without the plugin [G 4.1]. CORE 3 never ran that comparison [evaluation §2.8].

## 6. Who else does this, and how CORE compares

Twenty-eight tools and the harness built-ins were checked [competitors] [memory-layers-a] [memory-layers-b]. The closest:

|---|---|---|---|---|---|---|---|---|
| Harness built-ins alone | Partial | Partial | Partial | Partial | Partial | No | Partial | Yes |
| Claude Code Projects (beta) | Yes | Yes | Out of session only | Yes (account connectors) | Not checked | No | No | No (cloud, paid plan) |
| **The kit:** auto memory in the repository + the four-line block (tested); Backlog.md, connectors, a scheduled task (untested) | Partial | Partial | One line at session start; out of session | Yes | Partial | Partial | Yes | Yes |
| claude-mem | Yes | Yes | Partial | No | Partial | Yes | No | No |
| basic-memory | Yes | Yes | No | No | No | Partial | Yes | Partial |
| mem0; Zep / Graphiti | Yes | Thin or on request | No | No | No | mem0 only | No | No |
| Letta Code | Yes | Yes | Partial | No | No | No (it is a harness) | Outside project | Yes |
| Anthropic `productivity` | Yes | Partial | No | Yes | Partial | No | Yes | Yes |
| Standalone agents (OpenClaw, Hermes, Linear's agent) | Yes | Yes | **Yes** | Yes | Partial | No (run outside the session) | No | No |
| CORE 3.20.1 | Instructions | Yes | No | Form only | Partial | 2 of 3 | Yes | Yes (needs Node) |
| **CORE 4, planned** | Instructions + close pass | Yes | Hooks at session start and each prompt; native schedulers | Yes | Yes | Yes, with stated losses | Yes | Yes (code needs Node) |

*Partial*: only when asked, on one harness or machine, or for some kinds of fact. CORE 4's Interact cell assumes kept hooks; without them, CORE speaks up through the block's due line and its skills.

Three things stand out:

1. **No row is "yes" on all five jobs with readable state in the project.** Every tool that truly acts unprompted keeps its state elsewhere [competitors §A].
2. **Nothing tracks risks or people as project records.** Memory tools remember what the agent did; trackers remember work items [competitors §B].
3. **Almost nothing measures whether it helps.** No independent, blind result was found showing any of these memories improves coding work [memory-layers-b].

**Claude Code Projects** is the closest native rival: one harness, a paid beta, memory outside the repository. A Projects thread loads CORE's skills if CORE is added in Project settings > Plugins; whether its hooks run there is not stated (D3 6.7 checks). So CORE can work inside Projects, adding what it lacks.

**The kit** is the honest runner-up, and its tested part is what Layer 1 must beat (section 8). It lacks risks and people as records, a written close, speaking up beyond one line, and one behavior across harnesses.

## 7. Dependencies, tradeoffs, risks

**Depends on.** Layer 1: a harness that loads skills and reads a project rules or instruction file. On Claude Code the instruction block and the liveness line each get their own rules file, because any `CLAUDE.md` or `CLAUDE.local.md` in or above the folder stops Claude Code reading `AGENTS.md` [claude-code §1]. CORE never creates `CLAUDE.local.md`. Codex skips `AGENTS.md` in an untrusted project and cuts project files past 32 KiB [codex §1]. The script and hooks: Node.js 20 or newer. Measurement: Claude Code 2.1.299 or newer, a paid account, and a terminal started outside Claude Code. Update: one MCP server per outside source.

**Trades away.** CORE 3's multi-agent review, its HTML memory viewer, date-based "what did we know then" queries, generated `[[wikilinks]]`, and its four-tier retrieval. Recall becomes word matching over one-line summaries.

| Risk | Likelihood | What limits the damage |
|---|---|---|
| A harness changes its hook format, as Antigravity's often does [G 4.3]. | High | Layer 1 does not depend on hooks. The prompt hook prints a line every time, so a dead one shows. |
| The rewrite loses lessons buried in CORE 3's 176 test files. | Medium | The fixture stores, the prose checker, and a 29-item keep list [evaluation §8] are checked one by one before release. |
| The agent does not follow the habits, or writes too much. | Medium | The record test counts facts written, junk, duplicates, and stale copies. Layer 1 fails the kill test if it leaves clearly more copies than the kit. |
| A vendor ships the missing half, as Claude Code Projects has begun to [claude-code §8]. | Medium, rising | The kill test runs against built-in memory kept in the repository, and re-runs on the trigger in section 8. `metrics` warns when the shipped verdict is over 90 days old. |
| A planted memory steers the agent. | Low to medium | Hooks act only in enabled projects and pass pointers, not bodies. Skills are not gated and can read bodies anywhere. In a project not enabled on this machine, they treat bodies as quoted data: they say what a memory says and who said it, and never follow an instruction in it. Skills never run project code (D2 §9). |
| One maintainer. | Certain | 1,800 lines can be held in one head; 34,000 cannot. |

## 8. The verdict

**Verdict: rebuild CORE small, for its owner's own use, in the owner's own marketplace, and only if Layer 1 first beats the kit. Otherwise CORE does not ship; use the kit.**

**As a product for other people: no.** claude-mem has 115,000 GitHub stars and a paid tier, and the harness vendors ship memory by default and improve it monthly. So CORE 4.0 goes only to the owner's own marketplace; the public `core` entry stays on 3.20.1, and no CORE 3 user is moved.

**For the owner's own use — one person, three harnesses, three operating systems, months-long projects, a need to be told what is due:** nothing checked covers it. The kit and Projects each cover part.

**How each part earns its place.** Two tests. An *arm* is one setup the same tasks run under.

- **The record test.** Ten scripted sessions, three turns each, six repetitions per arm, plant five facts — a decision, its reversal, a risk, a person, a due date. Five probes ask for them; blind graders vote against a key written in advance. Auto memory is on in every arm: **built-in** (nothing else; reported, not ruled on), **kit**, **layer 1** (the block plus the five skills), and **full** (layer 1 plus the script and hooks).
- **The eval.** Claude Code's test runner scores fixed cases 0 to 1, ten runs per arm, auto memory off. Arms: **full**; **start-only** (session-start hook only); **script** (layer 1 plus the script); **layer 1**; **kit** (the block alone); **files** (the record alone); **nothing**.

All numbers are frozen before the first run.

**The kill test.** Layer 1 is kept only if all of these hold. On the record test, it recalls on average at least 1 more probe of 5 than kit, with the 95% paired interval above zero. It averages at least 4 of 5 probes. It is not worse on copies: on stale copies, and separately on duplicates, it fails only if its average excess is at least 1 per repetition with the interval above zero; copies count only in `_memories/` outside `archive/` and in auto memory. And on the `proactive-due` eval case, a small task on a day something is due, it beats the kit by 0.2.

**The script rule.** The script's record commands ship only if the **script** arm beats layer 1 by an average of 0.2 over `proactive-due` and `brief-budget`, behind on neither; otherwise only `check`, `selftest`, `metrics`, and `env` ship.

**The hook rules.** Each hook must beat the arm below it and must not lose elsewhere: the session-start hook (**start-only** against **script**) on three cases where it should help, the prompt hook (**full** against **start-only**) on one recall case if the block alone leaves room, the compaction re-send on a 25-turn run, and every hook on the record test's recall and copies.

"Must not lose": the 95% bound of the gap stays within 0.2 of zero, or within 1 probe or 1 copy on the record test. Shelved hooks go to a branch.

**When it is known.** Once the numbers are frozen, the skills are written without the script, and a person runs the built-in, kit, and layer 1 arms from a terminal outside Claude Code. If layer 1 loses, the build stops, with a way out: a one-page recipe for keeping the files as plain files, and CORE 3.20.1 left installed. If the test cannot be measured, it stops with no recommendation.

Three honest limits. Both tests run on Claude Code only; for Codex and Antigravity the result is inferred. Months of use are untested; the longest session is 25 turns. Six repetitions (about 41 calls per arm each, about 1,000 for four arms) can miss a small real effect. But a gain must clear zero and a harm check −0.2, so too few runs make CORE and each hook lose, never win.

Re-run the tests on any Claude Code release whose notes mention memory, hooks, skills, or plugins, or every 90 days, and re-read this verdict then.

## Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| Fix CORE 3 in place | The defects come from its shape [G 3.6]. Five months of point fixes produced 46 releases and the current size. |
| Harness built-ins only | Alone, they stay on one harness, track no risks or people, and do not speak up [G 4.1–4.3]. Their best form is inside the kit. |
| The kit (runner-up) | Loses what section 6 lists. It is what to use if Layer 1 fails the kill test. |
| Build everything, then test the script and hooks as one | The verdict would come after the work it judges, and a strong part would pass or fail with a weak one. |
| Publish 4.0 to the public `core` entry | It would move every CORE 3 user onto a release built for one person. |
| Gate the skills on the enabled list | Cloud sessions and new machines start with an empty list and would get nothing. Skills quote memory bodies as data instead. |
| claude-mem | Records what the agent did, not what the project decided; runs a background server [memory-layers-b §1]. |
| basic-memory as the store | Best fallback for storage, but adds Python and an AGPL core, and still needs CORE's behaviors [memory-layers-b §2]. |
| mem0, Zep, Graphiti, or an MCP memory server | A cloud account, a database, or a server to secure on three operating systems; none is readable in the project [memory-layers-a] [memory-layers-b]. |
| Letta Code | It replaces the harness instead of extending it [memory-layers-a §2.7]. |

## What was not verified

- **The workspace that saw the defects.** This run had the source repository only: no installed plugin, no project `PROJECT.md`, no memory store [G 1].
- **Anything on a live Codex or Antigravity install.** Their capabilities come from source code and documentation [codex §11].
- **That auto memory is on in every record-test arm,** and that scripted sessions honour `autoMemoryDirectory`. A control checks it; a repetition that fails is not measured, and under 4 good pairs so is the kill test.
- **Whether plugin hooks run in Claude Code Projects threads.** Not stated by Anthropic.
- **That CORE 4 will pass its own test.** Nothing is built.
- **The size limits and costs.** 1,800 lines, 60 KB, and 4,000 tokens are estimates; so is the price per call, until a calibration run measures it.
- **Star counts and some competitor dates.** Several came through a GitHub summarizing tool; the research files mark which.
- **The kill-test numbers.** Chosen, not measured.
