### R3-HA-01  —  major
- **Artifact:** D3, D2, D1 (follow-up to R2-HA-13, accepted as G15)
- **Location:** D3 contract F: "Key the turn as the first 8 hex characters of SHA-1 of `<conversationId>:<initialNumSteps>`." D3 step 3.4 Accept: "a later call with the same `lastUserInput` but a new `initialNumSteps` → recall runs again." D1 §4: "Session-start and per-prompt hooks on all three."
- **What is wrong:** Antigravity has no per-prompt event. `PreInvocation` fires before every model call, and the docs define `initialNumSteps` as "the number of steps currently in the trajectory". Each tool call in a turn adds steps, so the value changes on every call inside one turn. The docs' own example shows `invocationNum: 3` with `initialNumSteps: 10`. So the G15 key is new on every call, and the repeat rule never fires. The 3.4 test asserts exactly this wrong behaviour: same prompt, new step count, recall again. Step 8.4's fallback (`invocationNum == 0`) helps only if that counter restarts each turn, which the docs do not say. Antigravity already marks the turn boundary natively: `Stop` "fires when execution terminates".
- **What breaks if we ship it as-is:** On Antigravity, a turn with 15 tool calls gets 15 recall blocks. CORE sends them as `systemMessage` steps, which stay in the trajectory, not as transient ones. Each call also writes a non-repeat `prompt` row. So one long turn passes contract E's "≥ 3 `prompt` rows" bar for `no-handoff`. `pointer_rate` and the heartbeat count model calls, not prompts.
- **Suggested fix:** Add a `Stop` hook to the Antigravity `hooks.json` that writes a `turn-end` receipt. Treat the first `PreInvocation` after `SessionStart` or `turn-end` as the new turn, and answer `{}` to the rest. Rewrite the 3.4 test to match. Change D1's "per-prompt hooks on all three" to "per model call on Antigravity".
- **Evidence:** https://antigravity.google/docs/hooks.md §PreInvocation ("`initialNumSteps` | integer | The number of steps currently in the trajectory"; example `"invocationNum": 3, "initialNumSteps": 10`), §Supported events (`Stop`: "Fires when execution terminates"), §PreInvocation output (`systemMessage` "out-of-band system instruction" vs `ephemeralMessage` "A transient system message"); research-antigravity.md §6 "Places where the official pages disagree" #4; v3-d3.md:368, :690, :1207–1209; v3-d1.md:123.

### R3-HA-02  —  major
- **Artifact:** D3, D2 (follow-up to R2-HA-02, accepted as G12)
- **Location:** D3 step 6.2: `disallowedTools: Bash, PowerShell, Edit, Monitor, WebFetch, WebSearch, Skill, SendMessage, Agent, CronCreate`, "With these removed, the helper has no tool on today's list that runs a command." D2 §9, same claim.
- **What is wrong:** The claim is false for a helper running in the foreground. Claude Code removes only a short list from every subagent (`Workflow`, `ScheduleWakeup`, and a few others). The fixed background allowlist applies only to background subagents. In `claude -p` and the Agent SDK, Claude "can wait", which runs the helper in the foreground. A foreground helper keeps `RemoteTrigger`, which "creates, updates, runs, and lists cloud scheduled tasks" and needs no permission. A cloud task runs shell commands with the user's repository and connectors. The helper also keeps `PushNotification`, `SendUserFile`, and `CronDelete`. In both modes it keeps `Artifact` (publishes a page to claude.ai), `EnterWorktree`, and `TaskStop`. The frontmatter never sets `background: true`, which is the native way to pin the short background allowlist. `check --plugin` checks only the ten listed names, so a new tool gets past it.
- **What breaks if we ship it as-is:** A poisoned tracker ticket can tell the one helper that reads outside text to create a recurring cloud task. That task then runs commands under the user's account long after the session ends. D2 calls this control "structural". In a scheduled or `-p` run, which is where Update runs unattended, the control is not there.
- **Suggested fix:** Add `background: true` to `core-refresh.md`. Then only the fixed background list is left, MCP tools are kept, and a new built-in tool cannot get in. Also deny `RemoteTrigger`, `Artifact`, `EnterWorktree`, `ExitWorktree`, `TaskStop`, `NotebookEdit`, `PushNotification`, and `SendUserFile`. Make `helper-tools` assert `background: true`.
- **Evidence:** https://code.claude.com/docs/en/sub-agents.md:429–440 (first filter list; background "keeps every MCP tool but only these built-in tools"), :310 (`background` "keep this subagent in the background even when Claude asks to wait"), :922–924 ("`claude -p` and the Agent SDK: Claude can wait"); https://code.claude.com/docs/en/tools-reference.md:45 (`RemoteTrigger` row, permission "No"); v3-d3.md:928–936; v3-d2.md:367.

### R3-HA-03  —  major
- **Artifact:** D3, D2
- **Location:** D3 step 6.2 `sources.md`: "on Codex and Antigravity start a general helper with the text of `refresh.md` as its task". D3 6.2: "`claude/agents/core-refresh.md` (outside `agents/` so Antigravity does not load it)". D2 §9 lists the denylist as the injection control with no harness limit.

### R3-HA-04  —  major
- **Artifact:** D2, D3 (follow-up to R1-HA-13 and R2-PA-05, accepted as G27)
- **Location:** D3 contract K `copy-skills` ("copy `skills/` into `<project>/.agents/skills/`"); 4.3 §11(b), offered to Codex users; 8.3 runs `copy-skills` *before* starting `codex`. ### R3-HA-05  —  major
- **Artifact:** D2, D3, D1 (follow-up to R2-HA-11 / G13 and R2-PA-05 / G27)
- **Location:** D2 §2 Thursday: "A Claude Code cloud scheduled task … runs `/core:pulse unattended`". In `schedule.md` and setup, offer to enable the five skills on the claude.ai account for cloud tasks, and to add CORE under Project settings > Plugins for Projects. Note the cost: account skills also sync to terminal sessions, so they are listed beside the plugin's. Correct the Projects row and the 4.3 §11(b) wording.

### R3-HA-06  —  major

### R3-HA-07  —  major
- **Artifact:** D3, D2 (follow-up to R2-HA-03, accepted as G10)
- **Location:** D3 3.6: "inserts it … of `AGENTS.md` (creating it), and of `CLAUDE.md` too when one exists". D2 §1 "Where the block goes". D3 rule 4: "Never write generated text into a file a person edits."

On Antigravity there is a native carrier that exists only when the plugin is installed: a plugin's `rules/AGENTS.md` is "loaded automatically as an always-on rule whenever the plugin is enabled".
- **What breaks if we ship it as-is:** Teammates who never installed CORE are told at every session start that "CORE's hooks are not running here". They learn to ignore CORE's lines, which undoes the liveness signal for the owner.
- **Suggested fix:** On Antigravity, ship the fourth line in the plugin's `rules/AGENTS.md` and keep it out of the project file. Elsewhere, put it in a per-machine, uncommitted file (`CLAUDE.local.md` on Claude Code), or reword it to "if you have CORE installed".
