## Part 1 — The case against this plan

### 1. This is a second system

CORE 3 has 176 test files. Each one exists because something broke: a Windows path, a cloud-synced folder, a symlink, a second process writing at the same moment. The plan keeps the fixtures and three helper files and deletes the rest. A 1,800-line rewrite will meet the same edge cases again, one bug report at a time. The size budget can be met honestly, or it can be met by not handling them.

*The plan's answer:* most of those tests guard machinery the rewrite removes — stamps, locks, ledgers, migration. *Why that is not enough:* nobody has gone through the 176 files to sort "guards removed machinery" from "guards something the rewrite still does". Until someone does, the claim is a hope.

### 2. The central bet is untested, and the plan builds everything before testing it

The bet is that hooks and skills beat plain files alone. A capable model with file search may find `_memories/` unprompted. If so, the plugin is decoration. D1 says this out loud and makes it the release gate. But the gate sits at the end of nine phases. The plain-files baseline could be measured in a day, before anything is built, and v1 of the build plan does not do that.

### 3. Remembering still depends on the model choosing to remember

CORE 3's own files say in-flow writes get suppressed "consistently". CORE 4 answers with a shorter skill, a close pass, and a catch-up for unclosed sessions. None of those notices a decision when it happens. The plan measures the miss rate. It does not reduce it by any mechanism CORE 3 lacked, except that the skill is short enough to be read.

### 4. Recall gets weaker before it gets better

CORE 3 matches against memory bodies, follows one link, and has a fallback for vague questions. CORE 4 matches a prompt against one-line summaries the agent wrote. A question phrased differently from the summary gets nothing. The release gate lets v4 score up to 0.1 below v3. That is a plan to ship a known regression in the one job CORE 3 actually enforces.

### 5. "Interact" is delivered on one harness out of three

The brief asks for a loop. On Codex and Antigravity the plan offers "it rides along with your next prompt". That is not a loop; it is a reminder that waits for you. Antigravity has `/schedule` and sidecars. Codex has `/goal` and a sleep tool. The plan declines all four.

### 6. The security gate is one yes

A project is trusted after the user agrees once. The research the plan cites says people approve about 93% of prompts. After that yes, attacker-written summaries ride into every prompt, 160 characters at a time. A 160-character limit does not stop a short instruction. "Information, not instructions" is a sentence, not a control.

### 7. The measurement leans on one vendor's new tool

`claude plugin eval` has an early-access note in its own troubleshooting page. It exists on one harness of three. The four-cell design doubles the cost. Twenty cases at three runs each is a small sample for a judge that is known to be noisy. The +0.3 bar is a guess. On Codex and Antigravity, where most of the ladder lives, "does it help" stays unmeasured forever.

### 8. The budget is a number chosen before the design

Fifteen commands, three hook dialects, a watcher, a self-test, a migration, a blind-pack tool: 1,800 lines is tight. A tight budget invites dropped error handling, which is the defect class this rewrite exists to end.

### 9. It removes things the owner uses

The swarm review. The HTML memory view. Date-based queries. Generated `[[wikilinks]]`, which make the store browsable as a graph in Obsidian. The seams that let another plugin wrap CORE. The plan lists these as "removed" in one table row. For the person who uses them, each is a loss with no replacement named.

### 10. Receipts live where they vanish

Receipts sit in a git-ignored folder inside the project. A fresh clone has none. A cloud session has none. So "in how many sessions did the hooks run" is computed only for sessions on machines that kept their folder. The number will look better than the truth, because the sessions with no receipts are exactly the ones where something did not run.

### 11. The honesty contract has a hole

A command that read nothing may still answer `ok` if it sets `empty: true`. That flag is set by the same code that did the reading. A bug that returns an empty list will also set the flag. The self-test catches this only for the cases someone thought to plant.

### 12. Two agents, one folder, no locks

The plan says "last one wins" and moves on. The research it cites found that several agents writing one page lost 16 of 57 facts.

## Part 2 — What a professional would ask

| # | Question | The plan's answer today |
|---|---|---|
| 1 | **What is your write policy?** What triggers a write, and who decides? | The agent decides, guided by one test: would this change what you say or build in six weeks? Decisions, risks, commitments, open questions, people. Never secrets, never raw outside text. Research supports agent-chosen writes over per-turn extraction [literature §3]. |
| 2 | **How do you stop duplicates?** | Before writing, the agent searches the index and the archive. Same fact: update. Changed fact: new file, old one archived with a link. `check` flags duplicate ids. Near-duplicates with different ids are **not** detected by any script. |
| 3 | **What is your decay rule?** | None by formula. Memories untouched for 90 days, not pinned, with nothing due, and not named in the brief are archived by the `pulse` skill, with a count. The 90 is chosen, not measured. |
| 4 | **How do you handle a fact that changed?** | Replace and archive. One live version per fact. This follows the research finding that stale and fresh values side by side cause confidently wrong actions [literature §4]. |
| 5 | **What are your retrieval precision and recall?** | **No answer yet.** The plan sets thresholds against CORE 3's gold sets, which hold very few queries — one of them holds a single query [evaluation §6D]. Real numbers come from the first eval run. |
| 6 | **What is the context budget?** | About 400 tokens always on; up to 6,000 bytes of brief at start; up to 1,000 bytes per prompt, and only on a match. CORE 3: about 32,000 tokens at start. |
| 7 | **What does a cold start cost?** | A new project has no memories. CORE costs its 400 tokens and says nothing until there is something to say. Enabling a project is one sentence. |
| 8 | **What is the token cost per session?** | Estimated at 2,000–3,000 tokens for a session with a full brief and a few recalls. **Not measured.** `claude plugin details` measures the always-on part only. |
| 9 | **What happens at 10,000 sessions?** | The archive holds tens of thousands of small files and is never read by default. The active set is held near 300 by archiving. The index is rebuilt by hashing every active file at session start; at 300 files that is fast, at 3,000 it is not. **Not tested at scale.** |
| 10 | **How do you know it helps?** | The four-cell test in D2 §7: with and without the plugin, with and without the record. Claude Code only. |
| 11 | **What would make you kill it?** | The plugin fails to beat plain files alone. Stated in D1 §8. |
| 12 | **What is your no-memory baseline?** | Cell C in D2 §7: no plugin and no record. |
| 13 | **How do you keep the judge honest?** | Planted-fact text checks first. Judge sees the final answer only. Blind pack judged twice with order flipped. **Not done:** checking the judge against human labels. |
| 14 | **How do you handle poisoned memory?** | Nothing runs until the project is enabled. Hooks pass pointers, not bodies. Source of each memory is recorded. Unattended runs cannot write memories. See Part 1, item 6 for why this is thin. |
| 15 | **What does an unattended run do?** | Reads, refreshes sources, writes proposals to an inbox. Never writes memories or the brief. |
| 16 | **What is your concurrency story?** | One fact per file; atomic writes; no locks. Last writer wins. See Part 1, item 12. |
| 17 | **How do you roll back?** | The old version stays at tag `v3.20.1`. Migration refuses to run on uncommitted files, so `git checkout` undoes it. **Not covered:** a project that is not in git. |
| 18 | **What do you log, and what is in it?** | One line per hook or check: time, event, session id, status, counts, memory ids. Never prompt text or memory text. |
| 19 | **How do I debug a missed recall?** | `core.mjs recall --prompt "…"` shows what matched and why. `core.mjs metrics` shows whether the hook ran. |
| 20 | **What breaks when the harness changes?** | The hook file for that harness. CORE drops to skills-only and says so. Antigravity's hook format changed three times in three weeks [antigravity, summary 15]. |
| 21 | **Who is the second maintainer?** | Nobody. |
| 22 | **Why not embeddings?** | No evidence yet that this store needs them, and they bring an index that goes stale. Revisit on a measured miss. |
| 23 | **How is "focus" measured?** | Eval cases plant a due item among distractors and check that the brief names the first and not the second. Whether the user *felt* less loaded is **not measured**. |
| 24 | **Does the brief itself help?** | Unknown. One controlled study found always-loaded context files raised cost about 20% with no reliable gain in task success [literature §1]. The four-cell test is what will tell. |

## Alternatives considered and rejected

- **One reviewer instead of seven.** Rejected. One reader anchors on the first problem found. Seven with different mandates do not share blind spots.
- **Letting the drafting agent review its own draft.** Rejected where separate agents exist. An author grades its own reasoning as sound. If no separate agents were available, this log would say so on every finding.
- **Applying every finding.** Rejected. A plan that obeys every critic hedges every sentence. A finding that is answered in writing stays answered.
