# D1 — The Case

**Why rewrite CORE, what to build instead, and whether it should exist at all.**

Draft v1 · 2026-11-09 · Companion documents: [D2 — The Machine](v1-d2.md) · [D3 — The Build](v1-d3.md) · [D4 — The Critic Log](v1-d4.md) · Evidence: [grounding.md](grounding.md)

Tags like `[G 3.4]` point to a section of `grounding.md`. Tags like `[runtime §4]` point to a section of the matching research file in this folder. Every claim rests on a file, a command, or a page opened on 2026-11-09.

---

## The short version

Coding agents forget. Each session starts cold. The decision you made on Tuesday is gone by Thursday.

CORE is a plugin that fixes this. It keeps a project's decisions, risks, people, and open work in plain files, brings them back when they matter, and tells you what needs you.

CORE 3 works, but it has grown to 100 scripts and 600 KB of instructions, and its own health checks can say "fine" while looking at nothing. Meanwhile the agent programs it runs in have learned to do most of what CORE built by hand.

**The proposal:** rebuild CORE at about one-twentieth the size. Keep the plain files. Keep the judgment about what to write down and when to speak up. Hand everything else to features the agent programs already have. Make "I could not measure this" a first-class answer.

**The verdict:** CORE earns a place only as that thin layer, and only if it passes its own test. If the plugin does not beat the plain files alone in a blind comparison, drop the plugin and keep the files.

---

## 1. The problem

There are two problems. The second was caused by solving the first.

### Problem one: agents forget the project

A coding agent is good at the file in front of it and lost on the project around it. Between sessions it loses:

- **Decisions and their reasons.** It re-proposes the option you already rejected.
- **Risks and their status.** Nobody remembers that the vendor deadline moved.
- **People.** Who owns what, who promised what.
- **Things owed.** The reply due Friday. The question you have put off twice.

It also only reacts. It does not say "the legal reply is due today" unless you ask.

A few terms used below. A *harness* is the agent program: Claude Code, OpenAI Codex, or Google Antigravity. A *hook* is a command the harness runs at a fixed moment, such as when a session starts. A *skill* is a short instruction file the harness loads when needed. *MCP* is the standard way an agent calls an outside tool, such as an issue tracker.

### Problem two: the fix got too big to trust

CORE 3.20.1 is the current answer. Measured on its own repository:

| | CORE 3.20.1 | Proof |
|---|---|---|
| Scripts | 100 files, 34,313 lines | [G 2.1] |
| Instructions | 40 files, 607 KB | [G 2.1] |
| Read before your first task | 127 KB, about 32,000 tokens | [G 2.2] |
| Steps in one ordinary session | 58, of which 49 are at startup | [runtime §1.5] |
| Settings switches | 34 names | [runtime §8] |
| Releases | 46 in five months | [G 2.1] |

Where do the 34,000 lines go? About 34% measure CORE itself. About 18% guard CORE's own state files. About 7% is the part that actually recalls a memory [runtime §8].

And the measuring does not hold. Five defects were reported against this version. All five were checked against the source; four were reproduced by running the shipped scripts [G 3.1–3.5]:

1. **Scripts look in the wrong folder and report clean.** Five scripts build a path under `~/.claude` by hand. On a machine that keeps its config elsewhere they read nothing. One prints "0 candidates of 0 entries" and exits successfully.
2. **A startup check says memory is "not yet" loaded while it is loaded.** It infers a fact about the session from a path it worked out, instead of looking at the session.
3. **A close marker says "closed" over an empty ledger.** One file holds both a status word and a list of steps. A command writes the word without reading the list.
4. **A reader prints nothing and exits successfully**, whatever it is given.
5. **CORE's own startup upkeep trips its own change detector.** Startup rewrites a generated block inside memory files. The close check hashes those files, sees a change, and reports a render as owed.

These are one defect in five costumes: **a check that reports success while doing nothing.** A separate audit of the measurement code found seventeen more places where it happens [evaluation §6A]. CORE's own documents already name the pattern — "Instruments report healthy while recording nothing" — and list its fix as "add as found" [G 2.7]. Adding guards one at a time is how the code reached 34,000 lines.

Meanwhile, of the five jobs CORE is meant to do, only one is enforced by code today [runtime §4]:

| Job | In CORE 3 |
|---|---|
| Remember | Instructions only. In a test, a session where the user said "Remember that" stored nothing. |
| Recall | Real. A hook brings matching memory titles with every prompt. |
| Interact | No loop. Nothing runs between your messages. |
| Update | A registration form with nothing behind it. |
| Focus | Byte limits are real. The rest is instructions. |

So the largest parts of CORE 3 serve measuring and state-guarding, and the jobs that matter most have no code at all.

## 2. Why solve it

Because the work is long and spread out. Projects run for months. The same person works in three harnesses, on three operating systems, on a laptop and in cloud sessions. A forgotten decision costs an afternoon. A forgotten deadline costs more.

And because the first problem is real and still unsolved by anything else as a whole. Section 6 shows this row by row.

## 3. What happens if we don't

**If CORE 3 stays as it is:**

- Every session pays about 32,000 tokens before work starts.
- Health reports keep being wrong in ways that are hard to see. A tool that says "nothing needs your attention" when its recorder is dead [evaluation §6A] trains you to stop reading it.
- CORE's notes on the other harnesses are already out of date. Its install guide says Codex "has no session-start or session-end event". Codex's source at version 0.167.0 has fourteen hook events, including both [codex §4]. Antigravity is not supported at all [G 2.4].
- Each fix adds a guard, and each guard needs a guard. Forty-six releases in five months is the measure of that.

**If CORE is simply dropped:**

- Memory falls back to each harness's built-in. Claude Code's is on by default but stays on one machine and one harness. Codex's is off by default. Antigravity's documentation says "Agents don't remember conversations" [G 4.1] [codex §2] [antigravity §5].
- Nothing tracks risks, people, or things owed. Nothing speaks up. Nothing closes a session into the project.

## 4. The solution

### The premise

**Keep the judgment. Drop the machinery.**

CORE 3 has learned real things: what is worth writing down, how to record a decision so the rejected option is not proposed again, how to tell "owed" from "attempted" from "proven", how to keep a removed fact from coming back. That is judgment. It fits in a few pages.

Around it, CORE 3 built a retrieval engine, a ranking formula, a state-guarding system, and a measurement suite. That is machinery. In 2026 the harnesses supply most of it.

### What CORE 4 is

Three layers [D2 has the detail]:

1. **The record.** Plain markdown files in the project. One file per fact, a short brief on top. Readable, editable, committed with the code.
2. **The habits.** Five short skills: when to write, how to find, when to speak, what to refresh, how little to say.
3. **The wiring.** Three hooks and one background watcher, driving one small script with no dependencies.

And one rule: every check answers **working**, **broken**, or **not measured**. The third is never dressed as the first.

### What the harness does, and what CORE adds

| Job | The harness already provides | CORE adds |
|---|---|---|
| Remember | File tools. Skills. The session transcript. | The test for what is worth keeping. The file format. Replace, don't overwrite. A retired fact stays retired. |
| Recall | Hooks that add context at session start and with each prompt, on all three harnesses. File search. | A one-line-per-memory index. A matcher that returns three pointers or nothing. |
| Interact | Background monitors and schedulers (Claude Code). A prompt hook (all three). | The rules for what needs you. A watcher. "Speak at a pause, once." |
| Update | MCP. Helper agents. | One file per outside source with a freshness limit. A fixed digest. "Outside text is data." |
| Focus | — | Hard limits on every surface. No repeats. Snooze on "not now". |
| Measure | A plugin test runner that compares with and without the plugin (Claude Code). A token-cost readout. A validator. | The test cases. Three exit codes. A known-answer self-test. |

Every "already provides" cell was read from the vendor's own documentation or source this session [G 4.1] [codex] [antigravity].

### The size

| | CORE 3 | CORE 4 target |
|---|---|---|
| Script lines | 34,313 | 1,800 at most |
| Instruction bytes | 607 KB | 60 KB at most |
| Read at session start | about 32,000 tokens | about 2,000 (the brief and one block) |
| Skills | 8 | 5 |
| Settings switches | 34 | 1 |

## 5. Why this solution and not another

**Because the evidence points at plain files.** Letta, the team behind MemGPT, moved its memory from database tools to "a git-tracked collection of Markdown files that the agent searches with normal file-search and read tools", with no vector index by default [memory-layers-a §2.2]. Anthropic's guidance for agent builders is to start with the agent's own search and add meaning-based search only if needed [literature §2]. On a newer memory benchmark, files searched by a coding agent scored 72.5% against 48.5% for the best retrieval pipeline [literature §2]. Anthropic's own productivity plugin stores memory as a short always-loaded file plus a folder of markdown, with no scripts at all [G 4.4].

**Because small injected context beats large.** Model accuracy falls as input grows, well before the limit; a few hundred relevant tokens beat a full history in every model tested [literature §1]. So CORE 4 passes three pointers, not three documents.

**Because the defect class is structural.** Each of the six ways a CORE 3 check lies [G 3.6] has a rule in CORE 4 that removes the cause, not the symptom. For example: CORE 3 needs a hash cache, stamps, and a classifier to tell its own writes from yours, because it writes generated text inside your files. CORE 4 never does that, so there is nothing to tell apart. D2 §6 lists all six.

**Because the harnesses now carry the load.** Hooks that add context at session start and per prompt exist on all three. All three read `AGENTS.md` and load the same skill format [competitors §6.4]. Claude Code will run a plugin's test cases with and without the plugin and report the difference [G 4.1] — the comparison CORE 3's own changelog says "exists nowhere in this codebase" and later dropped as unobservable [evaluation §2.8].

## 6. Who else does this, and how CORE compares

Twenty-eight tools and the three harnesses' built-ins were checked [competitors] [memory-layers-a] [memory-layers-b]. The closest ones:

| | Remember | Recall | Interact | Update | Focus | All three harnesses | Readable files in the project | No server, key, or database | Measures itself |
|---|---|---|---|---|---|---|---|---|---|
| **Harness built-ins alone** | Partial: Claude Code yes, on one machine; Codex off by default; Antigravity none | Partial | Partial: schedulers exist, nothing uses them for the project | Partial: MCP exists, nothing prebuilt | Partial | No: each is its own | Partial | Yes | Claude Code only |
| **claude-mem** (115k stars) | Yes: a second agent notes every tool call | Yes | Partial | No | Partial | Yes | No: SQLite in the home folder | No: background server, a model call per tool use | No |
| **basic-memory** | Yes: markdown notes | Yes: search over MCP | No | No | No | Partial: Antigravity by MCP only | Yes | Partial: Python and a local index | No |
| **mem0** | Yes: extracted facts | Thin: one search on the first prompt | No | No | No | Yes | No: cloud | No: cloud key | Vendor benchmarks only |
| **Letta Code** | Yes: markdown in git | Yes | Partial | No | No | No: it *is* a harness | Yes, but outside the project | Yes | No |
| **Zep / Graphiti** | Yes: dated facts in a graph | Agent must ask | No | No | No | No | No | No | Vendor benchmarks only |
| **Anthropic `productivity` plugin** | Yes: tasks, people, terms | Partial | No: acts on `/update` | Yes: MCP trackers, mail, chat | Partial | No: Claude only | Yes | Yes | No |
| **Task trackers** (Beads, Backlog.md) | Work items only | Partial | No | Partial | Partial | Partial | Backlog.md yes; Beads no | Yes | No |
| **Standalone proactive agents** (OpenClaw, Hermes, Linear's agent) | Yes | Yes | **Yes** | Yes | Partial | No: they run outside the coding session | No | No | No |
| **CORE 3.20.1** | Instructions only | Yes | No loop | Form only | Partial | Two of three | Yes | Yes, needs Node | Yes, but see section 1 |
| **CORE 4 (planned, not built)** | Yes | Yes | Yes on Claude Code; next-prompt elsewhere | Yes | Yes | Yes, with stated losses | Yes | Yes, needs Node | Yes |

Three things stand out.

1. **No row is "yes" across the five jobs and also keeps readable state in the project.** Every tool that truly acts unprompted runs somewhere else and keeps its state somewhere else [competitors §A].
2. **Nothing tracks risks or people as project records.** Memory tools remember what the agent did. Trackers remember work items [competitors §B].
3. **Almost nothing measures whether it helps.** No independent, blind result was found showing any of these memories improves coding outcomes [memory-layers-b, summary 14]. The vendor benchmarks conflict: one system's score on the same test is reported as 84%, 75%, and 58% by different parties, and the test's own answer key is 6.4% wrong [memory-layers-a §1.11].

The tools with servers also had a hard year: published high or critical security advisories against basic-memory, Serena, and cognee, and a claude-mem release line that uploaded 30 days of prompts without asking [memory-layers-b, summary 4]. And the "reports success while doing nothing" defect is common in the field, not special to CORE: one assistant ran five silent months; another shipped hooks that never fired [competitors, finding 3].

### What a sensible person would use instead of CORE

Not one tool. A kit: `AGENTS.md` for standing rules, the harness's built-in memory left on, Backlog.md for work items, vendor MCP connectors, and one scheduled morning check [competitors §C].

They would gain near-zero upkeep. They would lose: risks and people as records, anything that speaks up during a session, a session close written into the project, one behavior across three harnesses, and any evidence that it helps.

## 7. Dependencies, tradeoffs, risks

**Depends on.** Node.js 20 or newer on the PATH. A harness that loads skills and runs hooks. Claude Code 2.1.269 or newer for the with-and-without test. One MCP server per outside source.

**Trades away.** The multi-agent "swarm" review, the HTML memory viewer, date-based "what did we know then" queries, and CORE 3's four-tier retrieval. Recall becomes word matching over one-line summaries; a question that shares no words with the summary gets no pointer. Between-prompt reminders exist only on Claude Code.

**Risks.**

| Risk | How likely | What limits the damage |
|---|---|---|
| A harness changes its hook format. Antigravity's changed three times in three weeks [antigravity, summary 15]. | High | Hooks are an optional layer. Without them CORE drops a rung and says so. Each harness has its own small hook file. |
| The rewrite throws away lessons buried in CORE 3's 176 test files. | Medium | The fixture stores, the gold sets, and the prose checker are kept and reused. The audit's list of 29 practices worth keeping [evaluation §8] is the checklist. |
| The agent does not follow the habits. CORE's own note says instructions-only duties run "about 40% of the time" — a figure with no source in the repository [G 2.7]. | Medium | Hooks cover the two moments that most need a guarantee. The eval measures how often a planted decision gets written. The number is published, whatever it is. |
| The plugin adds nothing over the plain files. | Unknown — this is the point of the test | The release gate in D3. If it fails, the verdict below changes. |
| A harness vendor ships the missing half. Claude Code's cloud "Projects" already has project memory and a "Waiting on you" list, in beta, for one user, not in the terminal [competitors §6.1]. | Medium, rising | CORE 4 is small enough to retire. The files stay useful with or without it. |
| A poisoned memory steers the agent. | Low to medium | D2 §9: nothing runs until you enable a project; hooks pass pointers, not bodies; unattended runs cannot write memories. |
| One maintainer. | Certain | 1,800 lines is something one person can hold in their head. 34,000 is not. |

## 8. The verdict

**Does CORE deserve a place in the market?** As a product for other people: **no.** claude-mem has 115,000 stars and a paid tier. The harness vendors ship memory by default and improve it monthly. A solo-maintained plugin will not win that contest and should not try.

**Does something else replace CORE for our use?** **No, not today.** Our use is one person, three harnesses, three operating systems, projects that run for months, and a need to be told what is due. Nothing checked covers that. The nearest fallback is basic-memory for storage plus our own skills on top, and it would bring Python, a local index, and an AGPL licence while still leaving the hard half to us [memory-layers-b, verdict].

**So: keep CORE, cut it to a twentieth of its size, and make it prove itself.** The proof is one number. Claude Code's test runner gives the plain-files-alone score and the files-plus-plugin score on the same tasks [D2 §7]. If the plugin does not clearly beat the files alone on recall, focus, and speaking up, then the plugin is decoration. In that case ship the file layout and a two-page `AGENTS.md` pattern, and stop maintaining code.

Re-run that test at every release and re-read this verdict every six months. The vendors are moving toward this ground. The day a harness's built-in does the five jobs across the other two, CORE's work is done and the files remain.

## Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| **Fix CORE 3 in place.** | The defects come from its shape: computed paths, generated text inside watched files, two records per state [G 3.6]. Five months of point fixes produced 46 releases and the current size. |
| **Use the harness built-ins only.** | They do not travel across harnesses or machines, they do not track risks or people, and nothing in them speaks up [G 4.1] [codex §2] [antigravity §5]. This is the baseline CORE 4 must beat in its own test. |
| **Adopt claude-mem.** | It records what the agent did, not what the project decided. It runs a background server and a model call per tool use, and stores a database in the home folder [memory-layers-b §1]. |
| **Adopt basic-memory as the store.** | The best fallback. Rejected for now because it adds Python, a local index and an AGPL core, reaches Antigravity only through MCP, and still needs all of CORE's behaviors on top [memory-layers-b §2, verdict]. Both use plain markdown, so the way there stays open. |
| **Adopt mem0, Zep, or Graphiti.** | Each needs a cloud account or a database. None is readable in the project. None does project management [memory-layers-a, verdict]. |
| **Switch to Letta Code.** | It replaces the harness instead of extending it [memory-layers-a §2.7]. |
| **Build CORE as an MCP memory server.** | A server process to install and secure on three operating systems, in a year when memory servers drew repeated security advisories. File tools already exist in every harness. |
| **The pragmatic kit** (AGENTS.md, built-in memory, Backlog.md, connectors, one scheduled check). | The honest runner-up. It loses the five things listed in section 6. If CORE 4 fails its test, this is what to use. |

## What I did not verify

- **The workspace that saw the defects.** This run had the source repository only. There was no installed plugin copy, no project `PROJECT.md`, and no memory store [G 1.1–1.3]. The defects were confirmed from source; the incident where a background pass claimed five writes and made none could not be re-run [G 3.5].
- **Anything on a live Codex or Antigravity install.** Their capabilities were read from source code and documentation, not run.
- **That CORE 4 will pass its own test.** Nothing is built. Every CORE 4 cell in the table above is a plan.
- **The size targets.** 1,800 lines and 60 KB are budgets set by estimate.
- **Star counts and some release dates for competitors.** Several came through a tool that summarizes GitHub pages; the research files mark which.
- **The "40% of the time" figure.** It is CORE's own, and no measurement behind it was found.
