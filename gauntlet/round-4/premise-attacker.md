# Round 4 — Premise attacker

Reviewing v4 of D1–D4. Mandate: argue that CORE should not exist, and test whether the verdict is defensible. I read rounds 1–3 (reviewer files, not `defence.md`) and the D4 Part 3 ledger, with fix codes H1–H18. Nothing below repeats an earlier finding. Where an earlier fix is broken or incomplete, the finding cites the earlier ID.

## The case against, in one paragraph

v4 can now kill CORE. That is real progress. But the kill test still does not test the reason CORE is said to exist. Its two halves point in opposite directions. Half (a) scores recall of the very four kinds of fact that the shared three-line block already names, so it is decided by how close the kit sits to the ceiling. Half (b), "being told what is due", runs against a kit whose block has no due rule, so the kit cannot win it. The hooks' gate has the same flaw one level down: one `Grep` for "v2" answers the prompt hook's only "ahead" case. Around the test, the plan's cut is wrong in three places. The script is exempt from every test. The script's metrics and `env` read hook receipts that a hookless release never writes. The "enabled" gate guards the hook channel, which passes pointers, and leaves Layer 1, which reads full bodies, open in every clone. Then the verdict says "for the owner's own use, not as a product" while the build updates every installed copy in place. The strongest native rival, auto memory written into the repository, is still never named. My verdict: the case for CORE 4 as specified does not hold yet. The case for plain files in the project still does.

### R4-PA-03  —  major
- **Artifact:** D1 / D3
- **Location:** D3 0.6 GATE.md kill rule (a), "a mean paired gap of at least 1 probe of 5 … and no more stale or duplicate copies"; D3 2.1 `script.json`, "five probes, one per planted fact"; D1 §5 table row "Recall | Session-start and prompt-time hooks on all three; file search".
- **What is wrong:** Half (a) of the kill test scores only recall, the one job D1 says the harnesses already do. The five probes ask for a decision, its reversal, a risk, a person, and a promise. The kit's block tells the agent to write exactly "a decision, risk, commitment, or person", and to look in `_memories/` before answering. Auto memory is on in both arms. So the probes test the block that both arms share. What the skills add, by D1's own list, is the replace rule, closing, a written handoff, and speaking up. Those earn no credit toward the margin. Stale and duplicate copies appear only as a veto against layer 1, never as a point in its favour. And unlike the hooks (`early_stop`), no step measures the kit's probe score before the 1-probe margin is frozen. If the kit averages above 4 of 5, the rule cannot be met by any Layer 1.
- **What breaks if we ship it as-is:** The existence verdict is decided by whether the kit hits the recall ceiling. A "not kept" then tells you nothing about the jobs CORE claims to add. A "kept" credits the skills for a gain the block may supply. Either way D1 §8's "each part ships only if it beats the thing below it" is ruled on the wrong job.
- **Suggested fix:** Score the record test per job: recall probes; the reversal (old form archived, not just recalled correctly); handoff written; due item raised unasked. Freeze one margin per job. Run the kit arm once before freezing and record its ceiling.
- **Evidence:** v4-d3.md:579, 887 (planted facts), 649 (block's write line); v4-d1.md:130, 225; v4-d3.md 0.6 JSON `early_stop` (hooks only).

### R4-PA-04  —  major
- **Artifact:** D1 / D3
- **Location:** D1 §8 kill test 1, "Otherwise CORE does not ship; use the kit."; D1 §6 row "**The kit:** built-in memory + the three-line block + Backlog.md + connectors + one scheduled task"; D3 2.3 stop text.
- **What is wrong:** Both outcomes of the kill test are relative. Nothing asks whether the winner is good enough to use. Layer 1 can ship at 2 of 5 probes against a kit at 1 of 5 if the interval clears zero. The kit can be recommended at 1 of 5. Worse, the kit the verdict recommends is not the kit that was tested. D1 §6 defines it as built-in memory, the block, Backlog.md, connectors, and a scheduled task. The tested kit is the block in `.claude/rules/core.md`. Backlog.md and the scheduled task are never run.

- **Suggested fix:** Add an absolute floor to GATE.md: layer 1 is kept only if it also reaches at least 4 of 5 probes on average. Reword the fallback to name exactly what was tested ("the three-line block in a rules file"), and list the untested kit parts as untested.
- **Evidence:** v4-d1.md:169, 225; v4-d3.md:579, 891, 915.

### R4-PA-05  —  major
- **Artifact:** D1 / D3

### R4-PA-07  —  major
- **Artifact:** D3 / D2
- **Location:** D3 9.4, "If the session-start hook is shelved, the prompt hook, `PreCompact`, and the liveness line … go too: with no status block, that line would cry wolf."; D3 1.2 `core` §2, "No status block → read `reference/ladder.md` and `PROJECT.md`, say in one sentence what is not working"; D3 8.1 `env`; D3 6.4 `metrics`.

### R4-PA-08  —  major
- **Artifact:** D1 / D2 / D3
- **Location:** D1 §4, "Hooks run only in *enabled* projects … So a planted memory in a cloned repository cannot reach the agent through a hook."; D1 §7 risk row, "A planted memory steers the agent | Low to medium | Hooks act only in enabled projects and pass pointers, not bodies"; D3 "Why each thing exists", "`enable` | … Harnesses trust folders but do not tell a plugin."
- **What is wrong:** The enabled gate guards the weaker channel and leaves the stronger one open. Hooks pass pointers: an id and a 160-character summary. Layer 1 is not gated. In any clone with `_memories/`, the committed `.claude/rules/core.md` tells the agent to "look in _memories/", and the `core` skill fires on "a project with a PROJECT.md or a _memories folder". Both lead the agent to read full memory bodies, enabled or not. So a planted memory reaches the agent anyway, through the path the security design does not count. Meanwhile, the harnesses already gate repository content behind their own trust: Claude Code holds settings hooks until the trust dialog, Antigravity checks workspace trust before loading repository skills and hooks, and Codex skips project `AGENTS.md` in an untrusted project.
- **What breaks if we ship it as-is:** The owner pays for the gate: one consent per machine (D4 Part 1 item 9), a print-a-command step on Codex, eval mode, the temp-folder condition, canaries, and `enabled-check` graders. In return the D1 risk row rates planted memory "low to medium" on a control that does not cover the main path. Requirement 6 ("how it treats untrusted content") is met only for hooks.
- **Suggested fix:** Either gate the skills too ("in a project not enabled here, read no `_memories/` body without asking"), or drop the enabled list and rely on the harness's trust, and rewrite the D1 risk row to say that Layer 1 reads bodies in any trusted folder.
- **Evidence:** v4-d1.md:118, 205; v4-d3.md:680 (`core` description), 154, 649; v4-d2.md:367 ("Write: skills | Any project"); research-claude-code.md:266 ("Claude Code holds back hooks from every settings file … until you accept the workspace trust dialog"); research-antigravity.md:931 ("interactive Workspace Trust verification before loading repository-local skills, hooks"); research-codex.md:77 ("If the project is marked untrusted, project files are skipped").
