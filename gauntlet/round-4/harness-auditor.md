### R4-HA-01  —  critical
- **Artifact:** D3, D2 (follow-up to R3-HA-07 and R3-HA-15, accepted as H12)
- **Location:** D3 1.1: "Claude Code appends it to `CLAUDE.local.md` (created if missing, added to `.git/info/exclude` unless Git ignores it)". D3 contract B: "`CLAUDE.local.md` per machine, uncommitted: the liveness line". D2 §1: "`CLAUDE.local.md` on Claude Code". Record test 2.1, full arm: "the liveness line in `CLAUDE.local.md`".
- **What is wrong:** H12 moved the block out of `AGENTS.md` because a `CLAUDE.local.md` stops Claude Code reading `AGENTS.md`. Then it puts the liveness line into a new `CLAUDE.local.md`. Creating that file switches off `AGENTS.md` for that user's Claude Code sessions. D1 §7 states the same fact as the reason for the rules file: "any `CLAUDE.md` or `CLAUDE.local.md` in or above the folder stops Claude Code reading `AGENTS.md`." The Claude Code docs warn about this exact case.
- **What breaks if we ship it as-is:** In a repo that uses only `AGENTS.md`, the common setup for a team that also uses Codex, the user says yes to one setup question. After that, Claude Code silently drops the team's project instructions: build commands, style rules, everything. Nothing in CORE reports it, and `agents_block: "added"` reads as success. The record test cannot catch it, because its temp project has no `AGENTS.md`.
- **Suggested fix:** Put the liveness line in its own rules file, `.claude/rules/core-liveness.md`, excluded through `git rev-parse --git-path info/exclude`. Rules files "don't count" toward the `AGENTS.md` switch. Never create `CLAUDE.local.md`.
- **Evidence:** https://code.claude.com/docs/en/memory.md:360 ("An `AGENTS.md` and a `CLAUDE.md` or `CLAUDE.local.md` … | Your `CLAUDE.md` files only"), :373–374 (`.claude/rules/` files "Don't count, and keep loading alongside `AGENTS.md`"), :385 ("Because `CLAUDE.local.md` counts, adding one to keep your own uncommitted instructions in a project that relies on `AGENTS.md` stops Claude from reading `AGENTS.md` for you"); v4-d3.md:261, :666, :891; v4-d2.md:86; v4-d1.md:195; v4-d3.md:1462 (D3's own rejected-alternatives line says the same).

### R4-HA-02  —  major
- **Artifact:** D3, D2 (follow-up to R3-HA-08 and R3-HA-11, accepted as H16)
- **Location:** D3 1.2: `allowed-tools: Bash(node ${CLAUDE_PLUGIN_ROOT}/scripts/core.mjs *)`. Contract K: "Finding the script. The status block's `script:` line … Run it as `node "<path>" <command>`." Contract F: "Every path prints with forward slashes, in double quotes." Record test 2.1 step 4: "No blanket `Bash(node *)`: on full, the skills' own `allowed-tools` admit the script, as for a user." 8.2 If it fails: "the `allowed-tools` rule did not match the quoted path … try the rule with the path quoted".
- **What is wrong:** Bash rules match the command text as a prefix. The rule expands to `node /…/core.mjs *`, with no quotes. The command the skills are told to run is `node "/…/core.mjs" queue`, with quotes. The docs' own pattern works only because the rule and the body use the same text. On Windows, `${CLAUDE_PLUGIN_ROOT}` expands with backslashes while the status block prints forward slashes, so even a quoted rule cannot match. Where Git Bash is missing, Claude Code uses the PowerShell tool, which a `Bash(…)` rule does not cover. D3 sees the risk, but only in 8.2, which runs after the hooks' gate (7.2).
- **What breaks if we ship it as-is:** In a `claude -p` run in Manual mode, a call that needs approval is denied. So in the record test's full arm (2.1 at 7.2), every `queue`, `close`, `env`, and `metrics` call is denied. The full arm quietly runs on the no-script path, and the hooks are kept or shelved on a crippled arm. The run is still marked as measured, because the hook receipts exist. Real users get a prompt on every script call, which is what R3-HA-08 described.
- **Suggested fix:** On Claude Code, make the skill body run `node "${CLAUDE_PLUGIN_ROOT}/scripts/core.mjs"`. Claude Code puts the same text in the body and the rule, so they match on every OS. Write the rule with the same quotes. Use the status-block path only on other harnesses. Make 2.1 mark a repetition "not measured" when the stream's `permission_denials` names `core.mjs`.
- **Evidence:** https://code.claude.com/docs/en/permissions.md:213 ("Bash rules match the whole command text"); https://code.claude.com/docs/en/headless.md:318 ("In a Manual mode `claude -p` run, a call that needs approval is denied"), :348 (`permission_denials`), :363 ("`Bash(git diff *)` allows any command starting with `git diff`"); https://code.claude.com/docs/en/skills.md:494–505 ("The `allowed-tools` rule then matches the exact command the skill body tells Claude to run"); v4-d3.md:500, :681, :893, :1356.

### R4-HA-03  —  major
- **Artifact:** D3, D2 (follow-up to R3-HA-02, accepted as H10)
- **Location:** D3 1.8, `claude/agents/core-refresh.md`: `tools: Read, Write, Glob, Grep, mcp__*` with `background: true`. If it fails: "if Claude Code rejects a frontmatter line, remove it". D2 §9: "a `tools` allowlist (`Read, Write, Glob, Grep, mcp__*`): no shell, and no future tool gets in."
- **What is wrong:** For `tools`, the docs give only the per-server entry `mcp__<server>__*`. A bare `mcp__*` is documented for `disallowedTools` only. For allow rules, the docs say an unanchored `mcp__*` "is skipped". The user registers tracker servers at run time, so CORE cannot name them in advance. The list also leaves out `ToolSearch`. Tool search is on by default, and it is how deferred MCP tools load. It is also where Claude Code reports a server that failed to connect. The real fix is already in the plan: `background: true` limits the helper to a fixed built-in set and "keeps every MCP tool".
- **What breaks if we ship it as-is:** If `mcp__*` resolves to nothing, or the tools stay deferred, the helper has no MCP tool. Every refresh then ends "`fetch_status: failed`" or "server not connected" on the one harness where the guard exists, and Update stops working. If the line is rejected, the written fallback deletes it. The helper then inherits every tool, Bash included, which brings back the injection path that R3-HA-02 closed.
- **Suggested fix:** Drop `tools`. Keep `background: true` and add `disallowedTools: Bash, PowerShell, Edit, NotebookEdit, WebFetch, WebSearch, Skill, LSP, EnterWorktree, ExitWorktree, Monitor, TaskStop, SendMessage, Artifact`. That leaves Read, Write, Glob, Grep, ToolSearch, and every MCP tool. No new built-in can get in, because the background filter removes it. Change the "if it fails" line so it never removes the restriction.
- **Evidence:** https://code.claude.com/docs/en/sub-agents.md:476–480 (`tools` example `mcp__github__*`; `mcp__*` only under `disallowedTools`), :440 (background "keeps every MCP tool but only these built-in tools: … `ToolSearch` …"); https://code.claude.com/docs/en/permissions.md:205 ("An unanchored allow glob such as … `"mcp__*"` is skipped"); https://code.claude.com/docs/en/mcp.md:1792 ("Tool search is enabled by default: MCP tools are deferred"), :429; https://code.claude.com/docs/en/tools-reference.md:61; v4-d3.md:824, :846; v4-d2.md:379.

### R4-HA-04  —  major
- **Artifact:** D3, D2 (follow-up to R3-HA-03, accepted as H10)
- **Location:** D3 1.8, `agents/core-refresh-antigravity.md`: frontmatter `tools: [view_file, write_to_file, …]`, `commandExecutionPolicy: off`, `inheritMcp: true`, with no `inheritCustomizations` and no `mainAgent`. D2 §9: "CORE ships its own helper file with command execution off".
- **What is wrong:** On Antigravity, `inheritCustomizations` defaults to `true`. That means the helper inherits the workspace's "skills, rules, and hooks". Its rules include CORE's own block from `.agents/rules/core.md` or `AGENTS.md`: "write it to `_memories/` as one short file". Its hooks include CORE's `SessionStart` and `PreInvocation`. `mainAgent` defaults to `true`, so the helper is listed as a primary agent the user can pick. `commandExecutionPolicy: off` sets the auto-execution policy for shell commands. It is the missing `run_command` in `tools` that removes the shell, not this field.
- **What breaks if we ship it as-is:** The one helper that reads untrusted tracker text has a write tool and a standing order to write decisions and commitments into `_memories/`. Text in a ticket can then land in the record without passing through `remember`, its write test, or `said_by`. If inherited hooks fire in the helper's own conversation, every refresh pulls the 7 KB status block and brief into the helper. It also writes session receipts for a session that never closes, which inflates `metrics`. Users see `core-refresh-antigravity` in `/agents` and the App's agent picker.
- **Suggested fix:** Add `inheritCustomizations: false` and `mainAgent: false` (keep `subagent: true`). In D2, say "no shell tool" instead of "command execution off". Note in 8.4 that the subagents page lists no `inheritMcp`, and check that MCP still reaches the helper.
- **Evidence:** https://antigravity.google/docs/build-plugins.md, custom-agents table ("`inheritMcp` / `inheritCustomizations` | `true` | Controls whether the agent inherits workspace MCP servers (`inheritMcp`) and skills, rules, and hooks (`inheritCustomizations`)"; "`mainAgent` | `true` | … users can select this agent as their primary session agent"; "`commandExecutionPolicy` … Auto-execution policy for shell commands"); https://antigravity.google/docs/subagents.md frontmatter table (no `inheritMcp` row; `mcpServers` default `[]`); v4-d3.md:831–842; v4-d2.md:379.

### R4-HA-05  —  minor
- **Artifact:** D3 (follow-up to R3-HA-01, accepted as H13)
- **Location:** Contract F: "`hook turn-end` (Antigravity's `Stop`): writes a `turn-end` receipt and answers `{}`." "The first call after this session's `session-start` or `turn-end` row starts a turn". 8.4 Accept: "exactly one non-repeat `prompt` row and one `turn-end` row per prompt."
- **What is wrong:** Three gaps in the H13 turn marker. (1) `Stop` output marks `decision` as **Required**, and `{}` leaves it out. (2) `Stop` also fires with `fullyIdle: false` while background tasks still run, and on `error` and `max_steps_exceeded`. Each of these ends the "turn" without a user prompt. (3) Google does not say `Stop` fires when the user cancels a run. If it does not, the next real prompt is treated as a repeat. The input carries `lastUserInput` on every `PreInvocation`, but contract F does not use it.
- **What breaks if we ship it as-is:** After a cancel, the next turn gets `{}` and a `repeat` row. The status block tells the agent "If one is missing, recall is off: say so once", so the user hears a false "recall is off". After a `fullyIdle: false` stop, a background task resuming counts as a new prompt and gets a recall block for an old question. A strict validator may reject the `Stop` output entirely. The 8.4 test sends two plain prompts, so it covers none of these.
- **Suggested fix:** Answer `Stop` with `{"decision":"stop"}`. Write `turn-end` only when `fullyIdle` is true. Also start a new turn when `lastUserInput` differs from the one recorded at the last non-repeat `prompt` row. Add a cancel case and a background-task case to 8.4.
- **Evidence:** https://antigravity.google/docs/hooks.md §Stop ("`fullyIdle` | boolean | **Required.** … `false` if active background tasks are still running"; "`terminationReason` … `"model_stop"`, `"max_steps_exceeded"`, `"error"`"; output "`decision` | string | **Required.**"), §Common input fields (`lastUserInput`); v4-d3.md:412–414, :1371.

### R4-HA-06  —  minor
- **Artifact:** D3, D2 (follow-up to H12)
- **Location:** D3 1.1: Codex gets "`AGENTS.md` … the block inserted after the first `# ` heading"; "Antigravity also reads `AGENTS.md`, so when both Codex and Antigravity are named, the `AGENTS.md` block serves both and `.agents/rules/core.md` is not written." D3 1.1: Codex liveness line "for the user to add to `~/.codex/AGENTS.md`". D2 §11: "Antigravity sees the block twice, in `AGENTS.md` and its rules file."
- **What is wrong:** H12 checked Claude Code's file precedence but not the other two harnesses'. In each directory Codex reads `AGENTS.override.md` *instead of* `AGENTS.md`, and in `~/.codex` it reads the override first too. Antigravity puts all `always_on` rules into one 20,000-token budget. When the total is over, it turns the *largest* rule files into one-line pointers, and a team's `AGENTS.md` is usually the largest. The tiny `.agents/rules/core.md` that D3 drops in the shared case is the one copy that would stay inline. D2 §11 and D3 1.1 also disagree on whether Antigravity gets one copy or two.
- **What breaks if we ship it as-is:** In a repo with an `AGENTS.override.md`, or a user with `~/.codex/AGENTS.override.md`, Codex never sees the block or the liveness line, while `agents_block: "added"` says it was written. In a Codex-and-Antigravity repo with heavy rules, Antigravity sees `- AGENTS.md:` and nothing more, so the three lines are not in context.
- **Suggested fix:** On Codex, write into `AGENTS.override.md` when one exists at that level, and say so. Always write `.agents/rules/core.md` for Antigravity, even when `AGENTS.md` also has the block. Then correct D2 §11's line.
- **Evidence:** https://learn.chatgpt.com/docs/agent-configuration/agents-md.md:11–12 ("Codex reads `AGENTS.override.md` if it exists. Otherwise, Codex reads `AGENTS.md`"; "it checks for `AGENTS.override.md`, then `AGENTS.md` … Codex includes at most one file per directory"); https://antigravity.google/docs/rules.md §Size limits ("If the total exceeds 20,000 tokens, Antigravity automatically demotes the largest rule files from inline text to lightweight pointers"); v4-d3.md:662–666; v4-d2.md:419.

### R4-HA-07  —  minor
- **Artifact:** D3, D2
- **Location:** Contract K: "`--sid` defaults to `CLAUDE_CODE_SESSION_ID`". 8.1: "The session id comes from `--sid`, else `CLAUDE_CODE_SESSION_ID` … Without a session id, the session rows are `unknown`." D2 §5 Skills only, "How you are told": "on Claude Code, `env` says **broken**".
- **What is wrong:** This is a native-first miss. Codex puts `CODEX_THREAD_ID` into the environment of every command the agent runs. It is the same id the hooks get as `session_id`, and the hooks spill files under `hook_outputs/<session_id>` in the docs and `<thread_id>` in the source. CORE reads only Claude Code's variable. So on Codex, `env` can say "broken" only when a status block hands over `sid=`. When the hooks are dead there is no status block, and that is exactly when the answer matters.
- **What breaks if we ship it as-is:** Codex resets hook approval on every CORE update, which D4 calls the most common way Codex falls down the ladder. In that state `env` and `metrics` say "not measured" instead of "broken: the session hook did not run". The liveness line is only a suggestion the user may never add to `~/.codex/AGENTS.md`. So the most frequent failure on Codex reads as "could not look".
- **Suggested fix:** Default `--sid` to `CLAUDE_CODE_SESSION_ID`, else `CODEX_THREAD_ID`, and say which in the evidence. Have 8.3 check that `CODEX_THREAD_ID` equals the hook's `session_id`.
- **Evidence:** `codex-rs/core/src/exec_env.rs` @rust-v0.167.0 lines 12, 30 (`CODEX_THREAD_ID_ENV_VAR`; "`CODEX_THREAD_ID` is injected when a thread id is provided"); `codex-rs/hooks/src/output_spill.rs` @rust-v0.167.0 line 57 ("`<temp_dir>/hook_outputs/<thread_id>/`") against https://learn.chatgpt.com/docs/hooks.md:538 ("`<temp_dir>/hook_outputs/<session_id>/<uuid>.txt`"); v4-d3.md:498, :1350; v4-d2.md:210, :219.

### R4-HA-08  —  minor
- **Artifact:** D2, D3, D1 (follow-up to R3-HA-05, accepted as H11)
- **Location:** D2 §5 Skills only: "a Projects thread with CORE added in Project settings > Plugins, where hooks do not run [research-claude-code §8]". D3 8.5: "In a Projects thread, add CORE in Project settings > Plugins; its hooks do not run there." D1 §6: same.
- **What is wrong:** The cited research section has no such statement. The docs say only that a thread does not run hooks from a repository's `.claude/settings.json`. For plugins, the research file records that plugin hooks "fire on their events" once "a session loads the plugin", and Project settings > Plugins does load the plugin into each thread. So "hooks do not run there" is unsourced and may be false. Claude Code also gives hooks the native signal for this case, `CLAUDE_CODE_REMOTE=true`, and CORE does not read it.
- **What breaks if we ship it as-is:** If plugin hooks do run, each thread is a fresh VM with an empty `noticed.json`. Every Projects thread then opens with "not enabled on this machine. Say 'enable CORE here'". If the user follows that, `enable add` writes to a VM that is thrown away. Meanwhile the ladder tells them hooks never run there, so the rung CORE reports is wrong.
- **Suggested fix:** Mark it "not stated by Anthropic; checked in 8.2". When `CLAUDE_CODE_REMOTE` is `true`, have `session-start` print one honest line, "CORE: cloud session; hooks are not enabled here; skills only", and offer no enabling.
- **Evidence:** https://code.claude.com/docs/en/claude-projects.md:354 ("Hooks in `.claude/settings.json` | Not run"), :368 (plugins "load into each new cloud thread"); https://code.claude.com/docs/en/cloud-environments.md:475; research-claude-code.md:88 ("Plugin hooks are always on … they fire on their events from then on"), :219–225 (no statement about plugin hooks in threads); https://code.claude.com/docs/en/env-vars.md:369 (`CLAUDE_CODE_REMOTE` "Read this from a hook … to detect whether you are in a cloud session"); v4-d2.md:219; v4-d3.md:1381; v4-d1.md:187.

### R4-HA-09  —  minor
- **Artifact:** D3, D2 (follow-up to R3-HA-15, accepted as H12)
- **Location:** D3 1.1: `rules/AGENTS.md` holds "In a project with a _memories/ folder: if this session did not start with a line beginning "CORE:", tell the user once that CORE's hooks are not running here." Contract F, not enabled: the notice is said "once per project per machine … Nothing else".
- **What is wrong:** A plugin's `rules/AGENTS.md` is always on, in every workspace. The same goes for the Codex copy in `~/.codex/AGENTS.md`. In a CORE folder that is *not enabled*, the hooks do run, say the notice once, and then print nothing in every later session. The liveness line cannot tell "not enabled" from "hooks dead".
- **What breaks if we ship it as-is:** On Antigravity, every session in a cloned repo that uses CORE, or in a project the user chose not to enable, starts with the agent saying "CORE's hooks are not running here". That is false, and it repeats forever. Users learn to ignore the one line that is meant to catch dead hooks.
- **Suggested fix:** In a CORE project that is not enabled, have `session-start` print one short line every session, `CORE: not enabled here`, which satisfies the liveness check. Keep the longer notice to once per machine.
- **Evidence:** https://antigravity.google/docs/build-plugins.md §Rules ("`rules/AGENTS.md` … Loaded automatically as an **always-on** rule whenever the plugin is enabled"); v4-d3.md:372 (not-enabled behaviour), :652–654, :666.

### R4-HA-10  —  minor
- **Artifact:** D3, D2
- **Location:** D3 1.1: the block goes to `.claude/rules/core.md`, and `CLAUDE.local.md` is "added to `.git/info/exclude`"; "Record `agents_block`; never ask again." D2 §9: the block written "With a yes to the exact text".
- **What is wrong:** `.claude/` and `.git/` are protected paths in Claude Code. A write there is "never auto-approved". It prompts in default and acceptEdits, goes to the classifier in auto, and is **denied** in `dontAsk`. Allow rules do not change this. CORE's own yes does not cover it. Also, in a git worktree `.git` is a file, so `.git/info/exclude` does not exist at that path.
- **What breaks if we ship it as-is:** Users get a second prompt right after answering CORE's. In `dontAsk` or `--restricted` sessions the write fails, yet `agents_block` is recorded and never offered again, so the block is silently missing. In a worktree the exclude write fails and the per-machine file shows up as untracked, ready to be committed.
- **Suggested fix:** Tell the user, before the write, that Claude Code will ask again for `.claude/`. After the write, read the file back, and record `agents_block: "added"` only if it is there. Resolve the exclude file with `git rev-parse --git-path info/exclude`.
- **Evidence:** https://code.claude.com/docs/en/permission-modes.md §Protected paths ("`default`, `acceptEdits` | Prompted … `dontAsk` | Denied"; "`permissions.allow` rules in settings files do not pre-approve protected-path writes"; protected directories include "`.git`" and "`.claude`"); v4-d3.md:660, :664, :666.
