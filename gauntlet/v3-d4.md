# D4 — The Critic Log

**The case against this plan, the questions a professional would ask, and every finding from the gauntlet.**

Draft v3 · 2026-11-09 · Companions: [D1 — The Case](v3-d1.md) · [D2 — The Machine](v3-d2.md) · [D3 — The Build](v3-d3.md) · Evidence: [grounding.md](grounding.md)

**In this document:** Part 1, the case against the plan · Part 2, what a professional would ask · how the review was run · Part 3, the gauntlet ledger, with every fix and every rebuttal · alternatives rejected · what was not verified.

This document does not defend the plan. Part 1 attacks the current draft (v3). Part 2 lists the questions a person who builds agent memory for a living would ask, with the plan's honest answer or "no answer yet". Part 3 records every finding the reviewers raised, what was done with it, and why. Part 3 can be read without opening any other file.

**Words used here.** *Layer 1* is the record, five skills, and a short block in the project's instruction file. *Layer 2* is the hooks and the one script. An *arm* is one setup the tests run the same tasks under: **full** (the plugin), **layer 1** (skills and block only), **files** (the record alone), **nothing**, and, in the record test, **built-in** (Claude Code's own memory). *Enabled* means the user said "use CORE here" on this machine; until then no hook passes project text to the agent.

## Part 1 — The case against this plan

Ranked. The first three are the ones most likely to sink it.

### 1. ★ The evidence costs money and comes from one harness

The record test, the five-arm comparison, and the CORE 3 comparison all spend model calls on one person's Claude Code account. A builder without one finishes the code and then reports "not measured" for every result that decides whether CORE should exist. Codex and Antigravity are never measured; their behaviour is inferred from Claude Code.

### 2. ★ The thresholds are guesses, frozen before any data

The gate needs 3 of 5 cases ahead by 0.2, a mean gap of 0.2, and no case behind by more than 0.2. Layer 1 must beat plain files by one probe in five. These numbers are written down before the first run so the first run cannot set its own bar. That stops one kind of bias. It does not make the numbers right. With five runs per arm, a real but small effect can still read as zero.

### 3. ★ Remembering still depends on the model choosing to remember

CORE 3's own records say in-flow writes get skipped "consistently". CORE 4's answer is a shorter skill, a write line in the block, a close pass, and a catch-up that proposes what was missed. None of these notices a decision when it happens. The record test measures the miss rate. Nothing in the design lowers it except brevity.

### 4. Recall is weaker on paraphrase, by design

CORE 4 matches a prompt against one-line summaries by shared words. A user who phrases a question differently from how the agent summarised the memory gets nothing. The paraphrase case is now in the gate, so this weakness can fail Layer 2. That is honest, and it may kill the wiring for a reason embeddings would fix.

### 5. Layer 1 in the repo is a copy that can go stale

For Codex and Antigravity, setup commits the five skills to `.agents/skills/`. Nothing updates that copy when CORE changes. A check warns when the copy is older than the installed CORE, but only on a machine where CORE is installed. On a machine without it, an old copy runs silently. Where the plugin is also installed, the agent sees the same skill twice.

### 6. A dead CORE is loud only if the agent reads the block

The prompt hook now prints one line every turn, and the block tells the agent to say so when the line is missing. That works only if the block reached the model. Claude Code skips `AGENTS.md` when a `CLAUDE.md` exists, which is why setup writes into `CLAUDE.md` then. Codex skips `AGENTS.md` in an untrusted project. A user who declines the block gets a silent CORE.

### 7. Codex drops to skills only after every update

Codex ties hook approval to a hash of the plugin's files. Every CORE release resets it. The user is told to re-approve once. A user who misses that runs on the lower rung until they notice.

### 8. The Antigravity half is written from documents alone

Its hook format is new, changes often, and fails silently. Its terminal sandbox hides the plugin folder from commands the agent runs, so agent-side commands fall back to Layer 1 behaviour there. The hook file and its JSON were written without a live install. Step 8.4 is the first contact, and it needs a machine with Antigravity.

### 9. The enabled list does not follow you

Each machine needs its own "use CORE here". Cloud machines start fresh each time. Skills no longer need the list, so a cloud session with the plugin gets Layer 1 in full, but never the hooks. For a user who lives in cloud sessions, CORE 4 is mostly Layer 1.

### 10. It removes things the owner uses

The swarm review, the HTML memory view, date-range queries, generated wiki links, and the background watcher. Each is removed with no replacement. For the person who used them, each is a loss.

### 11. The line budget invites cutting error handling

Thirteen commands, three hook formats, a self-test with planted faults, a migration, and a sampler, in 1,800 lines. A tight budget pushes toward dropping the careful handling the defect class punishes.

## Part 2 — What a professional would ask

| # | Question | The plan's answer today |
|---|---|---|
| 1 | **What is your write policy?** | The agent decides, guided by one test: would this change what you say or build in six weeks? Decisions, risks, promises, open questions, people; never secrets, raw outside text, or opinions about people. | 11 | **What would make you kill it?** | If Layer 1 does not beat plain files on the record test, CORE is not built: use the kit and the built-ins. If built-in memory beats Layer 1, use it on Claude Code. If Layer 2 fails its gate, it is shelved on a branch. |
| 12 | **What is your no-memory baseline?** | The **nothing** arm. |

| 16 | **What is your concurrency story?** | One fact per file; atomic writes; date ids; handoff notes named by time and machine; index not committed; receipts appended only. Two machines replacing the same fact is caught by `check --project`, which asks which wins. |
| 17 | **How do you roll back?** | Tag `v3.20.1`. `migrate` refuses an uncommitted store, and needs `--no-git` plus a backup warning outside Git. |
| 18 | **What do you log?** | One receipt per hook call and per check: time, event, session, status, counts, the memory ids pointed to. Never prompt or memory text. Kept 120 days. |
| 19 | **How do I debug a missed recall?** | `core.mjs recall --prompt "…"` shows what matched. `metrics` shows whether the hook ran and how often it offered pointers. |
| 20 | **What breaks when a harness changes?** | That harness's hook file. CORE drops to skills only. The missing recall line tells the agent, if the block reached it. |
| 21 | **Who is the second maintainer?** | Nobody. |
| 22 | **Why not embeddings?** | No measured miss needs them yet, and an embedding index goes stale. The paraphrase case is gated; if it fails the gate, this answer changes. |
| 23 | **How is focus measured?** | Planted due items among distractors; a reminder suppressed when snoozed. Whether the user *felt* less loaded is **not measured**. |
| 24 | **Does the brief itself help?** | Unknown. Always-loaded context files raised cost by over 20% with no general gain in task success in one study [literature §1]. The arms will show it. |

## How the review was run

- **Reviewers.** Each round, seven fresh agents — fact-checker, gap auditor, harness auditor, practitioner, executor, premise attacker, reader — each given only the file paths and `reviewer-brief.md`, never the drafting agent's reasoning. From round 2, each was told not to repeat an earlier finding and to report a broken earlier fix as a new finding. No reviewer reviewed its own text.
- **Defence.** The drafting agent ruled on every finding in writing. A partial rebuttal went back to the reviewer who raised it. A dispute went to a fresh judge agent, unless the drafting agent withdrew the rebuttal first.
- **Drafting.** From v3, each document was revised by a separate drafting agent working from the same written fix list. None of them reviewed.
- **A note on models.** At the user's request the model was changed partway through grounding. Every reviewer, judge, and drafting agent ran on the model the user chose.
- **Raw files.** `round-<n>/<reviewer>.md` holds each review; `round-<n>/defence.md` holds the rulings; `round-1/judge-PA-03.md` holds the one judge ruling.

## Alternatives considered and rejected

- **One reviewer instead of seven.** One reader anchors on the first problem found. Seven with different mandates do not share blind spots.
- **The drafting agent reviewing its own draft.** An author grades its own reasoning as sound.
- **Applying every finding without argument.** A plan that obeys every critic hedges every sentence. Seven partial rebuttals were written across two rounds. Five stood, one was overturned by a judge, and one was withdrawn when the reviewer showed evidence that the alternative fix failed.
- **A ledger that points to other files for its reasons.** Round 2 showed a reader cannot follow it. The fix codes and rebuttal reasons are now in this document.

## What was not verified

- That Part 1 is complete. It is one author's list.
- That the answers in Part 2 survive contact with a real build.
- That a reviewer working from documents alone can find what only a live install would show. No reviewer ran Codex or Antigravity.
- That round-2 fixes are right. Round 3 tests them.
