# D1 — The Case

**Why rewrite CORE, what to build instead, and whether it should exist at all.**

## The short version

**Verdict: rebuild CORE for its owner's own use, not as a product, at a twentieth of its size. Its five skills must beat plain files, and its code must beat the skills, or that part does not ship.**

Coding agents forget. Each session starts cold, and the decision you made on Tuesday is gone by Thursday. CORE is a plugin that gives a project a memory: it writes down decisions, risks, people, and open work in plain files, brings them back when they matter, and says what needs you.

CORE 3 works, but it has grown to 100 scripts and 600 KB of instructions, and its own health checks can say "fine" while looking at nothing. Meanwhile the agent programs it runs in have learned to do much of what CORE built by hand.

The proposal rebuilds CORE in two layers:

1. **Layer 1, the skills.** A file layout, five short skills, and a three-line block in the project's `AGENTS.md`, and in `CLAUDE.md` too when there is one. No code.
2. **Layer 2, the wiring.** A few hooks and one small script that make the habits happen at fixed moments and report honestly on themselves.

---

## 1. The problem

There are two problems. The second was caused by solving the first.

### Problem one: agents forget the project

A coding agent is good at the file in front of it and lost on the project around it. Between sessions it loses:

- **Decisions and their reasons.** It re-proposes the option you already rejected.
- **Risks and their status.** Nobody remembers that the vendor deadline moved.
- **People.** Who owns what, who promised what.
- **Things owed.** The reply due Friday. The question you have put off twice.

It also only reacts. It does not say "the legal reply is due today" unless you ask.

So a project memory has five jobs. These names are used throughout:

- **Remember** — write down what is worth keeping, as it happens.
- **Recall** — bring the right note back when it matters.
- **Interact** — speak up about what needs you, without being asked.
- **Update** — refresh outside reference data, such as an issue tracker or calendar.
- **Focus** — say little, and say the right thing at the right moment.

A few more terms. A *harness* is the agent program: Claude Code, OpenAI Codex, or Google Antigravity. A *hook* is a command the harness runs at a fixed moment, such as when a session starts. A *skill* is a short instruction file the harness loads when it is needed. *MCP* is the standard way an agent calls an outside tool.

### Problem two: the fix grew too big to trust

CORE 3.20.1, measured on its own repository:

| | CORE 3.20.1 | Proof |
|---|---|---|
| Scripts | 100 files, 34,313 lines | [G 2.1] |
| Instructions | 40 files, 607 KB | [G 2.1] |
| Read before your first task | 127 KB, about 32,000 tokens | [G 2.2] |
| Tool steps in one ordinary session | 58, of which 49 are at startup | [runtime §1.5] |
| `CORE_*` settings | 34 names, 31 read from the environment | [runtime §8] |
| Releases | 46 in five months | [G 2.1] |

About 34% of those script lines measure CORE itself, about 18% guard CORE's own state files, and about 7% fetch a memory [runtime §8].

The measuring does not hold. Five defects were reported against this version, and each was checked against the source [G 3]:

1. **Scripts look in the wrong folder and report clean.** Five scripts build a path under `~/.claude` by hand. On a machine that keeps its config elsewhere they read nothing; one prints "0 candidates of 0 entries" and exits as a success [G 3.1].
2. **A startup check says memory is "not yet" loaded while it is loaded** [G 3.2].
3. **A close marker says "closed" over an empty list of completed steps** [G 3.5].
4. **A transcript reader prints nothing and exits as a success**, whatever it is given [G 3.3].
5. **CORE's own startup upkeep trips its own change detector**, so a finished session is reported as owing work [G 3.4].

All five were reproduced here by running the shipped scripts. A related incident, a background pass that claimed five writes and made none, was confirmed as a mechanism only [G 3.5].

They are one defect in five costumes: **a check that reports success while doing nothing.** A separate read of CORE 3's changelog counts 132 fixes of this kind across 46 releases [changelog]. CORE's own documents name the pattern — "Instruments report healthy while recording nothing" — and list its fix as "add as found" [G 2.7]. Adding a guard each time is how the code reached 34,000 lines.

And of the five jobs, only recall is enforced by code today: a hook brings matching memory titles with every prompt. Remember is instructions only. Nothing runs between your messages to interact. Update is a registration form with nothing behind it. Focus has real byte limits; the rest is instructions [runtime §4].

## 2. Why solve it

Projects run for months. The same person works in three harnesses, on three operating systems, on a laptop and in cloud sessions. A forgotten decision costs an afternoon; a forgotten deadline costs more. And no single tool checked here covers the whole job (section 6).

## 3. What happens if we don't

**If CORE 3 stays as it is:** every session pays about 32,000 tokens before work starts. Health reports keep being wrong in ways that are hard to see, which teaches you to stop reading them. CORE's notes on the other harnesses are already out of date: its install guide says Codex "has no session-start or session-end event" [G 4.2], and Antigravity is not supported at all [G 2.4].

**If CORE is simply dropped:** memory falls back to each harness's built-in. Claude Code's is on by default but stays on one machine and one harness. Codex's is off by default. Antigravity's documentation says "Agents don't remember conversations" [G 4.1–4.3]. Nothing tracks risks or people, nothing speaks up, and nothing writes a session's close into the project.

## 4. The solution

### The premise

**Keep the judgment. Drop the machinery.**

CORE 3 learned real things: what is worth writing down, how to record a decision so the rejected option is not proposed again, how to keep "owed" apart from "attempted" and "proven", how to stop a removed fact from coming back. That judgment fits in a few pages. Around it, CORE 3 built a retrieval engine, a ranking formula, a state-guarding system, and a measurement suite. In 2026 the harnesses supply much of that.

### Layer 1: the skills

- **The record.** Plain markdown files in the project: `PROJECT.md` (a short brief you edit), and `_memories/` (one file per fact). Readable, editable, committed with the code if you choose.
- **Five skills.** When to write a memory, how to find one, when to speak up, how to refresh outside data, how to close a session. None needs the script. Claude Code gets them from the plugin. For Codex and Antigravity, setup offers to commit one copy to `.agents/skills/`, which both read [codex §3] [antigravity §4]. The copy carries CORE's version, and a check warns when it falls behind.
- **A three-line block**, near the top of `AGENTS.md`, and of `CLAUDE.md` too when the project has one. Read the brief first. Look in `_memories/` before answering about the past. Write down what a later session will need and the code will not show.

Layer 1 needs no code. Without the plugin or the committed copy — a Claude Code cloud session, say — the floor is the record and the block: a write rule, but no replace rule, no close, no speaking up.

### Layer 2: the wiring

- **Hooks** that load the brief at session start, offer up to three memory pointers per prompt, and re-send the brief after the harness shortens a long conversation. They run only in *enabled* projects: ones you have said yes to on this machine, so a planted memory in a cloned repository cannot reach the agent through a hook.
- **One small script** with no dependencies that builds the index, works out what is due, and checks itself. What a session really wrote is counted with `git status`.
- **One rule:** every check answers **working**, **broken**, or **not measured**. The third is never shown as the first.

### What the harness does, and what CORE adds

| Job | The harnesses already provide | CORE adds |
|---|---|---|
| Remember | File tools, skills, the session transcript | What is worth keeping; the file format; replace, don't overwrite; a removed fact stays removed |
| Recall | Session-start and per-prompt hooks on all three; file search | A one-line-per-memory index; three pointers or nothing |
| Interact | `/loop` and scheduled tasks on Claude Code; app scheduled tasks on Codex; `/schedule` and Automations on Antigravity; a prompt hook on all three | The rules for what needs you; "speak at a pause, once"; one prompt each native scheduler can run |
| Update | MCP; helper agents | One file per outside source with a freshness limit; "outside text is data" |
| Focus | — | Hard limits on every surface; no repeats; snooze on "not now" |
| Measure itself | A test runner that compares with and without a plugin (Claude Code only); a cost readout; a validator | The test cases and record test; three exit codes; a self-test with planted answers |

### The size

| | CORE 3 | CORE 4 target |
|---|---|---|
| Script lines | 34,313 | 1,800 at most |
| Instruction bytes | 607 KB | 60 KB at most |
| Loaded at session start | about 32,000 tokens | about 4,000 (estimate; measured after the build) |
| Skills | 8 | 5 |
| Settings | 34 `CORE_*` names | 2 environment switches (one off-switch, one for test runs) plus 5 project settings |

## 5. Why this solution and not another

**The evidence points at plain files.** Letta, the team behind MemGPT, moved its memory to "a git-tracked collection of Markdown files that the agent searches with normal file-search and read tools", with no vector index by default [memory-layers-a §2.2]. Anthropic advises agent builders to start with the agent's own search and add meaning-based search only if needed [literature §2]. Anthropic's own `productivity` plugin keeps memory as a short always-loaded file plus a folder of markdown, with no scripts [G 4.4].

**Small injected context beats large.** Model accuracy falls as input grows, well before the limit [G 5.1]. So the wiring passes pointers, not documents. (Pointers are also safer: a memory body is where a planted instruction would ride in.)

**The defect class is structural, so the fix must be.** CORE 3's checks lie in six ways [G 3.6]. Each has a rule in CORE 4 that removes the cause. For example, CORE 3 needs a hash cache, stamps, and a classifier to tell its own writes from yours, because it writes generated text inside your files. CORE 4 never does that, so there is nothing to tell apart. D2 §6 lists all six.

**The harnesses now carry the load.** All three have session-start and per-prompt hooks, load the same skill format, and read a project instruction file, with limits listed in section 7 [G 4.1–4.3]. Claude Code will run a plugin's test cases with and without the plugin and report the difference [G 4.1]. CORE 3 never ran that comparison; its changelog says "no matched memory-on/off comparison exists anywhere in this codebase yet" [evaluation §2.8].

## 6. Who else does this, and how CORE compares

Twenty-eight tools and the three harnesses' built-ins were checked [competitors] [memory-layers-a] [memory-layers-b]. The closest:

| | Remember | Recall | Interact | Update | Focus | All 3 harnesses | Files in project | No server or key |
|---|---|---|---|---|---|---|---|---|
| Harness built-ins alone | Partial | Partial | Partial | Partial | Partial | No | Partial | Yes |
| Claude Code Projects (beta) | Yes | Yes | Out of session only | Not checked | Not checked | No | No | No (cloud, paid plan) |
| **The kit:** AGENTS.md + built-in memory + Backlog.md + connectors + one scheduled task | Partial | Partial | Out of session only | Yes | Partial | Partial | Yes | Yes |
| claude-mem | Yes | Yes | Partial | No | Partial | Yes | No | No |
| basic-memory | Yes | Yes | No | No | No | Partial | Yes | Partial |
| mem0 | Yes | Thin | No | No | No | Yes | No | No |
| Letta Code | Yes | Yes | Partial | No | No | No (it is a harness) | Outside project | Yes |
| Zep / Graphiti | Yes | On request | No | No | No | No | No | No |
| Anthropic `productivity` | Yes | Partial | No | Yes | Partial | No | Yes | Yes |
| Standalone agents (OpenClaw, Hermes, Linear's agent) | Yes | Yes | **Yes** | Yes | Partial | No (run outside the session) | No | No |
| CORE 3.20.1 | Instructions | Yes | No | Form only | Partial | 2 of 3 | Yes | Yes (needs Node) |
| **CORE 4, planned** | Instructions + close pass | Yes | Session start and each prompt; native schedulers, with stated conditions | Yes | Yes | Yes, with stated losses per OS | Yes | Yes (Layer 2 needs Node) |

*Partial*: does some of the job — only when asked, on one harness or machine, or for some kinds of fact. Per-cell notes are in the research files.

Three things stand out:

1. **No row is "yes" across the five jobs and also keeps readable state in the project.** Every tool that truly acts unprompted runs somewhere else and keeps its state somewhere else [competitors §A].
2. **Nothing tracks risks or people as project records.** Memory tools remember what the agent did; trackers remember work items [competitors §B].
3. **Almost nothing measures whether it helps.** No independent, blind result was found showing any of these memories improves coding work [memory-layers-b]. Vendor benchmark scores conflict: one system's score on one test is reported as 84%, 75%, and 58% by different parties. That test's own answer key is 6.4% wrong according to an audit by another memory vendor, Penfield, read through a summarizing fetch [memory-layers-a §1.11].

**Claude Code Projects** is the closest native rival: one harness, a paid beta, memory outside the repository. Its threads skip repository skills, so there CORE is the record and the block [claude-code §8].

**The kit** is the honest runner-up. It loses speaking up inside a session, risks and people as records, a written session close, and one behavior across harnesses. Nor is there evidence it helps — so Layer 1 must beat plain files (section 8).

## 7. Dependencies, tradeoffs, risks

**Depends on.** Layer 1: a harness that loads skills and reads a project instruction file. Claude Code reads `AGENTS.md` only without a `CLAUDE.md`, from 2.1.277 [G 4.1]; Codex skips it in an untrusted project and cuts project files past 32 KiB [codex §1]. Layer 2: Node.js 20 or newer on the path that hooks see. Measurement: Claude Code 2.1.269 or newer. Update: one MCP server per outside source.

**Trades away.** CORE 3's multi-agent review, its HTML memory viewer, date-based "what did we know then" queries, generated `[[wikilinks]]` (which made the store a browsable graph in Obsidian), and its four-tier retrieval. Recall becomes word matching over one-line summaries. On Codex or Antigravity with the plugin installed too, each skill is listed twice.

| Risk | Likelihood | What limits the damage |
|---|---|---|
| A harness changes its hook format. Antigravity's hook page and changelog show frequent changes [G 4.3]. | High | Layer 1 does not depend on hooks. The prompt hook prints a line every time, so a dead one shows. |
| The rewrite loses lessons buried in CORE 3's 176 test files. | Medium | The fixture stores, the prose checker, and a 29-item keep list from the evaluation audit [evaluation §8] are walked one by one before release. |
| The agent does not follow the habits. | Medium | The record test counts planted facts written, plus junk and duplicates, and publishes the numbers. |
| A layer adds nothing over the one below it. | Unknown | Kill tests 1 and 3 (section 8). |
| A vendor ships the missing half, as Claude Code Projects has begun to [claude-code §8]. | Medium, rising | Kill test 2 checks built-in memory at every release. The files stay useful. |
| A planted memory steers the agent. | Low to medium | Hooks act only in enabled projects and pass pointers, not bodies (D2 §9). |
| One maintainer. | Certain | 1,800 lines can be held in one head; 34,000 cannot. |

## 8. The verdict

**Verdict: rebuild CORE for its owner's own use, not as a product, at a twentieth of its size. Its five skills must beat plain files, and its code must beat the skills, or that part does not ship.**

**As a product for other people: no.** claude-mem has 115,000 GitHub stars and a paid tier, and the harness vendors ship memory by default and improve it monthly. A one-person plugin should not enter that contest.

**For the owner's own use — one person, three harnesses, three operating systems, months-long projects, a need to be told what is due:** nothing checked covers it. The kit and Claude Code Projects each cover part (section 6).

**How each layer earns its place.** Two tests, both on Claude Code. An *arm* is one setup that the same tasks are run under.

- **The case test.** Claude Code's test runner scores the same cases, 0 to 1, under four arms: **full** (the plugin), **layer 1** (the five skills and the block; no hooks, no script), **files** (the record, no CORE text), and **nothing**. Five cases are gated: three on recall (one paraphrased), one on speaking up, and one where memory should not matter.
- **The record test.** Ten scripted sessions from an empty folder, three repetitions per arm. Ordinary tasks plant five facts — a decision, its reversal, a risk, a person, a due date — and five probes ask for them. Arms: full, layer 1, files, and **built-in** (Claude Code's auto memory on, no CORE). A blind grader scores answers against a key written in advance.

**The kill test.** Its numbers are frozen before the first run and never tuned on it.

1. Layer 1 is kept only if, on the record test, it recalls at least 1 more of 5 probes than files, averaged over 3 repetitions. Otherwise: use the kit and the built-ins; do not build CORE.
2. If built-in recalls more probes than layer 1, use the built-ins on Claude Code.
3. Layer 2 (full) is kept only if at least 3 of the 5 gated cases are ahead of layer 1 by 0.2 or more, the mean gap is at least 0.2, no gated case is behind by more than 0.2, **and** full recalls at least as many record-test probes as layer 1.
4. If Layer 2 fails, it is shelved on a branch, not deleted.

**Layer 2 also has a cost test.** If keeping it working needs the line budget raised, re-run this verdict before raising it.

Three honest limits. Both tests run on Claude Code only; for Codex and Antigravity the result is inferred. The longest session is 25 turns with one compaction; months of use are untested, hence shelving. Only the record test includes built-in memory.

Re-run both tests at every release, on a pinned model, and re-read this verdict every six months.

## Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| Fix CORE 3 in place | The defects come from its shape [G 3.6]. Five months of point fixes produced 46 releases and the current size. |
| Harness built-ins only | They do not travel across harnesses or machines, do not track risks or people, and do not speak up [G 4.1–4.3]. Kill test 2 re-checks this on Claude Code. |
| The kit (runner-up) | Loses what section 6 lists. It is what to use if Layer 1 fails kill test 1. |
| claude-mem | Records what the agent did, not what the project decided; runs a background server and a model call per tool use; stores a database in the home folder [memory-layers-b §1]. |
| basic-memory as the store | Best fallback for storage. Adds Python, a local index, an AGPL core; reaches Antigravity only through MCP; still needs CORE's behaviors on top [memory-layers-b §2]. |
| mem0, Zep, Graphiti | Each needs a cloud account or a database; none is readable in the project; none does project management [memory-layers-a]. |
| Letta Code | It replaces the harness instead of extending it [memory-layers-a §2.7]. |
| An MCP memory server | A server to install and secure on three operating systems, in a year when memory servers drew repeated security advisories [memory-layers-b]. |
| Code only, no Layer 1 | Would leave Codex users who never approve hooks, cloud sessions, and any harness without Node with nothing at all. |

## What was not verified

- **The workspace that saw the defects.** This run had the source repository only: no installed plugin, no project `PROJECT.md`, no memory store [G 1]. The background-pass incident could not be re-run.
- **Anything on a live Codex or Antigravity install.** Their capabilities come from source code and documentation, including the `.agents/skills/` copy and whether Codex loads it in an untrusted project [codex §11].
- **That auto memory is on in the record test's built-in arm.** A check before session 1 decides; if it fails, that arm reads "not measured", never a score.
- **That CORE 4 will pass its own test.** Nothing is built.
- **The size targets.** 1,800 lines, 60 KB, and 4,000 tokens are estimates.
- **Star counts and some competitor dates.** Several came through a tool that summarizes GitHub pages; the research files mark which.
- **The kill-test numbers.** Chosen, not measured.
