# Round 2 — Practitioner review of v2

Reviewer mandate: I build agent memory systems for a living. Would I sign v2 off? I read D1–D4 v2, the round-1 files and `defence.md`, and checked claims against `research-literature.md`, `grounding.md`, the fixtures in `tests/fixtures/`, and Claude Code's `headless.md` (fetched 2026-11-09).

Short answer: not yet. v2 fixed the decay rule, gave ids dates, and stopped committing the index. But the test that decides whether the code should exist now compares the plugin against an arm that has no skills and no instruction to write. So it credits Layer 1's work to Layer 2. Its first leg can almost never pass honestly, and its second leg runs unisolated. Separately, three parts of the record have no lifecycle: finished commitments, handoff notes, and the brief. Each of these fails within weeks of real use.

### R2-PR-01  —  critical
- **Artifact:** D2 §7; D3 7.6, 7.7, 9.4; D1 §8
- **Location:** D2 §7, "**Plugin minus convention** is what the wiring adds" and "**Convention minus files** is what the habits add without code"; D3 7.6, "Convention twins … Only their without-plugin score is used"; D3 7.7, "Arm **convention** writes `AGENTS.md` with the block and uses no plugin".
- **What is wrong:** D1 defines Layer 1 as the record, **five skills**, and the `AGENTS.md` block. The convention arm in both tests has the record and the block only. The skills ship inside the plugin, so in a without-plugin run they are absent. So "plugin minus convention" measures the skills *plus* the wiring, not the wiring. The three-line block also never tells the agent to write anything. It says read `PROJECT.md` and look in `_memories/`. In 7.7, the record test, the convention arm therefore has no write instruction at all. The plugin arm has the `remember` skill. The plugin will win the write rate, and so the probes, for a reason that belongs to Layer 1. The judge's ruling that created 7.7 asked for "the two-page `AGENTS.md` convention". v2 built a three-line read-only block instead.
- **What breaks if we ship it as-is:** D1's verdict says to keep Layer 2 only if it beats Layer 1. Neither test ever runs Layer 1. 7.7 will report that the plugin "keeps the better record", and the plan will keep the hooks, the watcher and 1,800 lines of script on the strength of five markdown files. This is the defect class moved into the gate: a check that reports a result for a thing it did not measure.
- **Suggested fix:** Add a **skills-only** arm to both tests: the plugin loaded with `CORE_DISABLE=1` (skills present, hooks no-op), plus the block. Gate Layer 2 on plugin minus skills-only. Keep the read-only convention arm as a separate, ungated baseline.
- **Evidence:** v2-d1.md:113–118 (Layer 1 = record, five skills, block); v2-d2.md:70–74 (the block's text); v2-d2.md:238–239; v2-d3.md:998, 1043; `round-1/judge-PA-03.md` ("the two-page `AGENTS.md` convention"). D3 decision 16 already makes `CORE_DISABLE=1` available, and `honesty-no-hooks` already uses it.

### R2-PR-02  —  critical
- **Artifact:** D3 7.7; D2 §7 "Does it keep a better record?"
- **Location:** 7.7, "runs the ten prompts in order with `claude -p "<prompt>" --allowedTools …`"; "Arm **builtin** uses neither, leaving Claude Code's built-in memory on."
- **What is wrong:** 7.7 runs plain `claude -p` on the maintainer's real home, without `--bare`. Claude Code's docs say that without `--bare`, `-p` "discovers and loads" hooks, skills, installed plugins, MCP servers, auto memory and `CLAUDE.md` "as an interactive session would, including anything configured in … `~/.claude`". So every arm carries the maintainer's own setup. That very likely includes CORE 3, which the owner uses and which enrolls folders on its own (D2 §9). Auto memory is on in all three arms, not just "builtin". The plugin arm loads a second plugin also named `core`. Nothing checks which plugins loaded, or that CORE 4's hooks fired: 7.7 reads no receipts and no `system/init` event. The same docs say `--bare`, which skips plugin hooks "even plugin ones passed by flag", "will become the default for `-p` in a future release". When that ships, the plugin arm becomes skills-only and the builtin arm loses auto memory. The report will look the same.
- **What breaks if we ship it as-is:** One of the two legs that decide Layer 2's future measures an unknown mix of CORE 3, CORE 4, auto memory and the user's settings. A Claude Code update can change what it measures with no visible sign. This is the defect the plan exists to kill: an instrument that reports a number while measuring something else.
- **Suggested fix:** Run each session with `--output-format stream-json`. Fail the repetition unless `system/init.plugins` lists exactly the arm's plugins. For the plugin arm, also require a `session-start` and a `prompt` receipt for that session id. Point `CLAUDE_CONFIG_DIR` at a fresh temporary config per repetition, so no user plugin, `CLAUDE.md`, or MCP server loads. Set `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in every arm except builtin.
- **Evidence:** `https://code.claude.com/docs/en/headless.md` §Start faster with bare mode: "Without it, `claude -p` discovers and loads them as an interactive session would, including anything configured in the working directory or `~/.claude`"; "Hooks still don't run in bare mode … of a plugin you load with a flag"; "will become the default for `-p` in a future release"; §Fail CI when a plugin… doesn't load (`system/init` `plugins`). research-claude-code.md:52 (`CLAUDE_CODE_DISABLE_AUTO_MEMORY`); grounding.md:206 (`CLAUDE_CONFIG_DIR`). v2-d3.md:1043.

### R2-PR-03  —  major
- **Artifact:** D3 9.4, 0.6, 7.6; D2 §7
- **Location:** 9.4, "plugin − convention ≥ 0.3 … averaged over the three gated cases, no gated case below −0.1"; 9.4 "No case made worse | no case with plugin − files below −0.1".
- **What is wrong:** This is the arithmetic of the v2 gate. (1) Two of the three gated cases sit at the ceiling in both arms. The Lantern fixture still has 45 memories, and both questions share words with one summary ("retry header", "provider … v2 support"). The convention arm is told to "look in `_memories/`" and will grep its way to 1.0, as round 1 predicted for arm B. (2) So the 0.3 mean rests on `proactive-due` alone. With five runs, scores move in steps of 0.2. A diff of 0.8 there gives a mean of 0.27, which fails. The gate needs a perfect 5–0 sweep. (3) The −0.1 floor is finer than the 0.2 step, so one extra failed run in either ceiling case vetoes the gate. If both arms pass 95% of runs, the plugin loses at least one more run than the convention on a given case 18% of the time. Across the two cases that is 33%. (4) The "no case made worse" gate compares against **files**, not convention. A plugin that does worse than the convention passes it. Round 1 asked for per-job gates and a grep-hard fixture (R1-PR-01). The fix added a convention arm and dropped `brief-budget`, but left the fixture and the averaging.
- **What breaks if we ship it as-is:** Leg one of the keep rule is a lottery. It is decided by whether the model repeats one injected "Needs you now" line in five of five runs, and it is vetoed a third of the time by noise. So the decision falls to leg two (R2-PR-01, R2-PR-02, R2-PR-04). Recall, the job D1 leads with, contributes nothing to the decision.
- **Suggested fix:** Gate per job, with each job's own bar. Use at least ten runs on gated cases. Express the floor in runs ("no case loses two or more runs more than the comparison arm"). Compare "made worse" against the convention arm. Give recall a fixture where grep is hard: paraphrased questions, and several hundred memories with shared vocabulary.
- **Evidence:** v2-d3.md:520–533 (fixture), 1004–1006 (gated cases), 1138, 1144 ("scores move in steps of 0.2"). Binomial arithmetic: P(X>Y) for X, Y ~ Bin(5, 0.05) = 0.18; 1 − 0.82² = 0.33. Literature §7: "Small sets hide small effects"; "Report n, the paired difference, and an interval."

### R2-PR-04  —  major
- **Artifact:** D3 9.4, 7.7; D1 §8
- **Location:** 9.4, "**or** in step 7.7 the plugin's probe score beats the convention's by at least 1 (of 5) on the mean, with a write rate no lower".
- **What is wrong:** The keep rule is an OR of two noisy legs, so it leans toward keeping. Leg two has 3 repetitions × 5 probes per arm. If the wiring adds nothing and both arms answer 60% of probes, the plugin still beats the convention by one probe on the mean 18% of the time. At 80% it does so 13% of the time. "Write rate no lower" holds about half the time by chance, and ties count as passing. D4 Part 1 item 2 notes that the thresholds were chosen in advance. It does not note that the OR gives a useless Layer 2 two chances to pass and a useful one two chances to be kept. Nothing makes the rule symmetric.
- **What breaks if we ship it as-is:** Even after R2-PR-01 and R2-PR-02 are fixed, a Layer 2 that adds nothing is kept roughly one release in six on leg two alone. The verdict "re-run at every release" turns that into a near-certain eventual keep, and nothing ever un-keeps it.
- **Suggested fix:** Make the rule one pre-registered decision. Pool both legs into one paired comparison per job with an interval. Keep Layer 2 only when the interval's lower bound is above zero. Use at least ten repetitions in 7.7.
- **Evidence:** Exact binomial: three repetitions of Bin(5, p), P(sum difference ≥ 3) = 0.18 at p = 0.5, 0.18 at p = 0.6, 0.13 at p = 0.8. v2-d3.md:1138, 1144; v2-d4.md:21.

### R2-PR-05  —  major
- **Artifact:** D3 7.7; D2 §7
- **Location:** 7.7, "**write rate** — how many of the five planted facts appear, by regex, in any file under the folder … after session 10".
- **What is wrong:** The record test counts only hits. It never counts junk, duplicates, or stale copies. An arm that writes 40 files with every sentence of every session scores the same write rate as one that writes five clean memories, or a higher one. For the reversal, the regex finds the new decision even when the old one is still active beside it. The only check on that is one probe, which may land on either copy. "Write rate no lower" rewards writing more. The literature's clearest memory result is the opposite: a store of 413 files did worse than nine.
- **What breaks if we ship it as-is:** The test cannot tell a disciplined record from a sprawling one, which is the property that decides whether the store still works at month six. A plugin that over-writes passes, and so does one that leaves two live versions of a reversed decision.
- **Suggested fix:** After session 10, also report files written, active memories that are not about a planted fact, and whether the session-2 decision is still active (it must be in `archive/`). Gate on "no more than N unplanted active memories" next to the write rate.
- **Evidence:** v2-d3.md:1041–1044. Literature §3: "Sonnet 3.7 wrote 413 memory files across 225 folders and earned one badge" against "nine files … earned four badges"; §4: "Never leave two live versions of a fact for search to find."

### R2-PR-06  —  major
- **Artifact:** D3 7.7, 5.3, contract E; D2 §2
- **Location:** 7.7, "runs the ten prompts in order … one session each"; contract E `no-handoff`, "no receipt of any kind in the last 2 hours"; D2 §2, "**On Wednesday you just quit.** Most sessions end that way."
- **What is wrong:** By D2's own account, most real sessions end without "wrap up". Their writes then come from the close pass, or from the catch-up at the next start. 7.7 runs ten `-p` sessions back to back, minutes apart, and no prompt says "wrap up". So `finalize` never runs. The 2-hour idle condition is never met, so `no-handoff` never fires and the catch-up never runs. 7.7 measures only the mid-task write path, and in a regime real use does not have.
- **What breaks if we ship it as-is:** The record test says nothing about the two write paths D1 counts as CORE 4's edge over CORE 3 ("instructions + close pass"). These are the paths that will produce most real memories. A broken catch-up, or one that invents facts (R2-PR-07), passes the release gate.
- **Suggested fix:** Give 7.7 a clock. Back-date receipts between sessions, or pass a test-only "now" to `core.mjs`, so sessions 3 and 6 end unclosed and are caught up. End session 9 with "wrap up". Report writes by path: mid-task, close, catch-up.
- **Evidence:** v2-d3.md:309, 842, 1043; v2-d2.md:130; v2-d1.md §6 table row "CORE 4, planned": "Instructions + close pass".

### R2-PR-07  —  major
- **Artifact:** D3 5.3; D2 §2, §9 "Read"; D2 Alternatives
- **Location:** 5.3, "Give a helper agent that one file and this task: 'Read the last 200 KB. List decisions made, commitments with dates, and questions left open. Quote nothing longer than one line.' Write memories for what it returns"; D2 Alternatives, "A script that detects decisions in each turn … extraction pipelines in the research omit and invent facts".
- **What is wrong:** The catch-up is an extraction pipeline. A model reads a transcript and returns "decisions", and the main agent writes them straight into the committed `_memories/` with no review. D2 rejects that pattern for per-turn use, and here it becomes the main write path (R2-PR-06). The round-1 fix (R1-PR-06) changed "300 lines" to "200 KB". It did not fix the problem. A Claude Code transcript is JSONL full of tool results, so 200 KB is often the last few file reads and test runs, and the session's first hours are never seen. When several sessions are unclosed (a week of plain quits), nothing says which one is caught up, or in what order. The helper also reads raw tool output: fetched pages, MCP results, file contents. Unlike the refresh helper, it gets no "outside text is data" rule, no tool limit, and no `said_by` rule for what it produces. A planted sentence in a fetched page ("the team decided to drop the auth check") can come back as a decision memory.
- **What breaks if we ship it as-is:** Most of the store will be written by the least reliable path, unseen by the user. Extraction systems in the cited study hallucinate and miss updates at high rates. The errors become committed, recalled "decisions", and the next sessions trust them.
- **Suggested fix:** Have the catch-up write to `_core/inbox/` with `said_by: agent` and a source line, and ask the user to approve the list at the next pause. Filter the transcript to user and assistant text before taking the tail. Catch up only the newest unclosed session, and list the rest as "not caught up". Give the helper the same data rule and tool limits as `core-refresh`.
- **Evidence:** v2-d3.md:842, 863–875 (the refresh helper's rules, absent here); v2-d2.md:363. Literature §3: "all systems have accuracy (Acc.) below 62%"; "most systems suffer omission rates above 50%"; "Session-end summarization is itself an injection point."

### R2-PR-08  —  major
- **Artifact:** D2 §7 "Numbers with a stated basis"; D4 Q6, Q8; D3 7.6
- **Location:** D2, "Session-start cost | about 4,000 tokens"; D4 Q8, "About 4,000 at start plus pointers"; ledger R1-PR-09, "Token figure includes the `core` skill body".
- **What is wrong:** R1-PR-09 asked for three things: null cases (an ordinary task where memory does not matter), tokens per arm recorded next to A − B, and helper runs counted in the cost. v2 did only the restatement. 7.6 has no null case. Every case is a memory case, so a plugin that slows ordinary work by 20% passes every gate. No arm's tokens or time are recorded. The catch-up helper reads up to 200 KB, roughly 50,000 tokens, per unclosed session, and D2 says most sessions are unclosed. That cost is missing from every budget. Pointers (up to 1,000 bytes a prompt) build up in context for the whole session, and that is missing too.

No gate can see the tax on ordinary coding, which is most of the work. The literature's example is a context feature that cost 20–23% more and helped nothing.

Record tokens and wall time per arm in `cells.mjs`. Add "catch-up helper tokens per session" to the D2 table, measured in 7.7.

### R2-PR-09  —  major
- **Artifact:** D3 contract E, 4.3, 5.1, 4.4; D2 §3
- **Location:** Contract E, "`due` | An active memory's `by-when` is past or within `now_hours` | `now`"; `remember` §8, "A failed attempt does not cancel what is owed"; `pulse` §4, "never list … open risks, or open questions".
- **What is wrong:** Nothing ever closes a commitment, an answered open question, or a retired risk. Contract C has no "done" status. No skill says "when a promise is kept, move it to `archive/`", and the tidy rule cannot touch these types. So once a `by-when` passes, the item is a `now` item for good. The "legal reply due Friday" sent on Friday is still "needs you now" in March. The only way out is "forget", which marks a true fact as retired. That is the wrong status, and it then blocks a similar fact from being written later.
- **What breaks if we ship it as-is:** Within a few weeks the session-start block opens with things already done. With the 4-hour rule (R2-PR-10) they are repeated several times a day. This is the failure the literature names: "empty or repeated check-ins led users to ignore about half of all proactive signals". The real deadline is lost among met ones. Speaking up, the job D1 sells against the kit, becomes noise.
- **Suggested fix:** Add a `done` outcome. A kept promise or answered question moves to `archive/` with `status: archived` and `resolved: <date>`. The `core` skill asks once, at the first announcement after a due date, "Done, or still owed?". A past-due item announced three times with no reply drops to `soon`.
- **Evidence:** v2-d3.md:279–284 (statuses), 304, 782, 814–818. Literature §8: "This led users to ignore around 50% of the proactive agent signals"; SRE: "Every page should be actionable."

### R2-PR-10  —  major
- **Artifact:** D2 §3; D3 contract E, 3.4, 7.4, 7.6
- **Location:** D2 §3, "An item announced on this machine in the last four hours is counted in the status line, not repeated"; 3.4, "Read at most the last 200 lines of this machine's receipts file for `data.recent`"; ledger R1-PR-10, "snoozes counted in `metrics`".
- **What is wrong:** The R1-PR-10 fix is three parts short. (1) The 4-hour window has no basis and is missing from D2's "Numbers with a stated basis" table. A developer who opens sessions at 9, 14 and 19 hears the same item three times a day. (2) `data.recent` comes from the last 200 lines of one receipts file. Watchers write a row every 10 minutes per open session, and prompt rows pile up. With three sessions open, the morning's `announce` row scrolls out of the tail before four hours pass, and the item is announced again. R1-PR-15 asked for lookup by session id or time, not tail position. That part was not done. Receipts are also split by harness, so a Codex session does not see what a Claude Code session announced. (3) R1-PR-10 asked to count announced → acted on / snoozed / ignored. `metrics` counts snoozes only. No eval case checks that a second session the same day stays quiet. The only quiet case uses a snoozed item.
- **What breaks if we ship it as-is:** Nobody can tell whether speaking up helps or annoys. The plan's one quiet-path test passes, while the common case, several sessions a day, repeats itself.
- **Suggested fix:** Announce each item at most once per day per machine, across harnesses, and look it up by time from all of this machine's receipt files. Add `announced`, `acted_on` (the item's memory changed within a day), and `ignored` to `metrics`. Add an eval case seeded with an `announce` receipt from an hour ago, with a reply that must not repeat it.
- **Evidence:** v2-d2.md:149, 266–277; v2-d3.md:315, 656, 737, 949, 1010. Round-1 R1-PR-15 suggested fix: "Look up announcements by `sid`, not by tail position." Literature §8: "Count your own messages. Track how many are acted on, ignored, or dismissed."

### R2-PR-11  —  major
- **Artifact:** D3 4.4 §4, contract H; D2 §4 "Tidying"; D4 Q3
- **Location:** `pulse` §4, "whose `updated` is older than `archive_after_days` and whose id appears in no `prompt` or `announce` receipt in that window"; contract H, "Rows older than 30 days are pruned at session start".
- **What is wrong:** The F7 fix rests on evidence the plan deletes. The window is 90 days, but receipts are kept for 30. So "not pointed to in 90 days" is checked against 30 days and reported as 90. That is the defect class: an instrument that reads less than it claims and does not say so. Receipts are also per machine and git-ignored. On a fresh clone, a new laptop, or a cloud session there are none, so every old explainer counts as "never pointed to". No command implements the rule: contract K has no tidy or candidates command. The agent must read the receipt files and cross-match ids by hand, and it may skip that step and propose on age alone. The eval case `pulse-tidy-protects-decisions` uses a fixture with no observation, explainer or review-finding at all. It passes if nothing is proposed, so the positive path is never tested.
- **What breaks if we ship it as-is:** On every new machine, the first tidy proposes archiving explainers the user relies on. The user is told they were "not pointed to in 90 days". That is false, and the user approves it because the tool said so.
- **Suggested fix:** Add `core.mjs tidy-candidates`, which returns `unknown` when receipt coverage is shorter than the window ("only 30 days of receipts here"). Either keep a small per-id "last pointed" file for 90 days or set the window to the retention. Add a fixture explainer that was pointed to last week and must not be proposed.
- **Evidence:** v2-d3.md:402, 430, 435–453 (contract K), 782, 1011; v2-d2.md:165, 277 ("enough for `metrics`' default 14-day window twice over", with no mention of the 90-day consumer).

### R2-PR-12  —  major
- **Artifact:** D4 Q9; D2 §11; D3 contract G, 3.2, 3.5
- **Location:** D4 Q9, "The active set is held near 300 by proposals … untested past 500"; contract G, "`RARE_FRACTION` … start at … 0.02"; 3.2, the gold set over Lantern, `policy-safety-store` and `nested-store`.
- **What is wrong:** At 10,000 sessions the D4 answer is false. Tidy may propose only observations, review notes and explainers. The `remember` skill's own test sends almost every write to decisions, risks, promises, open questions and people, which can never be proposed. Finished promises never leave either (R2-PR-09). So the active set grows with the project. At a few memories a week it passes 300 within a year and keeps going. The 300 warning then fires on every check, forever. Recall thresholds are tuned on stores of 7, 10 and 45 lines, where `RARE_FRACTION` 0.02 rounds to "the term is in exactly one line". At 2,000 lines it means "in up to 40 lines", which is a different matcher. Common project words then pass alone, so a single shared word yields a pointer. The perf test stops at 500 memories, and session start hashes every active file.
- **What breaks if we ship it as-is:** At scale, recall noise rises with no change to the code. The only field metric, `pointer_rate`, reports the rise as more pointers. The size warning becomes permanent noise. Nothing in the plan was measured at the size a months-long project reaches.
- **Suggested fix:** Correct D4 Q9. Tune and test the matcher on a store of at least 1,000 memories built from realistic decisions with shared vocabulary. Make the rare rule an absolute count, not a fraction, or report precision at 300, 1,000 and 3,000. Extend `perf.test.mjs` to 3,000 memories.
- **Evidence:** v2-d4.md:77; v2-d3.md:384–386, 643, 698, 782, 811; fixture sizes from `find tests/fixtures/<store> -path '*_memories*' -name '*.md' | wc -l`: nested 7, policy-safety 10, tier-safety 5, obligation3 7. Literature §2 (near-miss documents hurt the model).

### R2-PR-13  —  major
- **Artifact:** D3 3.2; D2 §7; D4 Q5
- **Location:** 3.2, "Mark queries `q01`–`q20` as tuning and `q21`–`q30` as held out … It asserts: every held-out literal query returns its expected id; no query ever returns a `forbidden` id; no negative query returns anything; 'please reformat this json file' returns nothing".
- **What is wrong:** The F8 fix for R1-PR-08 measures less than it reports. The held-out set is 10 queries, about three per kind, and precision and recall "by kind" on three queries carry no information. The same agent writes the queries, the summaries they target, and the matcher it tunes. "Literal" is defined as sharing two words with the summary, and `MIN_TERMS` starts at 2, so it passes by construction. "Never returns a forbidden id" cannot fail for the retired memories the negatives are built around, because `archive/` is not in `INDEX.md`. The real precision risk is ordinary coding prompts: long ones, pasted stack traces and logs, file names, identifiers. These carry dozens of terms and will clear `MIN_TERMS = 2` against something in a 300-line index. One short negative ("please reformat this json file") stands in for all of that.
- **What breaks if we ship it as-is:** Step 3.2 will log a precision number that cannot be low. In use, the hook will attach near-miss pointers to many working prompts, which the literature names as the harmful case, and no instrument will notice.
- **Suggested fix:** Have a fresh helper, not the builder, write the paraphrase and negative queries from the memory bodies alone. Hold out half. Add 30 negatives taken from real coding prompts (long, with logs and identifiers). Report false-pointer rate per prompt-length band. Make negatives target **active** near-miss memories, not retired ones.
- **Evidence:** v2-d3.md:294 (index holds active memories only), 384–386, 643–644; v2-d4.md:73. Literature §7: "selected by test score rather than train score to avoid overfitting"; "Trigger tests need hard negatives … the near-misses"; §2: "the retriever's highest-scoring documents that are not directly relevant … negatively impact".

### R2-PR-14  —  major
- **Artifact:** D3 2.5 `two-live`, 5.1 §5; D2 §11
- **Location:** `two-live`, "An active memory has a `supersedes` edge to a memory that is still active"; D2 §11, "Ids carry the date and the index is not committed, which removes the common conflicts."
- **What is wrong:** Date ids prevent filename clashes. They do not prevent two versions of one fact from forking. Say branch A (laptop) supersedes `dc-…-retry-header-v2` with "move to v3", and branch B (cloud) supersedes it with "stay on v2 until January". Git merges both cleanly: the old file moves to `archive/` on both sides, and two new files are added. Now two active memories supersede the same target. `two-live` passes, because the target is archived. `near-duplicate` passes, because the summaries use different words. The same happens without git, when two open sessions on one machine reverse one decision. No check runs at session start, so the fork is found only if someone runs `check --project`.
- **What breaks if we ship it as-is:** The user's stated setup (laptop, cloud, three harnesses, branches) produces the literature's worst case. The recall hook hands the agent both values, and the agent acts on one at random, confidently.
- **Suggested fix:** Add a `fork` check: two active memories with a `supersedes` edge to the same target fail. Run it in the session-start hook, and raise a `now` item "two current versions of <id> — which is right?".
- **Evidence:** v2-d3.md:602, 607, 814; v2-d2.md:348. Literature §4: "retrieval surfaces stale and fresh values side by side … it produces a confidently wrong action"; Claude Code docs: "Claude may pick one arbitrarily".

### R2-PR-15  —  major
- **Artifact:** D3 contract B, 5.2, 4.3 §6; D2 §11
- **Location:** Contract B, "`_summaries/summary-YYYY-MM-DD.md` (-b, -c for later ones the same day)"; `finalize` §2, "Update the 'Now' and 'Next' sections of `PROJECT.md`"; `core` §6, "Still true → set `updated` to today".
- **What is wrong:** The F16 fix for R1-PR-11 covered memory ids and `INDEX.md` only. Three conflict sources remain. (1) Handoff notes are named by date. Two machines or branches that each close a session on the same day both add `summary-2026-11-09.md`, which is an add/add conflict on every merge. On one machine, two sessions closing at once both pick `-b`, and one note overwrites the other. (2) Every close rewrites `PROJECT.md`'s "Now" and "Next", so any two branches with closed sessions conflict there, as R1-PR-11 said. (3) "Check before you rely" bumps `updated` in a committed file each time a memory is verified, so verifying on two branches conflicts.
- **What breaks if we ship it as-is:** Merges of parallel work keep producing conflicts in CORE's files. Users resolve them by taking one side, which silently drops the other side's handoff or brief update. D2 §11's "removes the common conflicts" is not true for the files touched most often.
- **Suggested fix:** Name handoff notes with time and machine (`summary-20261109T1405-<machine8>.md`). Keep "Now/Next" updates to one appended dated line that merges cleanly, or document the conflict. Record verification in a separate `verified:` field. Better still, record it in git-ignored `_core/` state, so a check does not edit the committed file.
- **Evidence:** v2-d3.md:246, 765, 837; v2-d2.md:348; round-1 R1-PR-11 ("`PROJECT.md`'s 'Now' and 'Next' lines will conflict for the same reason").

### R2-PR-16  —  major
- **Artifact:** D3 contract H, 1.2, 3.3
- **Location:** Contract F, session start: "Prune receipts older than 30 days"; 1.2, "`prune(project, days)`".
- **What is wrong:** Pruning means reading the receipts file, filtering it, and writing it back. It runs at **every** session start, while other sessions' hooks and watchers append to the same file. Any row appended between the read and the write-back is lost. With the atomic temp-and-rename write the plan uses, the loss is silent. On Windows, renaming over a file another process has open can fail outright. The rows that get lost matter. A lost `close` row makes a closed session look unclosed, so it is caught up again and its memories are written twice. A lost `announce` row means a repeat. A lost `session-start` row makes `env` report the hook as not running.
- **What breaks if we ship it as-is:** At thousands of sessions with several open at once, the heartbeat that every metric depends on drops rows at random. Two of the losses cause duplicate writes into the record. Nothing reports it, since `metrics` counts only the rows that survived.
- **Suggested fix:** Never rewrite a live receipts file. Rotate it by month (`receipts-<machine>-<harness>-YYYY-MM.jsonl`) and delete whole files older than the window. Appends then never race a rewrite.
- **Evidence:** v2-d3.md:357, 402, 555–556, 737 (watcher appends every `watch_minutes`).

### R2-PR-17  —  major
- **Artifact:** D3 5.2, 4.3 §2, 3.3; D2 §1, §2
- **Location:** `finalize` §3, "Write `_summaries/summary-<date>.md`, at most 150 words, headings 'Resume here', 'Done', 'Open'"; contract F session start injects "`--- PROJECT.md ---`" only.
- **What is wrong:** Nothing ever reads a handoff note. The session-start hook injects `PROJECT.md`. The `core` skill's start-of-session section reads the `CORE:` block and `PROJECT.md`. The index covers `_memories/` only, so the prompt hook cannot point to a summary either. The "Resume here" note, and the late note the catch-up writes, are write-only. The eval checks only that the file exists (`finalize-handoff`, `catch-up-unclosed`), never that the next session uses it.
- **What breaks if we ship it as-is:** The close tells the user "Handoff note saved", and the catch-up spends a helper run writing one. The next session then starts from `PROJECT.md`'s "Now" line alone, and the open items in the note ("flaky auth test still fails") are lost. A record that is reported as saved and is never read is a quiet form of the defect class.
- **Suggested fix:** Have the session-start hook add the newest handoff note's "Resume here" and "Open" sections (capped, say 600 bytes) under the brief. Add an eval case where the "Open" item exists only in the latest note and must come up at "Where are we?". Or drop the notes and say so.
- **Evidence:** v2-d3.md:342–358, 754, 837, 842, 1023, 1025; v2-d2.md:126–128.

### R2-PR-18  —  major
- **Artifact:** D3 4.3 §8, 5.1 §5, 2.5 `brief-links`; D2 §1
- **Location:** `core` §8, "Add only what changed this session. Never refill it from memory"; `brief-links`, "`PROJECT.md` names an id that is archived or missing".
- **What is wrong:** The brief is the one copy of the facts loaded in full at every session start and after every compaction. It has no supersede rule. When `remember` replaces a decision, it moves the old memory to `archive/`. It never looks for the old fact in `PROJECT.md`. `finalize` touches only "Now" and "Next". `brief-links` catches an archived **id** and misses the usual case, plain prose such as "We stay on the v2 header until the sandbox is fixed." D2's own walk-through shows the brief carrying "still on the v2 format for now".
- **What breaks if we ship it as-is:** After a reversal, the always-loaded brief says one thing, and the memory, shown only on a matching prompt, says the other. The stale copy wins because it is always there. This is two live versions of a fact again, in the most prominent place.
- **Suggested fix:** Add to `remember` §5: when superseding, search `PROJECT.md` for the old fact's subject words and update or remove that line in the same turn. Have `check --project` warn when a `PROJECT.md` line shares most of its words with an archived memory's summary.
- **Evidence:** v2-d3.md:604, 760, 814, 837; v2-d2.md:101 ("still on the v2 format for now"). Literature §4: "One fact, one place. When it changes, replace it."

### R2-PR-19  —  major
- **Artifact:** D2 §4 "Built-in memory"; D3 4.3 §12, 7.7
- **Location:** D2, "The `remember` skill draws the line: project facts … go in the record; your personal working preferences stay in auto memory"; ledger R1-PR-14, "Division of labour … the skill says so".
- **What is wrong:** The fix is a sentence in CORE's skill. Auto memory follows the harness's own policy, which explicitly saves type `project`: "ongoing work, deadlines, and decisions". A CORE skill does not switch that off. So on Claude Code both systems still record the same decision. When it is reversed, only CORE's copy is superseded. The old value stays in `MEMORY.md`, which is loaded at every session start and re-injected after compaction. R1-PR-14 asked for an eval case seeded with a conflicting auto-memory note, and none was added. 7.7 runs with auto memory on in every arm (R2-PR-02) and never looks in its folder for the stale decision.
- **What breaks if we ship it as-is:** On the main harness, every changed fact can leave a live stale copy in a store CORE neither reads nor fixes. The user sees the agent "forget" a reversal that CORE recorded correctly.
- **Suggested fix:** At enable time on Claude Code, tell the user once that auto memory also stores decisions, and offer the exact setting to turn it off for this project. CORE writes no harness settings, so the user applies it. In 7.7's plugin arm with auto memory on, grep the auto-memory folder after session 10 for the superseded decision, and report it.
- **Evidence:** grounding.md:203–204 ("type `project` is 'ongoing work, deadlines, and decisions…'"); research-claude-code.md:187 ("Auto memory | Re-injected from disk"); v2-d2.md:163; v2-d3.md:764, 1043.

### R2-PR-20  —  major
- **Artifact:** D2 §7 "On your own project"; D3 7.5 `blind-check.md`, 7.4 skill §5
- **Location:** "A fresh helper agent, shown only those files, writes one question per memory … A fourth helper, blind to the labels, grades both against the memory text."
- **What is wrong:** The questions come from the memories, and the answers are graded against the same memories. The helper that may read `_memories/` can look up each answer, and the helper told there is no record cannot know project facts. So the record arm wins every question by construction, whatever the record's quality. A memory that is false, such as a reversed decision still active or a catch-up invention (R2-PR-07), produces a question whose "right" answer is the false fact, and the record arm is scored correct. The check cannot come out against CORE.
- **What breaks if we ship it as-is:** The `metrics` skill offers this to the user as the way to "check CORE on this project's own memories". It always reports the record helping. That is a check that cannot fail, presented as evidence, and the plan's own literature calls that "worse than useless".
- **Suggested fix:** Ground the questions in something other than the memory: the git log, the code, or the user's answer. Or reframe the check as an audit. Show the user the ten sampled memories with their dates and sources, and ask which are still true. That gives a store-accuracy rate, which is the number that matters.
- **Evidence:** v2-d2.md:261–263; v2-d3.md:965, 976. Literature §7, skill-creator grader: "A passing grade on a weak assertion is worse than useless — it creates false confidence."

### R2-PR-22  —  minor

### R2-PR-23  —  minor
- **Artifact:** D3 contract C, 4.3 §6
- **Location:** `core` §6, "a memory about something that can change is a claim. Check its source first."
- **What is wrong:** Contract C has no source field. A memory has `said_by`, but no pointer to the code location, ticket, or message it rests on. So "check its source first" has nothing structured to check, and the agent must work out the source from prose. The design rule the plan cites, and GitHub's measured approach, both store a citation with each fact so it can be checked at read time.
- **What breaks if we ship it as-is:** Read-time verification, the one staleness defence with measured results, happens only when the agent happens to find the source. Stale claims about the code are trusted.
- **Suggested fix:** Add an optional `source:` list (path, path:line, ticket id, or URL) to contract C. Have `remember` fill it when one exists, and have `core` §6 check it before relying on the memory.
- **Evidence:** v2-d3.md:259–285, 758. Literature §4: "they check at read time … by checking the cited code locations"; design rule "Stamp every note with a date and a source pointer."
