### R2-HA-01  —  critical
- **Artifact:** D3 (and D2 §7)
- **Location:** D3 step 7.6, "Every case's `case.yaml`" (only `schema_version`, `name`, `runs`, `context.scaffold_script`, `execution.env`), and "Every case grants `Write Edit "Bash(node *)"` in the run command"; `tests/evals-shape.test.mjs` asserts every `case.yaml` matches this template.
- **What is wrong:** In `claude plugin eval`, the read-only tools are not on by default. A run gets only the tools the case lists in `allowed_tools`, plus what `--allow-tools` grants. The template has no `allowed_tools`, and the run command grants only Write, Edit, and `Bash(node *)`. So every run, in every arm, has no `Read`, `Glob`, `Grep`, `Skill`, or `Agent`. The agent cannot open `PROJECT.md` or a memory file. It cannot invoke a CORE skill except by a typed `/core:…` prompt. It cannot start the `core-refresh` or catch-up helper. `Edit` also fails, because it needs the file read first, and there is no Read tool. The convention and files arms are hit hardest. Their whole method is "look in `_memories/`", and they have no tool to look with. The plugin arm still gets the injected brief and pointer lines.
- **What breaks if we ship it as-is:** The gate (plugin minus convention ≥ 0.3) is measured between an arm that is handed text and arms that are blind. So the plugin can pass the gate without the wiring helping at all. Every `tool_used: Skill` grader fails. `recall-past-decision` can pass only if "PAY-212" happens to sit in the pointer's one-line summary. `proactive-due` and `remember-supersede` cannot edit anything. This is the defect class inside the measurement: the release gate reports a result while the arms it compares could not do the task.
- **Suggested fix:** Add `allowed_tools: [Read, Glob, Grep, Skill, Agent]` under `execution:` in the template. Make `evals-shape.test.mjs` assert it. Add a step 0.6 check that one `-convention` run shows a `Read` call on `_memories/`.
- **Evidence:** https://code.claude.com/docs/en/plugin-evals.md:347 ("A run allows only the read-only tools the case lists in `allowed_tools`, from `Read`, `Glob`, `Grep`, … `Skill`, … `Agent`, … plus whatever you grant with `--allow-tools`"), :345, :163 (quickstart uses `allowed_tools: [Read, Glob, Grep, Skill]`); https://code.claude.com/docs/en/tools-reference.md:255 (read-before-edit; newer models skip it only "when … the Read tool is available"); v2-d3.md:985–999.

### R2-HA-02  —  critical
- **Artifact:** D3, D2 (follow-up to R1-HA-03, accepted as F15)
- **Location:** D3 step 6.2, `disallowedTools: Bash, PowerShell, Edit`, "(`disallowedTools` removes those tools and keeps the rest of the pool, MCP tools included)". D2 §9: "it runs with shell and edit tools removed (`disallowedTools`), so it keeps MCP but cannot run a command".
- **What is wrong:** The fix keeps MCP, which is right. But the denylist leaves other tools that run commands or act outside the digest. Subagents run in the background by default. A background subagent keeps `Monitor`, which "runs a command in the background" under the same rules as Bash. It also keeps `Write`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Skill`, and `SendMessage`. The round-1 suggestion also listed `WebFetch, WebSearch, Agent`. v2 dropped those and missed `Monitor`. So a poisoned ticket can tell the helper to run a command through `Monitor`, to send the store to a URL through `WebFetch`, or to call CORE's own `remember` skill and write a memory. Any Bash allow rule the user has also covers `Monitor`, so such a command can run with no prompt.
- **What breaks if we ship it as-is:** D2 §9's central injection control for Update is false as written. The one helper that reads outside text has a command runner, a network fetch, and a writer for any path. D2 says the controls are "structural" because people approve 93% of prompts. This control is only a prompt.
- **Suggested fix:** Add `Monitor, NotebookEdit, WebFetch, WebSearch, Skill, SendMessage, Agent` to `disallowedTools`. Rewrite D2 to "keeps MCP, Read and Write; no shell, no web, no skills". Add `check --plugin` rows that fail if the agent file lacks any of these names.
- **Evidence:** https://code.claude.com/docs/en/sub-agents.md:429 (background "is the default"), :440 (background subagent keeps "`Bash`, `PowerShell`, `Edit`, `Write`, `NotebookEdit`, `WebFetch`, `WebSearch`, … `Skill`, … `Monitor`, … `SendMessage`"); https://code.claude.com/docs/en/tools-reference.md:39 (`Monitor` "Runs a command in the background"), :391 ("it uses the same permission rules as Bash"); v2-d3.md:869, :874; v2-d2.md:315.

### R2-HA-03  —  major
- **Artifact:** D2, D3, D1 (follow-up to R1-HA-14, accepted as F3)
- **Location:** D2 §1: "All three harnesses read `AGENTS.md` [G 4.1–4.3] … That is why Layer 1 works everywhere." D2 §5 rungs Skills only and Files only, "How you are told: The `AGENTS.md` block line, if installed". D3 step 3.6: "appends it to `AGENTS.md` (creating the file if needed)". D1:202: "Without them CORE drops a rung and says so."
- **What is wrong:** F3 made the `AGENTS.md` block the only dead-hook detector. R1-HA-14 said the block must also go into `CLAUDE.md`. v2 still writes `AGENTS.md` only. The block never reaches the model in three common cases. (1) Claude Code reads `AGENTS.md` only when there is no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` in the working folder or above it. It also skips `AGENTS.md` before v2.1.277, and in some first sessions after an upgrade. (2) Codex does not load project `AGENTS.md` at all when the project is marked untrusted. Plugin hooks there can still run, or fail, on their own approval. (3) Codex gives all project docs one 32 KiB budget and cuts what does not fit. Step 3.6 appends the block to the end of the file, so in a large `AGENTS.md` the block is the first thing cut.
- **What breaks if we ship it as-is:** In any repository that has a `CLAUDE.md`, a dead CORE on Claude Code is silent, with the block "installed". The same holds for a long `AGENTS.md` on Codex, or a project marked untrusted. Requirement 3, "no rung is a silent no-op", is met only where none of these apply. The user also sees `agents_block: "added"` and believes they are covered.
- **Suggested fix:** When a `CLAUDE.md` or `CLAUDE.local.md` exists, add the block to `CLAUDE.md` too, with the user's yes. Put the block at the top of `AGENTS.md`, not the end. Have `check --project` warn when `AGENTS.md` exceeds 32 KiB. Name these three cases on the Skills only and Files only rows.
- **Evidence:** https://code.claude.com/docs/en/memory.md:359–360, :371–373, :367 and §"When AGENTS.md support is unavailable"; `codex-rs/core/src/agents_md.rs` @rust-v0.167.0 lines 63–65 (`if config.active_project.is_untrusted() { return … }`), 67 and 155–166 (`project_doc_max_bytes`, "project doc exceeds remaining budget; truncating"); `codex-rs/hooks/src/engine/discovery.rs` (no project-trust check on plugin hooks); v2-d2.md:76, :185–186; v2-d3.md:711.

### R2-HA-05  —  major
- **Artifact:** D2, D3
- **Location:** D2 §5, Hooked rung, "Antigravity with hooks working | Brief, recall, status at start, close, checks". Contract K: "the script is `scripts/core.mjs` in the plugin folder". Skills run `verify`, `close`, `index`, `enable add`, `env`, `metrics`.
- **What is wrong:** Antigravity installs plugins under `~/.gemini/config/plugins/<plugin-name>`. Its terminal sandbox is on by default. On macOS and Linux, "anything not explicitly mounted is invisible inside the sandbox", and only project folders, temp, build caches, and system folders are mounted. On Windows, "other files in your user profile … stay hidden". So the agent's own `node …/core.mjs …` cannot see the script. It cannot see `~/.core/` (the enabled list and `install-id`) either, or the transcript under `~/.gemini/antigravity*/brain/`. In the Default preset, each run outside the sandbox stops for approval. Hooks run as plugin processes, outside this path, so the brief and recall still work.
- **What breaks if we ship it as-is:** On Antigravity, "close" and "checks" do not work by default. `finalize` cannot get counts from disk. `enable add` cannot write the enabled list. Catch-up cannot read the transcript. The Hooked row claims all of these. Each attempt either fails, which the skill reports as "not measured", or asks for approval every time. Neither is named as a loss.
- **Suggested fix:** Move "close, checks, enabling" to the What-you-lose column for Antigravity under the default sandbox. Document the one-time `read_file`/`write_file` grants for the plugin folder and `~/.core` in `ladder.md` and `INSTALL.md`. Add both to step 8.4's live check.
- **Evidence:** https://antigravity.google/docs/build-plugins.md:242 ("Installed plugins are unpacked into a read-only plugin directory (`~/.gemini/config/plugins/<plugin-name>`)"); https://antigravity.google/docs/sandbox.md:13, :63, :74, :124; https://antigravity.google/docs/hooks.md §Common input fields (`transcriptPath` under `<app_data_dir>`); v2-d2.md:184.

### R2-HA-06  —  major
- **Artifact:** D3 (follow-up to R1-HA-18 / R1-PR-17 / R1-GA-07, accepted as F6e)
- **Location:** Contract H: "`<machine>`: first 8 characters of `~/.core/install-id`; `nohome` if it cannot be read or created". Contract B: `install-id` "created if missing". Step 7.6: "Inside the runner's sandbox the home folder is unreadable; nothing in a test run needs it". `catch-up-unclosed`: "Fixture adds `_core/receipts-nohome-claude-code.jsonl`".
- **What is wrong:** F6e stopped eval runs from writing the trust list. It did not handle the machine id. In an eval run, hooks run outside the sandbox and resolve the real account home through `os.userInfo()`. They read the maintainer's real `install-id`, or create it in the real home if it is missing. The agent's `node core.mjs …` runs inside the sandbox, where the home folder is unreadable, so it gets `nohome`. Each run then has two machine ids. Hook rows go to `receipts-<real>-claude-code.jsonl`. Agent rows such as `close` go to `receipts-nohome-claude-code.jsonl`. The session-start hook builds the queue from "this machine's receipts", which is the real-id file. So it never sees the planted `nohome` session, and `no-handoff` never reaches the status block. Not verified: if the repository sits under the home folder, the sandboxed agent may not be able to read `core.mjs` at all.
- **What breaks if we ship it as-is:** `catch-up-unclosed` fails on a correct build, or passes only if the agent goes looking without being told. `close` rows never match their own sessions, so `handoff_coverage` reads 0 in every run. A first eval run on a clean machine writes `~/.core/install-id` into the real home, which `real-home-guard.mjs` exists to forbid. The same split happens outside evals under Antigravity's sandbox (R2-HA-05).
- **Suggested fix:** Put the machine id on the `CORE:` status line. Agent-side commands then take it with `--machine`, instead of re-deriving it. Name the fixture file after the id the hook will use. In `fixture.sh`, let the scaffold write the receipts through the hook's own command, so the file name matches.
- **Evidence:** https://code.claude.com/docs/en/plugin-evals.md:355 ("your home directory and Claude Code configuration are unreadable"), :477 ("hooks and servers run outside the agent's sandbox"); v2-d3.md:252, :395, :999, :1025; `scripts/release/real-home-guard.mjs:3`.

### R2-HA-07  —  major
- **Artifact:** D3, D4
- **Location:** Decision 16 and step 3.1: `EVAL_CORE_ENABLE=1` enables when "the project's real path and the real path of `env.CLAUDE_PLUGIN_DATA || env.PLUGIN_DATA` sit inside `os.tmpdir()`'s real path". Step 7.6 "If it fails": "Detect this from `untrusted-project-inert` passing in a case that should be enabled".
- **What is wrong:** Three harness facts work against the condition. (1) Claude Code exports `CLAUDE_PLUGIN_DATA` to hook processes only. "The variables aren't present in the environment of commands Claude runs through the Bash tool." So every agent-side `isEnabled` call in a run, such as `env`'s `enabled` row, says "not enabled" while the hook says enabled. (2) The run's child process gets only an allowlist from your shell: PATH, locale, provider and `CLAUDE_CODE_*` settings. `TMPDIR` is listed for the scaffold, not for the child. On macOS, Node's `os.tmpdir()` with no `TMPDIR` is `/tmp`, while per-user temp folders sit under `/var/folders/…`. So on macOS the hook's temp root and the run's folders can differ, and the condition can fail on every case. This is not verified either way. (3) The detection rule cannot detect it. `untrusted-project-inert` passes whether enabling works or not, because it has no `EVAL_CORE_ENABLE`.
- **What breaks if we ship it as-is:** In every run, the hook and the agent disagree about whether the project is enabled. That is two records of one state, which D2 §6 forbids. On macOS the whole suite may measure the "not enabled" path. The planned detector reports nothing, so the release reads plugin scores that were never measured with the plugin on. D4 Part 1 #4 names the risk but trusts a detector that cannot see it.
- **Suggested fix:** Agent-side commands do not decide enabling. They read it from the `CORE:` line, or report `unknown` with reason `eval-switch-hook-only`. Detect a dead switch by a regex grader on `recall-past-decision`'s trace for `CORE: hooks ok`. Fail the suite when it is absent. Log `os.tmpdir()` and the plugin data path in the session-start receipt, so step 0.6 shows them on each OS.
- **Evidence:** https://code.claude.com/docs/en/plugins/manifest-reference.md:573 ("Monitor commands | … | Not exported"), :579 ("aren't present in the environment of commands Claude runs through the Bash tool"); https://code.claude.com/docs/en/plugin-evals.md:281 (scaffold gets `TMPDIR`), :533 (child inherits "only an allowlist"); https://code.claude.com/docs/en/env-vars.md:412 (Claude Code's own temp default is "`/tmp` on macOS, `os.tmpdir()` on Linux and Windows"); v2-d3.md:97, :637, :1030, :1036; v2-d4.md Part 1 #4.

### R2-HA-08  —  major
- **Artifact:** D3, D2
- **Location:** Step 8.1 `env`: "`watch` | a `watch` receipt in the last `2 × watch_minutes`". Step 7.4: "`watch_alive` | a `watch` row in the last `2 × watch_minutes`". D2 §5: "A capability is **working** when a receipt from this session proves it". Contract H: every row has `sid`.

- **Suggested fix:** Have `watch` write `sid: null`. Until then, `env`'s `watch` row is `unknown`, reason `watch-not-session-bound`, unless only one session has started in the window. Say in D2 that the watcher cannot yet be tied to a session.
- **Evidence:** https://code.claude.com/docs/en/env-vars.md:384 (`CLAUDE_CODE_SESSION_ID` "in Bash and PowerShell tool subprocesses, hook command subprocesses, and stdio MCP server subprocesses"); https://code.claude.com/docs/en/plugins/manifest-reference.md:573; v2-d3.md:948, :1066; v2-d2.md:176.

### R2-HA-10  —  major
- **Artifact:** D2, D3
- **Location:** D2 §5: "Without a session id it never borrows another session's receipt; it shows the newest receipts as evidence and marks the hook lines 'not measured'." D3 step 5.2 (4): "the id and start time come from the `CORE:` block; without them, skip `close` and say 'close not recorded'".

With a known `sid`, an enabled project, and a readable receipts file, `session_hook` with no row is `fail`. - **Evidence:** https://code.claude.com/docs/en/env-vars.md:384 ("Set automatically to the current session ID in Bash and PowerShell tool subprocesses, hook command subprocesses … For Bash, PowerShell, and hooks this matches the `session_id` field in the hook JSON input"); v2-d2.md:176; v2-d3.md:837, :1070.

### R2-HA-13  —  minor

### R2-HA-14  —  minor
- **Artifact:** D3, D2
- **Location:** Contract F `hook prompt` and contract E `no-handoff` ("≥ 3 `prompt` rows"); step 7.4 `pointer_rate`, `silent_sessions`; step 4.4 (7) recommends `/loop 30m /core:pulse`; step 6.2 starts `core-refresh` as a helper.
