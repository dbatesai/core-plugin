## Part 1 — The case against this plan

### 1. Most of the plan cannot run without paying

The decisive evidence — the four-arm runner, the ten-session record test, the CORE 3 comparison — all spend model calls on one person's account, on one harness. The step labels make this visible, but they also show that a builder with no Claude Code subscription can finish phases 0–6 and then must report "not measured" for every gate that decides whether Layer 2 should exist.

### 2. The gate is still small and still chosen

Three gated cases, five runs per arm, scores in steps of 0.2. A threshold of 0.3, a floor of −0.1, and "1 of 5 probes" were picked before any data. The plan says to replace them after the first run — which means the first run both sets the bar and is judged against it.

### 3. The convention arm is a stand-in

The runner loads no project instruction files, so the convention arm receives the `AGENTS.md` text as an appended system prompt. An appended system prompt is louder than a file the agent may skim. If it overstates the convention, the plugin looks worse than it is; if it understates it, better. Nobody has measured which.

### 4. Test-run enabling rests on an unverified path

`EVAL_CORE_ENABLE` works only if the runner places the plugin data folder under the system temp folder. If it does not, every case silently measures the "not enabled" path. D3 adds a detection, but the detection is itself a case that could fail for other reasons.

### 5. Remembering still depends on the model choosing to remember

CORE 3's own files say in-flow writes get suppressed "consistently". CORE 4's answer is a shorter skill, a "mid-task" paragraph, a close pass, and a catch-up for unclosed sessions. None of these notices a decision when it happens. The ten-session test will measure the miss rate. Nothing in the design lowers it except brevity.

### 6. Recall is weaker on paraphrase, by design

CORE 3 matched against memory bodies, followed links, and had a fallback for vague questions. CORE 4 matches a prompt against one-line summaries. The gold set includes ten paraphrase queries, and the plan reports their score without asserting it, because it expects them to fail. A user who phrases things differently from how the agent summarized them gets nothing.

### 7. The dead-hook warning depends on a file the user may decline

If the user says no to the `AGENTS.md` block, a dead CORE is silent on every harness. The plan admits it. The rung table still lists "skills only" as a rung where CORE tells you what is missing — only if the block is installed.

### 8. Codex will drop to skills-only after every update

Hook approval on Codex is tied to a hash of the plugin's files. Every CORE release resets it. The plan's answer is a sentence telling the user to re-approve. A user who misses it runs on the lower rung until they notice, and the only notice is the block they may have declined.

### 9. The Antigravity half is written from documents alone

Its hook format is new, has changed often, fails silently, and has a reported crash on an injected field. The hook file, the JSON shapes, and the `PreInvocation` deduplication were all written without a live install. Step 8.4 is the first contact, and it is labeled `[live install]` — a step the executing agent may not be able to run at all.

### 10. Two copies of the enabled list will disagree in practice

The enabled list lives in each machine's home folder. A laptop, a desktop, and every cloud machine each need their own "enable CORE here". The plan treats cloud sessions as files-only rather than solving this. For a user who lives in cloud sessions, CORE 4 is mostly Layer 1.

### 11. It removes things the owner uses

The swarm review, the HTML memory view, date-based queries, generated wikilinks, wrapper seams. Each is listed as "removed" with no replacement. For the person who used them, each is a loss.

### 12. The budget invites cutting error handling

Fifteen commands, three hook dialects, a watcher, a self-test with ten planted items, a migration, a sampler — in 1,800 lines. A tight budget pushes toward dropping the careful handling that the defect class punishes.

## Part 2 — What a professional would ask

| # | Question | The plan's answer today |
|---|---|---|
| 1 | **What is your write policy?** | The agent decides, guided by one test: would this change what you say or build in six weeks? Decisions, risks, commitments, open questions, people; never secrets, raw outside text, or opinions about people. Agent-chosen writes beat per-turn extraction in the research [G 5.3]. |
| 2 | **How do you stop duplicates?** | Search the index and archive before writing; update the same fact, supersede a changed one. `check --project` fails on a replaced memory still active and warns on near-duplicate summaries. Paraphrased duplicates with different wording are not caught. |
| 3 | **What is your decay rule?** | No formula. `pulse` *proposes* archiving only stale-prone kinds (observations, review notes, explainers) unchanged and never pointed to for 90 days. Decisions in force, people, principles, open risks, and open questions are never proposed. The user approves. |
| 4 | **How do you handle a fact that changed?** | Replace and archive. One live version per fact; a check fails if two are live. |
| 5 | **What are your retrieval precision and recall?** | Measured at build time on a 30-query gold set with 10 held out, by kind. Paraphrase recall is expected to be poor and is reported. **No real-world number yet.** |
| 6 | **What is the context budget?** | 400 tokens always on (skill listing); about 4,000 at session start (skill body, brief, status); up to 1,000 bytes per prompt on a match. CORE 3: about 32,000 at start. |
| 7 | **What does a cold start cost?** | A new project: the user says "set up CORE here"; the skill creates the brief and folders. Nothing is said until there is something to say. |
| 8 | **What is the token cost per session?** | About 4,000 at start plus pointers. **Not measured** until built. |
| 9 | **What happens at 10,000 sessions?** | Receipts are pruned at 30 days. The archive grows and is never read by default. The active set is held near 300 by proposals. The index is rebuilt by hashing every active file; untested past 500. |
| 10 | **How do you know it helps?** | Four arms on Claude Code (plugin, convention, files, nothing) and a ten-session record test. Codex and Antigravity are inferred, not measured. |
| 11 | **What would make you kill it?** | Layer 2 is dropped if it fails both tests. Layer 1 stays. |
| 12 | **What is your no-memory baseline?** | The "nothing" arm. |
| 13 | **How do you keep the judge honest?** | Planted-fact text checks first; judge rubrics written as pass/fail; blind packs with ids stripped, judged twice in different orders. **Not done:** checking the judge against human labels. |
| 14 | **How do you handle poisoned memory?** | Nothing reaches the agent from a project not enabled on this machine; hooks pass pointers, not bodies; `said_by` on every memory; the refresh helper has no shell. One "yes" opens the gate, and people approve most prompts. |
| 15 | **What does an unattended run do?** | Only runs CORE schedules are marked unattended; those write proposals only. Other headless runs are treated as the user's. |
| 16 | **What is your concurrency story?** | One fact per file; atomic writes; date ids; index not committed. Last writer wins on a single file. |
| 17 | **How do you roll back?** | Tag `v3.20.1`; `migrate` refuses an uncommitted store and needs `--no-git` plus a backup warning outside git. |
| 18 | **What do you log?** | One receipt per hook call and per check: time, event, session, status, counts, the memory ids pointed to. Never prompt or memory text. Pruned at 30 days. |
| 19 | **How do I debug a missed recall?** | `core.mjs recall --prompt "…"` shows what matched; `metrics` shows whether the hook ran and how often it offered pointers. |
| 20 | **What breaks when a harness changes?** | That harness's hook file. CORE drops to skills-only and, if the block is installed, says so. |
| 21 | **Who is the second maintainer?** | Nobody. |
| 22 | **Why not embeddings?** | No measured miss yet that needs them, and an index that goes stale. Paraphrase recall is the place to watch. |
| 23 | **How is focus measured?** | Planted due items among distractors; a reminder suppressed when snoozed. Whether the user *felt* less loaded is **not measured**. |
| 24 | **Does the brief itself help?** | Unknown. Always-loaded context files raised cost about 20% without a reliable gain in one study [G 5.1]. The four arms will show it. |

## How the review was run

- **Reviewers.** Each round, seven fresh agents — fact-checker, gap auditor, harness auditor, practitioner, executor, premise attacker, reader — each given only the file paths and `reviewer-brief.md`, never the drafting agent's reasoning. No reviewer reviewed its own text.
- **Defence.** The drafting agent ruled on every finding. Partial rebuttals went back to the reviewer who raised them; a dispute went to a fresh judge agent.
- **A note on models.** At the user's request the model was changed partway through grounding. Every reviewer and judge ran on the model the user chose; research agents still unfinished at the switch were relaunched on it.
- **Raw files.** `round-<n>/<reviewer>.md` holds each review; `round-<n>/defence.md` holds the rulings and the fix list; `round-1/judge-PA-03.md` holds the one judge ruling.

## Alternatives considered and rejected

- **One reviewer instead of seven.** One reader anchors on the first problem found. Seven with different mandates do not share blind spots.
