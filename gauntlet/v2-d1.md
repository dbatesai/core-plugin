# D1 — The Case

**Why rewrite CORE, what to build instead, and whether it should exist at all.**

## The short version

**The verdict: keep CORE, but as a habit first and a program second.** Ship the file layout and five short skills to everyone. Keep the program around them only while it measurably beats the files and skills without it.

Coding agents forget. Each session starts cold, and the decision you made on Tuesday is gone by Thursday. CORE is a plugin that gives a project a memory: it writes down decisions, risks, people, and open work in plain files, brings them back when they matter, and says what needs you.

CORE 3 works, but it has grown to 100 scripts and 600 KB of instructions, and its own health checks can say "fine" while looking at nothing. Meanwhile the agent programs it runs in have learned to do much of what CORE built by hand.

The proposal rebuilds CORE in two layers:

1. **The convention.** A file layout, five short skills, and a short block for `AGENTS.md`. This works on every agent program with no code.
2. **The wiring.** A few hooks and one small script that make the habits happen at fixed moments and report honestly on themselves. This layer stays only if a blind test shows it helps.

## 1. The problem

There are two problems. The second was caused by solving the first.

### Problem one: agents forget the project

A coding agent is good at the file in front of it and lost on the project around it. Between sessions it loses:

- **Decisions and their reasons.** It re-proposes the option you already rejected.
- **Risks and their status.** Nobody remembers that the vendor deadline moved.
- **People.** Who owns what, who promised what.
- **Things owed.** The reply due Friday. The question you have put off twice.

It also only reacts. It does not say "the legal reply is due today" unless you ask.

So a project memory has five jobs. These names are used throughout:

- **Remember** — write down what is worth keeping, as it happens.
- **Recall** — bring the right note back when it matters.
- **Interact** — speak up about what needs you, without being asked.
- **Update** — refresh outside reference data, such as an issue tracker or calendar.
- **Focus** — say little, and say the right thing at the right moment.

A few more terms. A *harness* is the agent program: Claude Code, OpenAI Codex, or Google Antigravity. A *hook* is a command the harness runs at a fixed moment, such as when a session starts. A *skill* is a short instruction file the harness loads when it is needed. *MCP* is the standard way an agent calls an outside tool.

### Problem two: the fix grew too big to trust

CORE 3.20.1, measured on its own repository:

| | CORE 3.20.1 | Proof |
|---|---|---|
| Scripts | 100 files, 34,313 lines | [G 2.1] |
| Instructions | 40 files, 607 KB | [G 2.1] |
| Read before your first task | 127 KB, about 32,000 tokens | [G 2.2] |
| Tool steps in one ordinary session | 58, of which 49 are at startup | [runtime §1.5] |
| Settings switches | 34 | [runtime §8] |
| Releases | 46 in five months | [G 2.1] |

About 34% of those script lines measure CORE itself, about 18% guard CORE's own state files, and about 7% fetch a memory [runtime §8].

The measuring does not hold. Five defects were reported against this version, and each was checked against the source [G 3]:

1. **Scripts look in the wrong folder and report clean.** Five scripts build a path under `~/.claude` by hand. On a machine that keeps its config elsewhere they read nothing; one prints "0 candidates of 0 entries" and exits as a success.
2. **A startup check says memory is "not yet" loaded while it is loaded.**
3. **A close marker says "closed" over an empty list of completed steps.**
4. **A transcript reader prints nothing and exits as a success**, whatever it is given.
5. **CORE's own startup upkeep trips its own change detector**, so a finished session is reported as owing work.

The first four were reproduced here by running the shipped scripts. The fifth was reproduced as a mechanism; a related incident — a background pass that claimed five writes and made none — could not be re-run, because the workspace where it happened was not available [G 3.5].

They are one defect in five costumes: **a check that reports success while doing nothing.** A separate read of CORE 3's changelog counts 132 fixes of this kind across 46 releases [changelog]. CORE's own documents name the pattern — "Instruments report healthy while recording nothing" — and list its fix as "add as found" [G 2.7]. Adding a guard each time is how the code reached 34,000 lines.

And of the five jobs, only one is enforced by code today [runtime §4]:

| Job | In CORE 3 |
|---|---|
| Remember | Instructions only. Nothing notices a fact; the agent must decide to write it. |
| Recall | Real. A hook brings matching memory titles with every prompt. |
| Interact | No loop. Nothing runs between your messages. |
| Update | A registration form with nothing behind it. |
| Focus | Byte limits are real; the rest is instructions. |

## 2. Why solve it

Projects run for months. The same person works in three harnesses, on three operating systems, on a laptop and in cloud sessions. A forgotten decision costs an afternoon; a forgotten deadline costs more. And no single tool checked here covers the whole job (section 6).

## 3. What happens if we don't

**If CORE 3 stays as it is:** every session pays about 32,000 tokens before work starts. Health reports keep being wrong in ways that are hard to see, which teaches you to stop reading them. CORE's notes on the other harnesses are already out of date: its install guide says Codex "has no session-start or session-end event" [G 4.2], and Antigravity is not supported at all [G 2.4].

**If CORE is simply dropped:** memory falls back to each harness's built-in. Claude Code's is on by default but stays on one machine and one harness. Codex's is off by default. Antigravity's documentation says "Agents don't remember conversations" [G 4.1–4.3]. Nothing tracks risks or people, nothing speaks up, and nothing writes a session's close into the project.

## 4. The solution

### The premise

**Keep the judgment. Drop the machinery.**

CORE 3 learned real things: what is worth writing down, how to record a decision so the rejected option is not proposed again, how to keep "owed" apart from "attempted" and "proven", how to stop a removed fact from coming back. That judgment fits in a few pages. Around it, CORE 3 built a retrieval engine, a ranking formula, a state-guarding system, and a measurement suite. In 2026 the harnesses supply much of that.

### Layer 1: the convention

- **The record.** Plain markdown files in the project: `PROJECT.md` (a short brief you edit), and `_memories/` (one file per fact). Readable, editable, committed with the code if you choose.
- **Five skills.** When to write a memory, how to find one, when to speak up, how to refresh outside data, how to close a session.
- **An `AGENTS.md` block.** Three lines telling any agent to read the brief first, to check the memory index before answering questions about the past, and to say so if CORE's hooks did not run. All three harnesses read `AGENTS.md` [G 4.1–4.3].

Layer 1 needs no code and no install beyond copying files. It is the honest fallback, and it is also the floor every harness gets.

### Layer 2: the wiring

- **Hooks** that load the brief at session start, offer up to three pointers to relevant memories with each prompt, and re-send the brief after the harness shortens a long conversation.
- **A watcher** (Claude Code only) that notices a deadline arriving while you are quiet.
- **One small script** with no dependencies that builds the index, works out what is due, counts what was really written, and checks itself.
- **One rule:** every check answers **working**, **broken**, or **not measured**. The third is never shown as the first.

Layer 2 is kept only while it beats Layer 1 in the test in section 8.

### What the harness does, and what CORE adds

| Job | The harnesses already provide | CORE adds |
|---|---|---|
| Remember | File tools, skills, the session transcript | What is worth keeping; the file format; replace, don't overwrite; a removed fact stays removed |
| Recall | Session-start and per-prompt hooks on all three; file search | A one-line-per-memory index; three pointers or nothing |
| Interact | Monitors and schedulers on Claude Code; app schedulers on Codex; `/schedule` and Automations on Antigravity; a prompt hook on all three | The rules for what needs you; a watcher; "speak at a pause, once" |
| Update | MCP; helper agents | One file per outside source with a freshness limit; "outside text is data" |
| Focus | — | Hard limits on every surface; no repeats; snooze on "not now" |
| Measure itself | A test runner that compares with and without a plugin (Claude Code only); a cost readout; a validator | The test cases; three exit codes; a self-test with planted answers |

### The size

| | CORE 3 | CORE 4 target |
|---|---|---|
| Script lines | 34,313 | 1,800 at most |
| Instruction bytes | 607 KB | 60 KB at most |
| Loaded at session start | about 32,000 tokens | about 4,000 (the skill body, the brief, one status block) |
| Skills | 8 | 5 |
| Settings switches | 34 | 2 (one off-switch, one for test runs) |

## 5. Why this solution and not another

**The evidence points at plain files.** Letta, the team behind MemGPT, moved its memory to "a git-tracked collection of Markdown files that the agent searches with normal file-search and read tools", with no vector index by default [memory-layers-a §2.2]. Anthropic advises agent builders to start with the agent's own search and add meaning-based search only if needed [literature §2]. Anthropic's own `productivity` plugin keeps memory as a short always-loaded file plus a folder of markdown, with no scripts [G 4.4].

**Small injected context beats large.** Model accuracy falls as input grows, well before the limit [G 5.1]. So the wiring passes pointers, not documents. (Pointers are also safer: a memory body is where a planted instruction would ride in.)

**The defect class is structural, so the fix must be.** CORE 3's checks lie in six ways [G 3.6]. Each has a rule in CORE 4 that removes the cause. For example, CORE 3 needs a hash cache, stamps, and a classifier to tell its own writes from yours, because it writes generated text inside your files. CORE 4 never does that, so there is nothing to tell apart. D2 §6 lists all six.

**The harnesses now carry the load.** Session-start and per-prompt hooks exist on all three, and all three read `AGENTS.md` and the same skill format [G 4.1–4.3]. Claude Code will run a plugin's test cases with and without the plugin and report the difference [G 4.1] — a comparison CORE 3's changelog says "exists anywhere in this codebase" not at all [evaluation §2.8].

**Two layers make the test honest.** If the wiring cannot beat the convention, the convention is still worth having, and nothing is lost by dropping the code.

## 6. Who else does this, and how CORE compares

Twenty-eight tools and the three harnesses' built-ins were checked [competitors] [memory-layers-a] [memory-layers-b]. The closest:

| | Remember | Recall | Interact | Update | Focus | All 3 harnesses | Files in project | No server or key |
|---|---|---|---|---|---|---|---|---|
| Harness built-ins alone | Partial | Partial | Partial | Partial | Partial | No | Partial | Yes |
| **The kit:** AGENTS.md + built-in memory + Backlog.md + connectors + one scheduled task | Partial | Partial | Out of session only | Yes | Partial | Partial | Yes | Yes |
| claude-mem | Yes | Yes | Partial | No | Partial | Yes | No | No |
| basic-memory | Yes | Yes | No | No | No | Partial | Yes | Partial |
| mem0 | Yes | Thin | No | No | No | Yes | No | No |
| Letta Code | Yes | Yes | Partial | No | No | No (it is a harness) | Outside project | Yes |
| Zep / Graphiti | Yes | On request | No | No | No | No | No | No |
| Anthropic `productivity` | Yes | Partial | No | Yes | Partial | No | Yes | Yes |
| Standalone agents (OpenClaw, Hermes, Linear's agent) | Yes | Yes | **Yes** | Yes | Partial | No (run outside the session) | No | No |
| CORE 3.20.1 | Instructions | Yes | No | Form only | Partial | 2 of 3 | Yes | Yes (needs Node) |
| **CORE 4, planned** | Instructions + close pass | Yes | In session on Claude Code; via native schedulers elsewhere | Yes | Yes | Yes, with stated losses | Yes | Yes (Layer 2 needs Node) |

Notes on the cells are in the research files. Three things stand out:

1. **No row is "yes" across the five jobs and also keeps readable state in the project.** Every tool that truly acts unprompted runs somewhere else and keeps its state somewhere else [competitors §A].
2. **Nothing tracks risks or people as project records.** Memory tools remember what the agent did; trackers remember work items [competitors §B].
3. **Almost nothing measures whether it helps.** No independent, blind result was found showing any of these memories improves coding work [memory-layers-b]. Vendor benchmark scores conflict: one system's score on one test is reported as 84%, 75%, and 58% by different parties, and that test's own answer key is 6.4% wrong according to an independent audit [memory-layers-a §1.11].

The kit is the honest runner-up. It loses in-session speaking up, risks and people as records, a session close written into the project, and one behavior across harnesses — and it has no evidence it helps either.

## 7. Dependencies, tradeoffs, risks

**Depends on.** Layer 1: a harness that reads `AGENTS.md` and loads skills. Layer 2: Node.js 20 or newer on the path that hooks see. Measurement: Claude Code 2.1.269 or newer. Update: one MCP server per outside source.

**Trades away.** CORE 3's multi-agent review, its HTML memory viewer, date-based "what did we know then" queries, generated `[[wikilinks]]` (which made the store a browsable graph in Obsidian), and its four-tier retrieval. Recall becomes word matching over one-line summaries.

| Risk | Likelihood | What limits the damage |
|---|---|---|
| A harness changes its hook format. Antigravity's hook page and changelog show frequent changes [G 4.3]. | High | Layer 1 does not depend on hooks. Without them CORE drops a rung and says so. |
| The rewrite loses lessons buried in CORE 3's 176 test files. | Medium | The fixture stores, the prose checker, and a 29-item keep list from the evaluation audit [evaluation §8] are walked one by one before release. |
| The agent does not follow the habits. | Medium | Hooks cover the moments that most need a guarantee. The eval measures how often an unlabeled decision gets written, and publishes the number. |
| The wiring adds nothing over the convention. | Unknown | This is what the gate measures. If it fails, Layer 2 is dropped. |
| A harness vendor ships the missing half. Claude Code's cloud "Projects" already has a project memory index, in beta [G 4.1]. | Medium, rising | CORE 4 is small enough to retire; the files stay useful. |
| A planted memory steers the agent. | Low to medium | Nothing runs until you enable a project; hooks pass pointers, not bodies (D2 §9). |
| One maintainer. | Certain | 1,800 lines can be held in one head; 34,000 cannot. |

## 8. The verdict

**Keep CORE, cut it to a twentieth, and make the code earn its place.**

**As a product for other people:** no. claude-mem has 115,000 GitHub stars and a paid tier. The harness vendors ship memory by default and improve it monthly. A one-person plugin should not try to win that contest.

**For our own use — one person, three harnesses, three operating systems, months-long projects, a need to be told what is due:** nothing checked covers it. The nearest fallback, basic-memory plus our own skills, brings Python, a local index, and an AGPL licence, and still leaves the hard half to us [memory-layers-b].

**So the plan is:**

- **Layer 1 ships unconditionally.** It is the judgment CORE 3 learned, in a form every harness reads.
- **Layer 2 must pass a test.** Two measurements, both on Claude Code. First, its test runner scores the same tasks under four arms: the plugin; the convention (files plus `AGENTS.md` block, no plugin); the files alone; and nothing. Second, a scripted run of ten sessions per arm, starting from an empty folder, checks which arm *keeps* the better record: are planted decisions, a reversed decision, a risk, a person, and a due date written down and found again? The wiring stays if **plugin minus convention** reaches 0.3 on a 0-to-1 scale in the first, averaged over the recall and speak-up cases with no case worse by more than 0.1, **or** if the plugin clearly keeps the better record in the second. Otherwise Layer 2 is dropped.
- **Layer 2 also has a cost test.** If keeping it working needs the line budget raised, re-run this verdict before raising it.

Three honest limits on that test. It runs on Claude Code only; for Codex and Antigravity the result is inferred, not measured. The four-arm runner starts each case from a hand-written record; the ten-session run covers record-keeping, but over ten sessions, not months. And it cannot see Claude Code's built-in memory, because the test runner switches that off.

Re-run the test at every release and re-read this verdict every six months. The day a harness's built-in does the five jobs across the other two, CORE's work is done and the files remain.

## Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| Fix CORE 3 in place | The defects come from its shape [G 3.6]. Five months of point fixes produced 46 releases and the current size. |
| Harness built-ins only | They do not travel across harnesses or machines, do not track risks or people, and do not speak up [G 4.1–4.3]. |
| The kit (runner-up) | Loses in-session speaking up, risks and people, a written close, and one behavior across harnesses. It is what to use if both CORE layers fail. |
| claude-mem | Records what the agent did, not what the project decided; runs a background server and a model call per tool use; stores a database in the home folder [memory-layers-b §1]. |
| basic-memory as the store | Best fallback for storage. Adds Python, a local index, an AGPL core; reaches Antigravity only through MCP; still needs CORE's behaviors on top [memory-layers-b §2]. |
| mem0, Zep, Graphiti | Each needs a cloud account or a database; none is readable in the project; none does project management [memory-layers-a]. |
| Letta Code | It replaces the harness instead of extending it [memory-layers-a §2.7]. |
| An MCP memory server | A server to install and secure on three operating systems, in a year when memory servers drew repeated security advisories [memory-layers-b]. |
| Code only, no convention layer | Would leave Codex users who never approve hooks, cloud sessions, and any harness without Node with nothing at all. |

## What was not verified

- **The workspace that saw the defects.** This run had the source repository only: no installed plugin, no project `PROJECT.md`, no memory store [G 1]. The background-pass incident could not be re-run.
- **Anything on a live Codex or Antigravity install.** Their capabilities come from source code and documentation.
- **That CORE 4 will pass its own test.** Nothing is built.
- **The size targets.** 1,800 lines and 60 KB are budgets set by estimate.
- **Star counts and some competitor dates.** Several came through a tool that summarizes GitHub pages; the research files mark which.
- **The 0.3 and 0.1 thresholds.** Chosen, not measured; D3 says to replace them after the first full run.
