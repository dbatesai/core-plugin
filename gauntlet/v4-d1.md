# D1 — The Case

**Why rewrite CORE, what to build instead, and whether it should exist at all.**

## The short version

**Verdict: rebuild CORE for its owner's own use, not as a product, at a fraction of its size. Each part ships only if it beats the thing below it. The test of whether CORE should exist runs before any hook or script is written.**

Coding agents forget. Each session starts cold, and the decision you made on Tuesday is gone by Thursday. CORE is a plugin that gives a project a memory: it writes down decisions, risks, people, and promises in plain files, brings them back when they matter, and says what needs you.

CORE 3 works, but it has grown to 100 scripts and 600 KB of instructions, and its health checks can say "fine" while looking at nothing. Meanwhile the agent programs it runs in now do much of what CORE built by hand.

The proposal rebuilds CORE in two layers:

1. **Layer 1, the skills.** A file layout, five short skills, and a three-line block. No code needed; a small script ships alongside to check CORE and work out what is due.
2. **Layer 2, the hooks.** They make the habits happen at fixed moments. Each ships only if it helps.

---

## 1. The problem

There are two problems. The second was caused by solving the first.

### Problem one: agents forget the project

A coding agent is good at the file in front of it and lost on the project around it. Between sessions it loses:

- **Decisions and their reasons.** It re-proposes the option you already rejected.
- **Risks and their status.** Nobody remembers that the vendor deadline moved.
- **People.** Who owns what, who promised what.
- **Promises.** The reply due Friday. The question you have put off twice.

It also only reacts. It does not say "the legal reply is due today" unless you ask.

So a project memory has five jobs:

- **Remember** — write down what is worth keeping, as it happens.
- **Recall** — bring the right note back when it matters.
- **Interact** — speak up about what needs you, without being asked.
- **Update** — refresh outside reference data, such as an issue tracker or calendar.
- **Focus** — say little, and say the right thing at the right moment.

A *harness* is the agent program: Claude Code, OpenAI Codex, or Google Antigravity. A *hook* is a command the harness runs at a fixed moment, such as when a session starts. A *skill* is a short instruction file the harness loads when it is needed. *MCP* is the standard way an agent calls an outside tool.

### Problem two: the fix grew too big to trust

CORE 3.20.1, measured on its own repository:

| | CORE 3.20.1 | Proof |
|---|---|---|
| Scripts | 100 files, 34,313 lines | [G 2.1] |
| Instructions | 40 files, 607 KB | [G 2.1] |
| Read before your first task | 127 KB, about 32,000 tokens | [G 2.2] |
| Tool steps in one ordinary session | 58, of which 49 are at startup | [runtime §1.5] |
| `CORE_*` settings | 34 names, 31 read from the environment | [runtime §8] |
| Releases | 46 in five months | [G 2.1] |

About 34% of those script lines measure CORE itself, 18% guard its own state files, and 7% fetch a memory [runtime §8].

The measuring does not hold. Five defects were reported against this version, and each was checked against the source [G 3]:

1. **Scripts look in the wrong folder and report clean.** Five scripts hard-code a path under `~/.claude`. Where the config lives elsewhere they read nothing; one prints "0 candidates of 0 entries" and exits as a success [G 3.1].
2. **A startup check says memory is "not yet" loaded while it is loaded** [G 3.2].
3. **A close marker says "closed" over an empty list of completed steps** [G 3.5].
4. **A transcript reader prints nothing and exits as a success**, whatever it is given [G 3.3].
5. **CORE's own startup upkeep trips its own change detector**, so a finished session is reported as owing work [G 3.4].

All five were reproduced here by running the shipped scripts. A related incident, a background pass that claimed five writes and made none, was confirmed as a mechanism only [G 3.5].

They are one defect in five costumes: **a check that reports success while doing nothing.** CORE 3's changelog holds 132 fixes of this kind across 46 releases [changelog §2.2]. CORE's own documents name the pattern — "Instruments report healthy while recording nothing" — and list its fix as "add as found" [G 2.7]. Adding a guard each time is how the code reached 34,000 lines.

Of the five jobs, only recall is enforced by code today, by a hook on every prompt. Remember is instructions only. Nothing runs between your messages to interact. Update is a form with nothing behind it. Focus has byte limits; the rest is instructions [runtime §4].

## 2. Why solve it

Projects run for months. The same person works in three harnesses, on three operating systems, on a laptop and in cloud sessions. A forgotten decision costs an afternoon; a forgotten deadline costs more. And no single tool checked here covers the whole job (section 6).

## 3. What happens if we don't

**If CORE 3 stays as it is:** every session pays about 32,000 tokens before work starts. Health reports keep being wrong in ways that are hard to see, which teaches you to stop reading them. Its notes on other harnesses are stale: its install guide says Codex "has no session-start or session-end event" [G 4.2], and it does not support Antigravity [G 2.4].

**If CORE is simply dropped:** memory falls back to each harness's built-in. Claude Code's is on by default but stays on one machine and one harness. Codex's is off by default. Antigravity's documentation says "Agents don't remember conversations" [G 4.1–4.3]. Nothing tracks risks or people, nothing speaks up, and nothing writes a session's close into the project.

## 4. The solution

### The premise

**Keep the judgment. Drop the machinery.**

CORE 3 learned real things: what is worth writing down, how to record a decision so the rejected option is not proposed again, how to keep "owed" apart from "attempted" and "proven", how to stop a removed fact from coming back. That judgment fits in a few pages. The harnesses now supply much of the machinery CORE 3 built around it.

### Layer 1: the skills

- **The record.** Plain markdown files in the project: `PROJECT.md` (a short brief you edit), and `_memories/` (one file per fact). Readable, and committed with the code if you choose.
- **Five skills:** `core` (the brief, and when to speak up), `remember` (write, replace, or close a memory), `pulse` (what is due or stale; refresh outside data), `finalize` (close a session), and `metrics` (check CORE itself). None needs the script. Claude Code gets them from the plugin. For Codex and Antigravity, setup offers to commit one copy to `.agents/skills/`, which both read [codex §3] [antigravity §4].
- **A three-line block:** read the brief first; look in `_memories/` before answering about the past; write down what a later session will need and the code will not show. It goes where each harness always reads it: `.claude/rules/core.md` on Claude Code, `.agents/rules/core.md` on Antigravity, and `AGENTS.md` on Codex [claude-code §1] [antigravity §2] [codex §1].

Layer 1 needs no code. Claude Code cloud sessions and cloud scheduled tasks never load plugins or `.agents/skills/` [claude-code §8, §12]. There the floor is the record and the block — a write rule, but no replace rule, no close, no speaking up — unless you enable the five skills on your claude.ai account, which setup offers.

**The script ships with Layer 1.** One small file with no dependencies that builds the index, works out what is due (models misjudge dates), moves CORE 3 stores, and checks itself.

### Layer 2: the hooks

- **A session-start hook** loads the brief and what is due, and re-sends them after the harness shortens a long conversation.
- **A prompt hook** offers up to three memory pointers per prompt (per model call on Antigravity, where CORE marks each turn's start [antigravity §6]).
- Hooks run only in *enabled* projects, where you have said "Enable CORE here" on this machine. So a planted memory in a cloned repository cannot reach the agent through a hook.

Two rules cover both layers.

- **Every check answers working, broken, or not measured**, and the third is never shown as the first. A session's writes are counted from disk, by id, and its close receipt says how it closed.
- **"Not measured" never ships.** A part whose test could not run counts as not kept.

### What the harness does, and what CORE adds

| Job | The harnesses already provide | CORE adds |
|---|---|---|
| Remember | File tools, skills, the session transcript | What is worth keeping; the file format; replace, don't overwrite; a removed fact stays removed |
| Recall | Session-start and prompt-time hooks on all three; file search | A one-line-per-memory index; three pointers or nothing |
| Interact | Scheduled tasks on all three (`/loop` on Claude Code, Automations on Antigravity); prompt-time hooks | What needs you; "speak at a pause, once"; one prompt each scheduler can run |
| Update | MCP; helper agents | One file per outside source with a freshness limit; "outside text is data" |
| Focus | — | Hard limits on every surface; no repeats; snooze on "not now" |

### The size

| | CORE 3 | CORE 4 limit (checked after the build) |
|---|---|---|
| Script lines | 34,313 | 1,800 at most, hooks included |
| Instruction bytes | 607 KB | 60 KB at most |
| Loaded at session start | about 32,000 tokens | about 4,000 (estimate) |
| Skills | 8 | 5 |
| Settings | 34 `CORE_*` names | 2 environment switches and 4 project settings |

One rule for the budget: if the hooks need more than 1,800 lines, they are shelved.

## 5. Why this solution and not another

**The evidence points at plain files.** Letta, the team behind MemGPT, moved its memory to "a git-tracked collection of Markdown files that the agent searches with normal file-search and read tools", with no vector index by default [memory-layers-a §2.2]. Anthropic advises agent builders to start with the agent's own search and add meaning-based search only if needed [literature §2]. Anthropic's `productivity` plugin keeps memory as one short always-loaded file plus a markdown folder, with no scripts [G 4.4].

**Small injected context beats large.** Model accuracy falls as input grows, well before the limit [G 5.1]. So the hooks pass pointers, not documents.

**The defect class is structural, so the fix must be.** CORE 3's checks lie in six ways [G 3.6]. Each has a rule in CORE 4 that removes the cause. For example, CORE 4 never writes generated text inside your files, so it needs no hash cache, stamps, or classifier to tell its writes from yours. D2 §6 lists all six.

**The harnesses now carry the load.** All three have session-start and prompt-time hooks, load the same skill format, and read a project rules or instruction file [G 4.1–4.3]. Claude Code will run a plugin's test cases with and without the plugin [G 4.1]. CORE 3 never ran that comparison: "no matched memory-on/off comparison exists anywhere in this codebase yet" [evaluation §2.8].

## 6. Who else does this, and how CORE compares

Twenty-eight tools and the three harnesses' built-ins were checked [competitors] [memory-layers-a] [memory-layers-b]. The closest:

| | Remember | Recall | Interact | Update | Focus | All 3 harnesses | Files in project | No server or key |
|---|---|---|---|---|---|---|---|---|
| Harness built-ins alone | Partial | Partial | Partial | Partial | Partial | No | Partial | Yes |
| Claude Code Projects (beta) | Yes | Yes | Out of session only | Yes (account connectors) | Not checked | No | No | No (cloud, paid plan) |
| **The kit:** built-in memory + the three-line block + Backlog.md + connectors + one scheduled task | Partial | Partial | Out of session only | Yes | Partial | Partial | Yes | Yes |
| claude-mem | Yes | Yes | Partial | No | Partial | Yes | No | No |
| basic-memory | Yes | Yes | No | No | No | Partial | Yes | Partial |
| mem0; Zep / Graphiti | Yes | Thin or on request | No | No | No | mem0 only | No | No |
| Letta Code | Yes | Yes | Partial | No | No | No (it is a harness) | Outside project | Yes |
| Anthropic `productivity` | Yes | Partial | No | Yes | Partial | No | Yes | Yes |
| Standalone agents (OpenClaw, Hermes, Linear's agent) | Yes | Yes | **Yes** | Yes | Partial | No (run outside the session) | No | No |
| CORE 3.20.1 | Instructions | Yes | No | Form only | Partial | 2 of 3 | Yes | Yes (needs Node) |
| **CORE 4, planned** | Instructions + close pass | Yes | Hooks at session start and each prompt; native schedulers | Yes | Yes | Yes, with stated losses | Yes | Yes (code needs Node) |

*Partial*: does some of the job — only when asked, on one harness or machine, or for some kinds of fact. CORE 4's Interact cell assumes the hooks are kept; without them, CORE speaks up only when a skill runs.

Three things stand out:

1. **No row is "yes" across the five jobs and also keeps readable state in the project.** Every tool that truly acts unprompted runs and keeps its state somewhere else [competitors §A].
2. **Nothing tracks risks or people as project records.** Memory tools remember what the agent did; trackers remember work items [competitors §B].
3. **Almost nothing measures whether it helps.** No independent, blind result was found showing any of these memories improves coding work [memory-layers-b]. Vendor scores conflict: one system's score on one test is reported as 84%, 75%, and 58% by different parties [memory-layers-a §1.11].

**Claude Code Projects** is the closest native rival: one harness, a paid beta, memory outside the repository. A Projects thread loads CORE's skills if CORE is added in Project settings > Plugins; hooks do not run there [claude-code §8]. So CORE works inside Projects, adding the record in the repository, risks and people, a written close, and the same habits on the other harnesses.

**The kit** is the honest runner-up. It loses speaking up inside a session, risks and people as records, a written close, and one behavior across harnesses. Its memory part, built-in memory plus the same three lines, is what Layer 1 must beat (section 8).

## 7. Dependencies, tradeoffs, risks

**Depends on.** Layer 1: a harness that loads skills and reads a project rules or instruction file. On Claude Code the block gets its own rules file, because any `CLAUDE.md` or `CLAUDE.local.md` in or above the folder stops Claude Code reading `AGENTS.md` [claude-code §1]. Codex skips `AGENTS.md` in an untrusted project and cuts project files past 32 KiB [codex §1]. The script and hooks: Node.js 20 or newer on the hooks' path. Measurement: Claude Code 2.1.269 or newer and a paid account. Update: one MCP server per outside source.

**Trades away.** CORE 3's multi-agent review, its HTML memory viewer, date-based "what did we know then" queries, generated `[[wikilinks]]`, and its four-tier retrieval. Recall becomes word matching over one-line summaries.

| Risk | Likelihood | What limits the damage |
|---|---|---|
| A harness changes its hook format, as Antigravity's often does [G 4.3]. | High | Layer 1 does not depend on hooks. The prompt hook prints a line every time, so a dead one shows. |
| The rewrite loses lessons buried in CORE 3's 176 test files. | Medium | The fixture stores, the prose checker, and a 29-item keep list [evaluation §8] are walked one by one before release. |
| The agent does not follow the habits, or writes too much. | Medium | The record test counts facts written, junk, duplicates, and stale copies. An arm with more stale or duplicate copies than the arm it beats is not kept. |
| A vendor ships the missing half, as Claude Code Projects has begun to [claude-code §8]. | Medium, rising | Kill test 1 includes built-in memory and is re-run often (section 8). The files stay useful. |
| A planted memory steers the agent. | Low to medium | Hooks act only in enabled projects and pass pointers, not bodies; skills never run code from the project (D2 §9). |
| One maintainer. | Certain | 1,800 lines can be held in one head; 34,000 cannot. |

## 8. The verdict

**Verdict: rebuild CORE for its owner's own use, not as a product, at a fraction of its size. Each part ships only if it beats the thing below it. The test of whether CORE should exist runs before any hook or script is written.**

**As a product for other people: no.** claude-mem has 115,000 GitHub stars and a paid tier, and the harness vendors ship memory by default and improve it monthly. A one-person plugin should not enter that contest.

**For the owner's own use — one person, three harnesses, three operating systems, months-long projects, a need to be told what is due:** nothing checked covers it. The kit and Claude Code Projects each cover part (section 6).

**How each part earns its place.** Two tests, both on Claude Code. An *arm* is one setup the same tasks run under.

- **The record test.** Ten scripted sessions from an empty folder, three turns each, six repetitions per arm. Tasks plant five facts — a decision, its reversal, a risk, a person, a due date — and five probes ask for them. A blind grader scores answers against a key written in advance. Every arm has auto memory on, as shipped: **built-in** (nothing else; reported, not ruled on, since the kit contains it), **kit** (plus the same three-line block, no skills), **layer 1** (kit plus the five skills), and **full** (layer 1 plus the hooks).
- **The eval.** Claude Code's test runner scores fixed cases 0 to 1, ten runs per arm. Arms: full, **full, recall off** (session-start hook only), layer 1, **files** (the record alone), and **nothing**. Its gate: of three cases where hooks can help, at least two ahead by 0.2, with a mean gap of 0.2; on two where they should not matter, none behind by more than 0.2.

**The kill test.** Its numbers are frozen before the first run and never tuned on it.

1. Layer 1 ships only if, on the ten-session record test, it beats **kit** on recall probes and on being told what is due, by a fixed margin, with a paired interval over 6 repetitions that excludes zero. Otherwise CORE does not ship; use the kit.
2. The session-start hook ships only if **full, recall off** beats layer 1 on the eval gate.
3. The prompt hook ships only if **full** beats **full, recall off** on the recall cases.
4. Any rule that cannot be measured counts as not kept. Shelved hooks go to a branch.
5. The script's self-audit commands (`check`, `selftest`, `metrics`), with `queue` and `migrate`, ship whenever Layer 1 ships.

**When it is known.** Right after the numbers are frozen, the five skills are written without the script and the built-in, kit, and layer 1 arms run. If layer 1 loses, the build stops there.

Three honest limits. Both tests run on Claude Code only; for Codex and Antigravity the result is inferred. Months of use are untested; the longest session is 25 turns, hence shelving. Six repetitions can miss a small real gain, but a gap whose interval includes zero counts as not kept, so too few runs can only make CORE lose.

Re-run the kill tests at every minor harness release or every six months, and re-read this verdict then.

## Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| Fix CORE 3 in place | The defects come from its shape [G 3.6]. Five months of point fixes produced 46 releases and the current size. |
| Harness built-ins only | They do not travel across harnesses or machines, track risks or people, or speak up [G 4.1–4.3]. Kill test 1 includes them. |
| The kit (runner-up) | Loses what section 6 lists. It is what to use if Layer 1 fails kill test 1. |
| Build everything, then test all hooks as one | The verdict would come after the work it judges, and a useful hook and a weak one would pass or fail together. |
| claude-mem | Records what the agent did, not what the project decided; runs a background server and a model call per tool use; stores a database in the home folder [memory-layers-b §1]. |
| basic-memory as the store | Best fallback for storage. Adds Python, a local index, an AGPL core; reaches Antigravity only through MCP; still needs CORE's behaviors on top [memory-layers-b §2]. |
| mem0, Zep, Graphiti | Each needs a cloud account or a database; none is readable in the project; none does project management [memory-layers-a]. |
| Letta Code | It replaces the harness instead of extending it [memory-layers-a §2.7]. |
| An MCP memory server | A server to install and secure on three operating systems, in a year when memory servers drew repeated security advisories [memory-layers-b]. |
| Code only, no Layer 1 | Would leave Codex users who never approve hooks, cloud sessions, and machines without Node with nothing. |

## What was not verified

- **The workspace that saw the defects.** This run had the source repository only: no installed plugin, no project `PROJECT.md`, no memory store [G 1]. The background-pass incident could not be re-run.
- **Anything on a live Codex or Antigravity install.** Their capabilities come from source code and documentation, including the `.agents/skills/` copy and whether Codex loads it in an untrusted project [codex §11].
- **That auto memory is on in every record-test arm.** A check before session 1 reads only the auto-memory folder, never transcripts. If it fails, that arm reads "not measured", which kill test 4 counts as not kept.
- **That CORE 4 will pass its own test.** Nothing is built.
- **The size limits.** 1,800 lines, 60 KB, and 4,000 tokens are estimates.
- **Star counts and some competitor dates.** Several came through a tool that summarizes GitHub pages; the research files mark which.
- **The kill-test numbers.** Chosen, not measured.
