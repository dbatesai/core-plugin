# D4 — The Critic Log

**The case against this plan, the questions a professional would ask, and every finding from the gauntlet.**

Draft v4 · 2026-11-09 · Companions: [D1 — The Case](v4-d1.md) · [D2 — The Machine](v4-d2.md) · [D3 — The Build](v4-d3.md) · Evidence: [grounding.md](grounding.md)

**In this document:** Part 1, the case against the plan · Part 2, what a professional would ask · how the review was run · Part 3, the gauntlet ledger, with every fix and every rebuttal · alternatives rejected · what was not verified.

This document does not defend the plan. Part 1 attacks the current draft (v4). Part 2 lists the questions a person who builds agent memory for a living would ask, with the plan's honest answer or "no answer yet". Part 3 records every finding the reviewers raised, what was done with it, and why. Part 3 can be read without opening any other file.

**Words used here.** *Layer 1* is the record, five skills, and a short block in the project's instruction file. *Layer 2* is the hooks. The script's self-audit commands ship with Layer 1. An *arm* is one setup the tests run the same tasks under. The record test has four, all with Claude Code's auto memory on: **built-in** (nothing else), **kit** (plus the same three-line block, no skills), **layer 1** (kit plus the five skills), **full** (layer 1 plus the hooks). The eval adds **full, recall off** (session-start hook only), **files** (the record alone), and **nothing**. *Enabled* means the user said "enable CORE here" on this machine; until then no hook passes project text to the agent.

## Part 1 — The case against this plan

Ranked. The first three are the ones most likely to sink it.

### 1. ★ The evidence costs money and comes from one harness

The record test (about 720 calls), the eval, and the CORE 3 comparison all spend model calls on one person's Claude Code account. A builder without one finishes the code and then reports "not measured" for every result that decides whether CORE should exist. Codex and Antigravity are never measured; their behaviour is inferred from Claude Code.

### 2. ★ The thresholds are guesses, frozen before any data

The hooks' gate needs 2 of 3 cases ahead by 0.2 and a mean gap of 0.2. Layer 1 must beat the kit by a fixed margin with an interval that excludes zero over six repetitions. These numbers are written down before the first run so the first run cannot set its own bar. That stops one kind of bias. It does not make the numbers right. A real but small gain will often read as "no difference shown", and the layer will not ship. The plan chose that error on purpose; it is still an error.

### 3. ★ Remembering still depends on the model choosing to remember

CORE 3's own records say in-flow writes get skipped "consistently". CORE 4's answer is a shorter skill, a write line in the block, a close pass, and a catch-up that proposes what was missed. None of these notices a decision when it happens. The record test measures the miss rate. Nothing in the design lowers it except brevity.

### 4. Recall is weaker on paraphrase, by design

CORE 4 matches a prompt against one-line summaries by shared words. A user who phrases a question differently from how the agent summarised the memory gets nothing. The paraphrase case is a must-not-lose check on the prompt hook. If word matching loses to an agent searching the folder itself, the prompt hook is shelved, for a reason embeddings might fix.

### 5. Layer 1 in the repo is a copy that can go stale

For Codex and Antigravity, setup commits the five skills to `.agents/skills/` (on Codex the user runs the copy command, because Codex's sandbox keeps `.agents` read-only). Nothing updates that copy when CORE changes. A check warns when the copy is older than the installed CORE, but only on a machine where CORE is installed. On a machine without it, an old copy runs silently. Where the plugin is also installed, the agent sees the same skill twice.

### 6. A dead CORE is loud only if the agent reads the block

The prompt hook now prints one line every turn, and the block tells the agent to say so when the line is missing. That works only if the line telling it to reached the model. That line lives in a per-machine file, because it is about the plugin, not the project. Codex skips `AGENTS.md` in an untrusted project. A user who declines it gets a silent CORE.

### 7. Codex drops to skills only after every update

Codex ties hook approval to a hash of the plugin's files. Every CORE release resets it. The user is told to re-approve once. A user who misses that runs on the lower rung until they notice.

### 8. The Antigravity half is written from documents alone

Its hook format is new, changes often, and fails silently. Its terminal sandbox hides the plugin folder from commands the agent runs, so agent-side commands fall back to Layer 1 behaviour there. The hook file and its JSON were written without a live install. Step 8.4 is the first contact, and it needs a machine with Antigravity.

### 9. The enabled list does not follow you

Each machine needs its own "use CORE here". Claude Code cloud sessions and cloud scheduled tasks never load plugins at all. They get the skills only if the user enables them on the claude.ai account, and a Projects thread gets them only if CORE is added in Project settings. Neither ever runs the hooks. For a user who lives in cloud sessions, CORE 4 is Layer 1 at best, and often just the files.

### 10. It removes things the owner uses

The swarm review, the HTML memory view, date-range queries, generated wiki links, and the background watcher. Each is removed with no replacement. For the person who used them, each is a loss.

### 11. The line budget invites cutting error handling

Thirteen commands, three hook formats, a self-test with planted faults, a migration, and a sampler, in 1,800 lines. If the hooks need more, they are shelved. A tight budget pushes toward dropping the careful handling the defect class punishes.

### 12. The kit arm is written by the plan's author

Kill test 1 pits Layer 1 against a three-line block the same author wrote. A sharper block, or a better-tuned auto memory, might match Layer 1 and kill CORE. A weaker one makes Layer 1 look good. The block is frozen with the gate, but nobody independent wrote it.

### 13. The build plan grew while the product shrank

D3 went from about 15,000 words in v2 to about 23,000 in v4. Every addition answers an accepted finding, mostly about making a test able to fail. The product it describes got smaller in each round: the watcher, `verify`, and one hook file went. But an executing agent now reads a document longer than CORE 3's startup context, and a long plan hides its own contradictions.

## How the review was run

- **Reviewers.** Each round, seven fresh agents — fact-checker, gap auditor, harness auditor, practitioner, executor, premise attacker, reader — each given only the file paths and `reviewer-brief.md`, never the drafting agent's reasoning. From round 2, each was told not to repeat an earlier finding and to report a broken earlier fix as a new finding. No reviewer reviewed its own text.
- **Defence.** The drafting agent ruled on every finding in writing. A partial rebuttal went back to the reviewer who raised it. A dispute went to a fresh judge agent, unless the drafting agent withdrew the rebuttal first.
- **Drafting.** From v3, each document was revised by a separate drafting agent working from the same written fix list. None of them reviewed.
- **A note on models.** At the user's request the model was changed partway through grounding. Every reviewer, judge, and drafting agent ran on the model the user chose.
- **Raw files.** `round-<n>/<reviewer>.md` holds each review; `round-<n>/defence.md` holds the rulings; `round-1/judge-PA-03.md` holds the one judge ruling.
